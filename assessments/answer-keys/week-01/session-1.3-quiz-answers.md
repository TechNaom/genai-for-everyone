# Answer Key — Session 1.3 Quiz

**1.** B. (A is false — capability varies by task and tier, not by open/closed status alone. C is false — many open-weight models have licensing conditions. D is false — the difference is real and substantial, covering data control, customization, and infrastructure burden.)

**2.** It's incomplete because "best" depends entirely on the task and the constraints involved — capability, speed, cost, context length, and compliance can all point to different answers depending on what you're building. The better question is: "best for this specific task, given which constraints matter most here?"

**3.** B — Speed matters most because a real user is actively waiting; a slow response directly hurts the experience, while most simple chat-widget questions don't require frontier-level reasoning capability.

**4.** Compliance and data-handling requirements (e.g., confirmed agreements for handling sensitive health data, data residency policies) — these can eliminate otherwise-strong options entirely, so they should be checked before investing time comparing capability or cost among options that might not even be permitted.

**5.** Worth investigating: whether the simple features (like a short confirmation message) actually need frontier-tier capability, or whether a smaller, faster, cheaper tier from the same provider would produce equally good results at a fraction of the cost and with lower latency. This is a common, avoidable cost/latency inefficiency — paying frontier prices for tasks that don't need frontier capability.

**6.** The flaw: benchmark rankings shift constantly and measure capability in ways that may not reflect your actual use case at all. A model that tops a reasoning benchmark might be slower, far more expensive, or non-compliant for a given application compared to a "lower-ranked" model that's actually the better practical fit. Chasing the top benchmark spot ignores speed, cost, context length, and compliance entirely — exactly the dimensions this chapter emphasized.
