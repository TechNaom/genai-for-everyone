# Answer Key — Session 7.1 Quiz

**1.** (1) What specific problem, for what specific user? (2) What does it actually do, end to end? (3) What GenAI techniques from the program does it use, and why? (4) How will you know if it worked?

**2.** It fails the "specific problem, specific user" test — it's a wish, not a scope. It gives no concrete end-to-end description and no way to know if it succeeded, so it can't actually be scoped down into buildable work in the time remaining.

**3.** False. A strong capstone should visibly use 2-3 techniques from the program (e.g., RAG + evaluation, or agents + guardrails) for a real reason — a project that's "just a chatbot" wastes the depth built up over the previous six weeks and doesn't showcase distinct skills.

**4.** Cut scope down to something finishable in the time remaining, rather than trying to build the full 3-week idea in 2-3 sessions. A finished, well-evaluated small project is worth more in a portfolio/interview than an unfinished ambitious one — size the project to the time actually available.

**5.** Because scope tends to silently expand mid-build without a written boundary — stating explicitly what's out of scope is what stops "just one more feature" creep and keeps the project finishable in the remaining time.

**6.** It's specific, measurable, and falsifiable — you can check it against a golden dataset and get a clear yes/no/percentage answer. "It feels good to use" is subjective, can't be checked objectively, and gives no signal about what's actually failing (exactly the eval-mindset lesson from Week 5).

**7.** Come back with a scoped proposal — a specific problem, specific user, an approach, a success metric, and explicit non-goals — rather than disappearing to build an ambitious, unscoped demo. Scoping the ambiguous request is the highest-leverage first move, not writing code.
