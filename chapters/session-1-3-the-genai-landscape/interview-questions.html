Session 1.3 Interview Prep 8 min read

Interview Questions: The GenAI Landscape

Interviewers listen for trade-off reasoning and concrete examples, not memorized definitions. These map to how early-career GenAI interviews actually open.

1 How would you choose between an open-weight model and a closed/proprietary API for a new project?
Strong answer

Frame it as a structured trade-off. Closed models (e.g., Claude, GPT, Gemini) typically offer stronger out-of-the-box capability and zero infrastructure burden. Open-weight models (e.g., Llama, Mistral, DeepSeek) offer cost control at scale, data privacy, and self-hosting flexibility, but require GPU infrastructure and more operational work. The "right" answer depends on which constraint dominates — cost, privacy/compliance, or raw capability.

Red flags

Declaring one universally "better," or assuming "open" always means free and unrestricted — it's a claim about downloadable weights and self-hosting, not necessarily open training data or a permissive license.

Follow-up

"When would self-hosting an open-weight model actually be cheaper?" (Answer: at high, predictable volume, where fixed GPU cost beats ongoing per-token API fees.)

2 A startup wants to use the most powerful model available for every single feature, regardless of cost. What would you push back on, and why?
Strong answer

Many features — a short confirmation message, a simple classification — work fine on a smaller, faster, cheaper tier. Frontier capability is wasted there, while the cost (often 10x+ on output tokens) and added latency are real. The disciplined move is to build with a strong model first, then test explicitly whether a cheaper tier is good enough per feature, rather than defaulting to the biggest model everywhere.

Red flags

Agreeing that "more powerful is always safer," or claiming to know the answer without proposing to actually test the cheaper tier on the real task.

Follow-up

"How would you decide which features can drop to a cheaper tier?" (Answer: run the real task on both tiers and compare quality against the cost/speed gap — measure, don't assume.)

3 What's the difference between a model's capability and its speed, and when does speed matter more?
Strong answer

Capability is how well the model handles complex reasoning, writing, or coding — roughly what benchmarks measure. Speed (latency) is how fast it responds and how soon the first token appears. Speed matters more for real-time, user-facing apps — a live chat widget a person is waiting on — where a small quality gain isn't worth users staring at a spinner. Capability matters more for unattended batch work where latency is invisible.

Red flags

Treating capability and speed as the same axis, or not being able to name a concrete case where speed wins.

Follow-up

"Why do most providers ship a tiered lineup?" (Answer: smaller models are faster and cheaper; a small/mid/frontier lineup lets you match the tier to each task.)

4 How would you evaluate model options for a healthcare application handling patient data?
Strong answer

Compliance and data handling come first, full stop. Start by filtering to providers that offer a signed compliance agreement for sensitive health data and acceptable data-residency guarantees — possibly a self-hosted open-weight model so data never leaves your infrastructure. Only then compare capability and cost among the options that already clear that bar. Verify commitments directly with the provider's enterprise team, since documentation lags reality.

Red flags

Leading with "whichever model is most capable," or trusting a marketing/docs page for a compliance claim instead of confirming it directly.

Follow-up

"Could a less capable model be the correct choice here?" (Answer: yes — if it's the only one that satisfies compliance, capability is secondary.)

5 Why might a single company reasonably use three different models across three features, instead of standardizing on one?
Strong answer

Because different features have different dominant constraints. A customer-facing chat widget prioritizes speed and cost (a small fast tier). An overnight contract-summarizer prioritizes capability and context length (a frontier, large-context model). A feature touching protected data prioritizes compliance (a filtered or self-hosted option). There's no "house model" requirement — matching the model to each task's constraints is the actual skill.

Red flags

Insisting standardization is always better for simplicity, without acknowledging the constraints that make one model a poor fit for another feature.

Follow-up

"What's the downside of using many models?" (Answer: added operational and evaluation overhead — so re-evaluate on a cadence, not constantly.)

6 A founder says "we should always use whichever model is #1 on the latest benchmark." What's the flaw?
Strong answer

"Best" is an incomplete question — the real question is "best for what task, under which constraints?" A benchmark measures capability, which is the most volatile and most overweighted dimension, and ignores speed, cost, context length, and compliance that often decide real applications. A model 2% better on a benchmark is rarely worth a large cost or latency penalty, and benchmarks shuffle monthly, so chasing #1 means constant churn.

Red flags

Accepting benchmarks as a complete decision tool, or not connecting the flaw to the specific dimensions a benchmark leaves out.

Follow-up

"How often should you actually re-evaluate model choice?" (Answer: on a cadence — quarterly is common — not every launch.)
