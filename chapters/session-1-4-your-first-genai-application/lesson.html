Your First GenAI Application

On this page 1. The three roles 2. Statelessness 3. The request-response cycle 4. A realistic mistake
Not a demo, not a simulation — an actual working chatbot. This is also where a handful of conceptual gaps tend to surface for the first time: things that were invisible while we were just talking about LLMs, but become unavoidable the moment you write code that calls one. The biggest, which surprises almost everyone: the model has no memory of your previous messages unless you explicitly send them again, every single time. That one fact reshapes how you'll think about every chatbot and every API call for the rest of this program.
Sub-topic 1 of 4

1. The three roles — system, user, assistant

Every message you send to a modern LLM API isn't just "text in, text out." It's a sequence of labeled turns, each tagged with a role. Understanding these three roles is the single most important piece of mechanical knowledge in this session.

What is... the system role? Instructions from you, the developer — set once, defining how the model should behave for the whole conversation. The end user never sees or writes it. Think of it as the briefing you give a new employee on day one ("You're a support agent; be concise; if you don't know, say so") — operating context they carry into every conversation, not something the customer said.

The user role is the live input from the actual person using your app — the question they typed. This is the part that changes every single turn.

The assistant role is the model's own previous responses. This matters more than it first seems, because of Part 2: in a multi-turn conversation you don't send just the system prompt and the latest user message — you send the entire history, including everything the assistant said earlier, every single time.

Put together, a real request (simplified) looks conceptually like this — all four entries get sent together, even though only the last line is "new":

One request, four role-tagged entries 
system:    "You are a helpful coding assistant specializing in Python..."
user:      "How do I read a CSV file in Python?"
assistant: "You can use the built-in csv module, or pandas for more..."
user:      "Show me the pandas version."

In code, that history is usually a plain Python list of dictionaries, each with a role and content key. Here's the exact shape you'll build today — no API call, just the data structure:

roles.py
Click "Run Code" — the system prompt is sent separately, so it isn't in this list.
Go Deeper: why is the system prompt separate from the list?

Most APIs (including Anthropic's) take the system prompt as its own top-level system= argument, distinct from the messages list of alternating user/assistant turns. That's a deliberate design choice: the system prompt is stable developer-owned configuration, while messages is the growing, user-driven conversation. Keeping them apart makes it obvious which text you control versus which text your user drives.

Quick recap
  • system — developer instructions, set once, invisible to the user.
  • user — the live human input, new every turn.
  • assistant — the model's own previous replies, re-sent every turn.
Sub-topic 2 of 4

2. The most important mechanical fact — statelessness

Here it is, as plainly as possible: the model does not remember your previous messages on its own. Each API call is independent. If you want the model to "remember" something said three messages ago, you — the developer — have to include that entire earlier conversation in every new request.

What is... statelessness? A stateless system keeps no memory of past requests between calls. The LLM receives one block of role-tagged text, predicts what comes next, and then retains nothing. The next call starts from a blank slate unless you re-send the history yourself.

When you use Claude.ai or ChatGPT it feels like a continuous conversation with persistent memory. That feeling is an illusion maintained by the application layer, not a property of the model. Behind the scenes, every time you send a new message, the app silently re-sends the entire conversation history — every previous user message and assistant reply — bundled with your new message as one fresh request.

So when you build your own chatbot today, you are responsible for what the chat app does invisibly: keep a running list of the conversation, and send that whole list with every request. Forget it, and your bot has no memory of anything said before — it feels broken, even though the model works exactly as designed.

The analogy: a brilliant consultant with no memory between meetings Imagine hiring a genuinely excellent consultant who has zero memory between meetings. Every time you meet, you must hand them a full transcript of every previous meeting before they can pick up where you left off. Forget the transcript and they'll greet you like a stranger, even if you last spoke five minutes ago. That's not a flaw in their intelligence — it's just how their memory works, and it's on you to bring the transcript every time. That is exactly how working with an LLM API feels.
Quick recap
  • Every API call is independent — the model remembers nothing on its own.
  • The "continuous conversation" feeling is created by the app re-sending full history each time.
  • In your own code, maintaining and re-sending that history is your job.
Sub-topic 3 of 4

3. The request-response cycle, end to end

Let's demystify what otherwise looks like a black box. Here's exactly what happens when your code "talks" to an LLM:

The five-step cycle 
1  Your code builds a request
   (system prompt + role-tagged messages, newest user turn last)
      |
2  The provider's servers run the model on everything in that request
   (the tokenize -> embed -> predict loop from Session 1.2)
      |
3  A structured JSON response comes back
   (generated text PLUS metadata: model, tokens used, stop reason)
      |
4  Your code extracts the text and does something with it
   (print it, show it in a web page, speak it aloud)
      |
5  If the conversation continues, append BOTH the user message
   AND the assistant reply to your running history -> back to step 1

Two details from that diagram catch people off guard. First, the response in step 3 is structured data, not raw text — you have to reach into it to pull out the generated string. Second, step 5 is the loop-closer that makes multi-turn memory work, and it's the one beginners skip.

What is... in the response, beyond the text? The reply comes back as JSON containing the generated text plus metadata: which model ran, how many input and output tokens were consumed (that's what you're billed on), and why generation stopped (a natural end, or hitting your max_tokens limit). Your code reads the text out of that structure — in Anthropic's SDK, it lives at response.content[0].text.

This cycle, repeated, is the entirety of how every chatbot you've ever used actually works under the hood. There's no hidden magic beyond what you'll build yourself in today's exercise.

Quick recap
  • Build request → send → receive structured JSON → extract text → append both turns to history.
  • The response is a data structure with metadata, not a bare string.
  • Step 5 — appending the reply too — is what keeps the next turn coherent.
Sub-topic 4 of 4

4. A realistic mistake, worked through

Here's a mistake almost every beginner makes once. Recognizing it now saves real debugging time later.

The setup: your chatbot's first exchange works great. The user asks a follow-up that depends on the previous answer — "can you make that shorter?" — and the model responds as if it has no idea what "that" is, sometimes asking "shorter version of what?"

What went wrong: almost certainly, the code only sends the latest message each turn, not the full history. The model isn't being forgetful — it genuinely never received the earlier exchange. Here's the buggy shape: a brand-new one-message list, rebuilt every turn.

forgetful.py (buggy) 
while True:
    user_input = input("You: ").strip()

    # BUG: a fresh one-message list every turn — nothing earlier is sent.
    messages = [{"role": "user", "content": user_input}]

    response = client.messages.create(
        model=MODEL_NAME, max_tokens=500,
        system=SYSTEM_PROMPT, messages=messages,
    )
    print("Bot:", response.content[0].text)

The fix: keep one running list, created once outside the loop. Every turn, append the user's message, send the entire list, then append the assistant's reply too. That last append is the step beginners skip — and skipping it is the #1 cause of a "forgetful" bot. Here's the corrected chatbot in full, exactly what you'll build in today's exercise:

chatbot.py (fixed) 
import os, sys
from dotenv import load_dotenv
from anthropic import Anthropic

load_dotenv()
SYSTEM_PROMPT = "You are a friendly, concise assistant."
MODEL_NAME = "claude-haiku-4-5-20251001"

client = Anthropic(api_key=os.environ["ANTHROPIC_API_KEY"])

# ONE running list, created once — this list IS the conversation's memory.
conversation_history = []

while True:
    user_input = input("You: ").strip()
    if user_input.lower() == "quit":
        break

    # 1. append the user's new message
    conversation_history.append({"role": "user", "content": user_input})

    # 2. send the ENTIRE history, not just this turn
    response = client.messages.create(
        model=MODEL_NAME,
        max_tokens=500,
        system=SYSTEM_PROMPT,
        messages=conversation_history,
    )

    # 3. extract the text from the structured response
    assistant_reply = response.content[0].text
    print(f"Bot: {assistant_reply}\n")

    # 4. append the assistant's reply too — the step everyone forgets
    conversation_history.append({"role": "assistant", "content": assistant_reply})

Thought process: Before writing a chatbot, an experienced dev decides where the memory lives: one list created once, outside the loop, so it survives across turns. The easy-to-miss subtlety is that both sides of each exchange must be appended — the user message before the call and the assistant reply after — or the model can't see its own prior answers. They'd also guard the missing-API-key case up front so the script fails with a clear message instead of a stack trace.

Quick recap
  • The "forgetful" bug is sending only the latest message, not the full history.
  • Fix: one list, created once; append the user turn, send it all, append the reply.
  • Forgetting to append the assistant's reply is the single most common cause.
In the Real World
  • Every production chat product — support bots, coding assistants, customer-facing widgets — is doing exactly what you built here: storing a running message list and re-sending it each turn. The "memory" users feel is application code, not the model.
  • Because history is re-sent every turn, long conversations cost more and eventually hit the context window — real teams trim or summarize old turns to stay within limits and control token spend, a direct consequence of statelessness.
  • "Our chatbot forgets what the user just said" is a genuinely common bug ticket, and the root cause is almost always a missing history append — the exact mistake worked through in Part 4.

Points to Remember

  • Every request to an LLM API is structured with roles: system (developer instructions, set once), user (live human input), and assistant (the model's own previous responses).
  • The model has no memory between API calls on its own. Any sense of "continuous conversation" is created by your code re-sending the entire history with every new request.
  • The illusion of persistent memory in chat apps is maintained by the application layer, not the model — every new message silently includes everything said before it.
  • The request-response cycle is: build a role-tagged request → send it → receive structured JSON → extract the text → append both the new user message and the new assistant reply to your running history.
  • The most common beginner bug is forgetting to maintain and resend conversation history, which makes a chatbot seem "forgetful" even though the model is behaving exactly as designed.
