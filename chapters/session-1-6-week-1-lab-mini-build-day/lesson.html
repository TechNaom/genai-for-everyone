Sub-topic 1 of 5

1. The build: "Explain It To Me Simply"

You're building a command-line tool that takes any topic and an audience level, and produces an explanation calibrated to that audience — a 10-year-old gets a different explanation than a working professional, who gets a different explanation than a domain expert wanting a quick refresher.

This sounds simple. It's deliberately simple — today isn't about complexity, it's about correctly assembling pieces you already understand into something that actually works end to end.

What is... a synthesis build? A synthesis build is a small project whose whole purpose is to make you use several separate ideas together, in one working artifact, rather than one idea in isolation. The value isn't the tool itself — it's the moment you discover which concepts you can actually wield versus which ones only felt clear while reading.
Quick recap
  • The tool takes a topic and an audience level and returns a calibrated explanation.
  • It is intentionally simple — the goal is assembly, not complexity.
  • "Works end to end" is the bar for today.
Sub-topic 2 of 5

2. Why this tool touches all of Week 1

This project was chosen specifically because building it well requires touching almost everything from this week. Each earlier session shows up as a concrete design decision:

Session 1.1 — predictive vs. generative
You're building a generative tool — every output is freshly composed for the specific topic and audience, not selected from a fixed list.
Session 1.2 — how LLMs work
Audience-appropriate explanations are fundamentally a context problem — you're shaping what the model considers when generating, the same idea as a context window holding relevant information.
Session 1.3 — the landscape
You'll make a real, defensible choice about which model tier fits this task. Hint: think hard about whether you need a frontier-tier model, or whether a smaller, faster tier does just as well.
Session 1.4 — your first application
The literal foundation: system/user roles, constructing a request, parsing a response.
Session 1.5 — hallucination & bias
You'll add a small but meaningful safeguard: flagging when a topic is the kind of thing where hallucination risk is especially high (very specific dates, statistics, niche technical claims).
What is... a well-scoped task? A well-scoped task is one with clear, bounded requirements that a smaller, cheaper model can handle reliably. "Explain this topic at this level" is well-scoped; "reason through a novel multi-step proof" is not. Recognizing the difference is exactly the Session 1.3 judgment that keeps GenAI systems fast and affordable.
Quick recap
  • Generative (1.1), context shaping (1.2), model choice (1.3), request/response (1.4), honesty flag (1.5) — all five, in one tool.
  • The tool is a well-scoped explanation task, so a lighter model tier is the right call.
Sub-topic 3 of 5

3. The build, step by step

Six steps take you from an empty file to a working tool. The heart of it is the three system prompts — that's where Session 1.4's roles become concrete, and where "done well" and "done technically" diverge.

  1. Design the audience levels. At least three distinct levels (a reasonable default: "curious beginner / kid," "working professional, no specialized background," "domain expert wanting a refresher"). For each, write one sentence on what should change — not just vocabulary, but depth, analogy use, and assumed background.
  2. Design the system prompt. Not just "explain simply" (too vague) but something that specifies tone, length, and what kind of analogies fit each level.
  3. Build the input handling. Accept a topic and a level, validate the level against your defined options, and give a clear error if something's missing or invalid.
  4. Make the API call. Apply Session 1.4 directly: construct the request with the right roles, send it, parse the response, and handle a failed call gracefully rather than crashing.
  5. Add the honesty flag. Before displaying, check whether the topic or explanation contains specific numbers, dates, or claims worth independently verifying — and if so, append a short, non-alarmist note.
  6. Test across all three levels with the same topic. If "explain quantum entanglement" produces meaningfully different output per level, it works. If all three sound suspiciously similar, your system prompt needs more specific per-level instructions.

Here is the skeleton the exercise scaffolds for you — the three system prompts and the API call are the parts that integrate this week's ideas:

explainer.py 
MODEL_NAME = "claude-haiku-4-5-20251001"  # a fast, low-cost tier (Session 1.3 judgment)

SYSTEM_PROMPTS = {
    "beginner": (
        "You explain things to a curious 10-year-old with no background "
        "knowledge. Use ONE simple, everyday analogy. NEVER use jargon "
        "without immediately explaining it. Keep it to 3-4 short sentences."
    ),
    "professional": (
        "You explain things to an intelligent working professional with no "
        "specialized background in this topic. Moderate vocabulary is fine; "
        "avoid deep jargon unless you define it. Aim for 4-6 sentences."
    ),
    "expert": (
        "You give a quick, dense refresher to someone with deep domain "
        "expertise. Skip basic setup. Use precise terminology freely. "
        "Focus on nuance rather than fundamentals. 2-4 sentences."
    ),
}

def explain(client, topic, level):
    response = client.messages.create(
        model=MODEL_NAME,
        max_tokens=400,
        system=SYSTEM_PROMPTS[level],
        messages=[{"role": "user", "content": f"Explain: {topic}"}],
    )
    return response.content[0].text

Thought process: the entire quality of this tool lives in the three system prompts, not the code around them. So the real "thought process" is prompt design: for each level, decide what vocabulary is banned, what kind of analogy is required, what background you're allowed to assume, and how long the answer should be. Vague instructions ("explain simply") produce vague differentiation; concrete behavioral instructions produce real differentiation. This is exactly the judgment Week 2 turns into a repeatable skill.

Go Deeper: why the honesty flag is deliberately crude

A keyword scan will flag some safe text and miss some risky text — it's not a real fact-checker. That's on purpose. The point of Step 5 isn't to solve hallucination (no current tool does that fully — see Session 1.5), it's to build the habit of pairing every generated output with an honest signal about where it might be wrong. Later weeks replace this crude heuristic with grounding, retrieval, and evaluation — but the instinct to flag uncertainty starts here.

Quick recap
  • Six steps: levels → system prompts → input handling → API call → honesty flag → test all three levels.
  • The system prompts are the heart of the build.
  • The honesty flag is a simple heuristic that builds a habit, not a fact-checker.
Sub-topic 4 of 5

4. "Done well" vs. "done technically"

It's possible to build something that runs without errors and still misses the point of the exercise. Here's the difference, concretely.

Done technically (passes, but misses the point) The tool accepts a topic and a level, sends a generic prompt like "explain {topic} for a {level}," and prints whatever comes back. It runs. It doesn't crash. But the outputs across levels often sound nearly identical, just slightly shorter or longer — because the system prompt never actually specified what should differ beyond length.
Done well (the actual goal) The system prompt for each level specifies concrete behavioral instructions — for the "curious kid" level, explicitly requiring a relatable everyday analogy and forbidding jargon entirely; for the "domain expert" level, explicitly allowing field-specific terminology and skipping basic setup the expert would find condescending. The difference isn't more code — it's a more thoughtful system prompt.

That distinction — recognizing that near-identical output is a system-prompt problem, not a code problem — is itself a Week 1 skill, and exactly the kind of judgment Week 2 (Prompt Engineering) will formalize into a repeatable practice.

Quick recap
  • "Runs without errors" and "demonstrates understanding" are different bars.
  • Near-identical output across levels is a system-prompt problem, not a code problem.
  • Quality lives in the prompt's specificity: banned jargon, required analogy types, assumed background.

5. Reflection: what clicked, what's fuzzy

Before moving into Week 2, take five honest minutes (genuinely worth doing, not a platitude) to answer these for yourself:

  • Could you explain, without looking back, why an LLM might confidently give a wrong answer to a very specific factual question? If shaky, revisit Session 1.5.
  • Could you sketch, from memory, what happens between typing a message and seeing a response, including the role of conversation history? If not, Session 1.4 is worth a second pass.
  • Did building today's tool surprise you anywhere — a place where you thought you understood something until you had to implement it? That surprise is valuable information.

This isn't busywork. The single best predictor of struggling in Week 2 (and beyond) is carrying forward an unexamined gap from Week 1, because everything after this point assumes this foundation is solid.

Quick recap
  • Honest self-assessment now is cheaper than discovering a gap later.
  • Shaky on hallucination → Session 1.5. Shaky on request/response → Session 1.4.
  • The surprises during the build are the most useful signal you have.
In the Real World
  • Audience-adaptive explanation is how real products ship the same content to different tiers of user — a "explain like I'm five" toggle, an "expert mode," a plain-language summary of a legal or medical document.
  • The "done technically vs. done well" gap is the single most common reason a demoable GenAI feature never becomes a shippable one — it runs, but the differentiation is shallow.
  • Pairing every generated answer with an honesty signal (a source, a confidence note, a "verify this" flag) is now standard practice in production GenAI, from search summaries to customer-support copilots.

Points to Remember

  • Today's build deliberately touches every major idea from Week 1 — predictive/generative, context and tokens, model choice, request/response mechanics, and honest handling of hallucination risk.
  • "Runs without errors" and "actually demonstrates understanding" are different bars. A tool that produces nearly identical output across audience levels has a system-prompt problem, not a code problem — and recognizing that distinction is itself a Week 1 skill.
  • The quality of an adaptive tool lives almost entirely in the system prompt's specificity. Vague instructions produce vague differentiation; concrete behavioral instructions (banned jargon, required analogy types, assumed background) produce real differentiation.
  • Honest self-assessment now is cheaper than discovering a gap later. Week 2 builds directly on this week's foundation; an unexamined gap here compounds.
