Interview Questions: Anatomy of a Great Prompt

Prompt engineering is consistently described by hiring managers as the single most "immediately testable" GenAI skill — interviewers often hand you a bad prompt live and ask you to fix it on the spot, not just describe techniques abstractly. Expect to be asked to do prompt engineering, not just define it. Each question below includes what a strong answer sounds like, common red flags, and a natural follow-up. Click any question to expand it.

1 Here's a vague prompt: "Write something about our product." What's wrong with it, and how would you fix it?
Strong answer

Name the missing elements specifically — no audience, no format, no length, no tone, no constraints — rather than a vague "it's not detailed enough." Then actually produce a rewrite live: e.g. "Write a 100-word product description for our wireless noise-canceling headphones, targeting frequent-traveling professionals, emphasizing battery life and comfort, confident but not salesy tone, single paragraph." Interviewers want to see the rewrite, not just the critique.

Red flags

Stopping at "it's too vague" without naming which specific pillars are missing, or describing the fix in the abstract instead of writing an actual improved prompt.

Follow-up

"Which of the four pillars did each part of your rewrite address?" (e.g. "targeting frequent travelers" is context, "100 words" and "single paragraph" are constraints/format.)

2 What's the difference between giving a model context and giving it constraints? Why do you need both?
Strong answer

Context is background information the model needs to give a relevant answer — who the audience is, what the business does, what situation this is responding to. Constraints are boundaries on the output itself — length, format, tone, what to avoid. Missing context produces an answer that's on-topic but generic or wrong for the situation; missing constraints produces an answer that's relevant but the wrong shape or length to actually use. You need both because they solve different failure modes.

Red flags

Treating context and constraints as interchangeable, or being unable to give a concrete example of each.

Follow-up

"Give me an example of a prompt with great context but no constraints, and describe what would go wrong." (e.g. full backstory on a refund request but no length limit — the model might write a 500-word email nobody will read.)

3 How do you know when a prompt has enough detail versus when it needs more?
Strong answer

The test: could a competent person, given only this prompt, produce something close to what's needed without guessing at anything important? If yes, it's enough — more detail past that point is diminishing returns and can clutter focus. If the output comes back unusable, look for a specific fact you knew but never told the model; that gap is almost always the actual fix, not "make the whole prompt longer."

Red flags

Answering "just add more detail until it works," with no test for knowing when to stop, or assuming a longer prompt is automatically a better one.

Follow-up

"Can a prompt be too long and still fail? Why?" (Yes — it can be missing exactly one critical detail despite being long and well-formatted; length doesn't equal completeness.)

4 Walk me through rewriting a bad prompt live, explaining each change as you make it.
Strong answer

Narrate the process pillar by pillar rather than jumping straight to a polished final version: start from the vague prompt, add clarity (name the exact deliverable), add context (the background the model needs), add constraints (length/tone/boundaries), add format (the output shape) — saying out loud which pillar each addition fixes as you go. This mirrors the worked "Help with customer email" rewrite from the lesson.

Red flags

Silently producing a final polished prompt with no narration of the reasoning — interviewers are evaluating the process, not just the end result.

Follow-up

"Which single addition mattered most, and how would you know if you'd skipped it?" (Usually context or constraints — skipping it produces an answer that's plausible but wrong for the actual situation or unusable in shape.)

5 A teammate's prompt works great in testing but produces inconsistent output in production. What would you investigate first?
Strong answer

Check whether the test examples covered a narrow range of inputs while production sees far more variety in phrasing, edge cases, and context. Check whether the prompt gives explicit constraints (tone, format, boundaries) or leaves the model to "figure it out" — ambiguity that a handful of test cases happened not to expose. This is diagnosing a robustness gap in the prompt itself, not assuming the model just "got worse."

Red flags

Jumping straight to "switch models" or "add more examples" without first checking whether the original prompt was ever specific enough to be robust.

Follow-up

"What would you change about the prompt itself, not the process around it?" (Tighten context/constraints, or add a couple of representative examples showing the expected tone — the seed of few-shot prompting, next session.)

Rapid-Fire Review

Quick recall check — fill in each blank and hit Check.

🎉 5 for 5 — you're ready to talk about prompt anatomy in an interview.

Strategy Tips

  • Cover the "Strong answer" line, answer out loud, then check yourself against it — that's how these are meant to be used for self-testing.
  • Practice the live-prompt-rewrite format specifically (Question 4) — it's the most common live-coding-equivalent for prompt engineering roles, and the one most people under-practice because it feels less "studyable" than definitions.
  • Interviewers are listening for trade-off reasoning and a real rewrite, not textbook recall. When in doubt, narrate which pillar each change addresses.
