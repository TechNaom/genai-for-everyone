Session 2.1 Project 20 min build

The Thoroughness Trap

The Pro path build for this session — a diagnostic exercise built directly on Part 4 of the lesson: a prompt can be long, well-formatted, and detailed-looking while still missing the one critical piece of context that actually matters.

Example run

Output 
1. Outage apology email
   Missing detail: The prompt never mentions the SLA service credit
   that Enterprise customers are contractually owed and are already
   receiving.
   Why it fails: Without that detail, the generated email apologizes
   but says nothing about the credit -- Enterprise customers who know
   their contract will notice the omission and may escalate a support
   ticket asking where their credit is, creating exactly the confusion
   the email was supposed to prevent.
   Fixed prompt: "Write an email to all customers explaining that our
   service had a 4-hour outage yesterday..."
How to run Download starter.py below and run python starter.py. No API key, no internet access, and no external libraries needed — this is a pure diagnostic-reasoning exercise.
starter.py solution.py (reference)

What to build

Four CASES, each pairing a thorough_prompt that reads as genuinely reasonable — clear task, decent length, sensible tone and format guidance — with a business_situation paragraph that reveals one real fact the prompt writer forgot. Fill in the three None fields for each case:

  • missing_critical_detail — the ONE fact missing from the prompt.
  • why_it_fails — one sentence on what breaks downstream without it.
  • fixed_prompt — the original prompt, rewritten to actually include that fact.
The habit this trains Read each thorough_prompt on its own first — it should look genuinely good, not obviously lazy. Then read the business_situation, which contains the fact a real stakeholder in that scenario would already know. Your job is to spot the gap between what the prompt says and what the situation actually requires — exactly the way you'd have to on the job when a prompt "looks fine" but the output still causes a real problem.

Ideas to make it your own

  • Write a fifth case from your own work or coursework — a prompt that looked thorough to you at the time but was missing something you only noticed later.
  • Run both the original thorough_prompt and your fixed_prompt through a real model (free tier of any provider) and compare how the outputs actually differ.

Why this project matters

The most expensive prompt failures aren't the obviously lazy one-liners — those get caught immediately because the output is obviously bad. The expensive ones are prompts that look complete: good length, clear tone, solid formatting, and one missing fact that nobody notices until it causes a real support ticket, a compliance problem, or a production bug. Learning to interrogate a "thorough-looking" prompt against the actual business situation, not just against a length or formatting checklist, is the habit this project is built to train.
