Session 2.4 Interview Prep 8 min read

Interview Questions: Structured Outputs

Prompt engineering is consistently described by hiring managers as the single most "immediately testable" GenAI skill — interviewers often ask candidates to write or critique an actual prompt live, not just describe techniques abstractly. Structured-output questions are where that shows up hardest, because there's a concrete, checkable right answer: did your approach actually survive a model returning something imperfect? Each question below includes what a strong answer sounds like, common red flags, and a natural follow-up. Click any question to expand it.

1 Why is getting reliable JSON output from an LLM harder than it sounds, and how do you make it more reliable?
Strong answer

Naming the actual failure modes: models can add explanatory text around the JSON, use inconsistent field names, or produce malformed syntax under certain prompts. Then naming the mitigations as a set, not just one: explicit schema definition in the prompt, asking for JSON-only output with no preamble, using a model's structured-output/JSON mode if available, and — the one that matters most — validating and parsing defensively in code rather than trusting the output blindly.

Red flags

Naming only one technique (usually "just ask for JSON"), or treating prompt wording alone as a complete solution with no mention of code-side handling.

Follow-up

"Which of those techniques would you keep if you could only pick one, and why?" (Defensive parsing — it's the only one that doesn't depend on the model behaving correctly.)

2 You're building a resume parser that returns structured JSON. What happens if the LLM returns a field with the wrong data type, and how do you guard against that breaking your application?
Strong answer

Recognizing that a wrong type (e.g. "years_experience": "8 years" instead of 8) is invisible to json.loads() — the JSON is syntactically valid, so a parse-only check passes it straight through. The guard is a separate schema/type validation step run on the parsed dict before the data is used downstream, with a defined fallback or error-handling path when validation fails — and an acknowledgment that even a well-tested prompt won't guarantee 100% type compliance.

Red flags

Assuming "it parsed successfully" is the same as "it's correct," or having no answer for what happens after validation fails (crash, silently use the bad value, etc.).

Follow-up

"Where in the pipeline would you put that validation step, and what would you do on failure?" (Right after parsing, before the data reaches any business logic; on failure, log it, use a safe default, or flag the record for human review rather than crashing or silently proceeding.)

3 What's the difference between a prompt that "successfully produces parseable JSON" and one that's "production-reliable"?
Strong answer

"Parseable" only means it worked in your testing — json.loads() didn't throw. "Production-reliable" means the surrounding system has defensive parsing for when output isn't perfect, type validation beyond JSON syntax, explicit handling for missing data, and has been tested against a genuinely broad and messy range of inputs, not just a handful of convenient examples used during development.

Red flags

Treating "it worked when I tried it" as equivalent to "it's reliable," with no mention of testing breadth or code-side safeguards.

Follow-up

"How would you go about finding the inputs your prompt hasn't been tested on yet?" (Deliberately generate edge cases — missing fields, unusual formats, adversarial or malformed text — rather than only reusing convenient dev examples; this previews Week 5's evaluation practices.)

4 Why would you instruct a model to return null for missing fields instead of letting it guess?
Strong answer

A guess risks a confidently invented value being mistaken for verified data — directly connecting back to Session 1.5's hallucination warning, since the model has no internal signal distinguishing a fluent guess from a fluent fact. null is an honest, checkable signal that the information wasn't found in the source text; a plausible-looking guess is not, and it's far more dangerous precisely because it doesn't look wrong.

Red flags

Treating a guessed value as harmless because "it's usually close enough," or not connecting the risk back to hallucination.

Follow-up

"Does instructing null actually guarantee the model won't guess anyway?" (No — it's a real, documented failure mode that models can still fill in a value despite the instruction, which is why this alone isn't a complete guarantee and a human review step matters for high-stakes extraction.)

5 You've tested your extraction prompt on 10 examples and it works perfectly every time. Should you consider it production-ready? Why or why not?
Strong answer

Not necessarily — 10 examples, especially if they're the convenient ones used during initial development, may not represent the full range of real-world inputs the prompt will eventually face. Genuine production-readiness requires testing against a broader, more representative, and intentionally messier set of inputs. The candidate should also flag that "worked every time" on a small set doesn't rule out schema drift on unusual inputs later.

Red flags

Answering "yes, if it passed all my tests" with no interrogation of what those tests actually covered.

Follow-up

"What formal process exists for this later in the program?" (Week 5's evaluation practices — testing against representative, adversarial, and edge-case inputs as a discipline, not an informal spot-check.)

Rapid-Fire Review

Quick recall check — fill in each blank and hit Check.

🎉 5 for 5 — you're ready to talk about structured outputs in an interview.

Strategy Tips

  • Cover the "Strong answer" line, answer out loud, then check yourself against it — that's how these are meant to be used for self-testing.
  • Interviewers are listening for the two-layer answer — prompt-side mitigations and code-side defenses — not just "I'd write a good prompt."
  • If you can, describe a specific type-validation bug you'd guard against (like a numeric field coming back as a string) — concrete beats abstract every time.
