Session 2.4 Intermediate 25–30 min read

Structured Outputs

Every technique so far in Week 2 produced output meant for a human to read. This chapter is about output meant for code to read — and code doesn't forgive a stray sentence the way a human does.

On this page 1. Why Reliable JSON Is Harder Than It Sounds 2. Four Techniques That Actually Improve Reliability 3. A Worked Example: The Resume Parser 4. When Structured Output Still Goes Wrong
A human reading slightly-off prose barely notices. A parser handed slightly-off JSON crashes outright. That one sentence is the entire reason this chapter exists. The moment you build anything beyond a simple chatbot — a form-filler, a data extractor, an agent calling tools (which you'll formalize in Week 4) — you need the model's output in a precise, predictable shape your code can rely on. Getting this wrong is one of the most common sources of real production bugs in GenAI applications, and, encouragingly, it's almost always avoidable with a handful of disciplined practices. That's what today is about.
Sub-topic 1 of 4

1. Why Reliable JSON Is Harder Than It Sounds

It's tempting to assume that asking a model "return this as JSON" is enough. Sometimes it is. But models can — and regularly do — add explanatory text before or after the JSON ("Sure, here's the JSON you requested:"), use inconsistent field names across calls, produce syntactically malformed JSON (a trailing comma, an unescaped quote inside a string), or simply misunderstand which fields you actually wanted.

Why this happens, mechanically Recall Session 1.1: the model is predicting the most statistically plausible next token. "Sure, here's the JSON you requested:" followed by an explanation is an extremely common pattern in the kind of text models train on — people explaining what they're about to show you. Without explicit instruction otherwise, that conversational politeness pattern can leak into output specifically meant to be machine-parsed. It's not the model being careless; it's the same next-token mechanism from Session 1.1 doing exactly what it always does, applied to a context where you needed something stricter.
what_breaks_a_parser.txt 
"Sure, here's the JSON you requested:\n{...}"    -> extra text before the object
"{...}\nLet me know if you need anything else!"  -> extra text after the object
{"full_name": "..."}  vs  {"name": "..."}        -> inconsistent field naming
{"skills": ["Python", "SQL",]}                   -> trailing comma, invalid JSON
{"years_experience": "8 years"}                  -> right field, wrong type

Here's the real-world cost of getting this wrong: if your code does something like json.loads(model_response) and the model prepended "Here's the JSON:" before the actual object, that call throws an exception. In a live application, that's not a cosmetic issue — it's a crash, or at minimum a swallowed error that silently breaks a feature. This is precisely the gap between "looks like it works in a quick test" and "works reliably in production," and it's one of the most common, most avoidable gaps in real GenAI applications.

Quick recap
  • Models can wrap JSON in conversational text, use inconsistent field names, or produce malformed syntax — none of this is a hypothetical edge case.
  • The cause is mechanical: conversational-explanation patterns are extremely common in training data and can leak into machine-parsed output.
  • An unhandled json.loads() failure isn't cosmetic — it's a crash or a silently broken feature in production.

2. Four Techniques That Actually Improve Reliability

Technique 1: Explicit schema definition in the prompt Don't just say "return JSON" — show the exact shape you want, field by field, ideally with the expected type for each field. The second version below removes ambiguity about field names (is it "name" or "full_name"? "email" or "email_address"?) and explicitly forbids the conversational wrapper text that causes parsing failures.
weak-vs-strong.txt 
WEAK:   "Extract the name and email from this text as JSON."

STRONG: "Extract the name and email from this text and return ONLY a JSON
         object in exactly this format, with no other text before or after:
         {
           \"name\": \"string\",
           \"email\": \"string\"
         }"
Technique 2: Explicit "no preamble" instructions Directly instructing the model to return only the JSON, with no introductory or closing text, meaningfully reduces (though doesn't perfectly eliminate) the conversational-wrapper problem from Sub-topic 1. Phrases like "Respond with ONLY the JSON object, no other text" or "Do not include any explanation" are doing real, specific work — they're not just politeness filler.
Technique 3: A provider's structured-output / JSON mode, when available Many model providers offer a dedicated feature — sometimes called "JSON mode" or "structured outputs" — that constrains the model's output generation at a mechanical level to guarantee syntactically valid JSON, sometimes even validating against a schema you provide. When available, this is meaningfully more reliable than prompt instructions alone, because it's enforced by the generation process itself rather than relying on the model choosing to follow an instruction. Check your specific provider's documentation — exact implementation and naming varies.
Technique 4: Defensive parsing in your code — the most important one Here's the technique that matters most, and the one most often skipped: never assume the model's output is valid just because you asked nicely. Always parse defensively — try a direct parse, then fall back to extracting the span between the first { and last } if that fails, and return a clear failure signal rather than letting an exception propagate.

This isn't elaborate — it's a simple, honest acknowledgment that even a well-engineered prompt can occasionally fail, and your code's job is to handle that failure gracefully (log it, retry, fall back to a default) rather than crash the entire application. This connects directly to Session 1.5: even with every mitigation in this chapter applied, you are still working with a system that doesn't guarantee its own output, and good engineering plans for that reality rather than hoping around it. Quick recap
  • Technique 1 — give an explicit schema with types, not just "return JSON."
  • Technique 2 — explicitly forbid preamble/closing text.
  • Technique 3 — use a provider's JSON/structured-output mode when it's available; it's enforced mechanically, not just requested.
  • Technique 4, the most important — parse defensively in your own code, because it's the only technique that doesn't depend on the model behaving.

3. A Worked Example: The Resume Parser

Let's combine every technique from Sub-topic 2 into something realistic: a prompt that extracts structured data from a resume's text.

resume-extraction-prompt.txt 
Extract the following information from this resume text and return ONLY
a JSON object in exactly this format, with no other text before or after:

{
  "name": "string",
  "email": "string or null if not found",
  "years_experience": "number, your best estimate based on listed roles",
  "skills": ["array", "of", "strings"]
}

If a field cannot be determined from the text, use null for strings/numbers
or an empty array for skills. Do not guess at information not present.

Resume text:
{resume_text}

Notice several deliberate choices here: the schema is explicit with types (Technique 1); there's explicit handling instruction for missing data — null, not a guess, connecting straight back to Session 1.5's hallucination concerns, since an absent field is far better than a confidently invented one; and the "no other text" instruction guards against the conversational-wrapper problem (Technique 2). Combined with defensive parsing in the surrounding code (Technique 4), this is a realistic, production-reasonable approach — not a toy example.

Thought process: the real skill here isn't the Python try/except — it's deciding, before you ask an AI assistant to write it, exactly which failure modes the function must survive: wrapper text before the JSON, wrapper text after it, a response that isn't JSON at all, and a response that parses but has the wrong field types. A vague request like "write a function to parse JSON safely" gets you a bare try/except that still can't handle wrapper text. Naming the specific failure modes up front is what turns a generic try/except into the fallback-extraction logic this session actually needs.

Write the prompt you'd give an AI assistant to build this:

Paste your prompt into Claude, ChatGPT, Copilot, or whatever assistant you use, and compare what it builds against parse_model_json above — does it handle wrapper text on both sides, and does it fail with a clear signal (like None) instead of raising? That comparison is the real test, not a score.
Show a strong version of this prompt 
Write a Python function parse_model_json(raw_text: str) that safely parses JSON returned by an LLM. It must handle these cases without ever raising an uncaught exception: (1) raw_text is already valid JSON -- parse and return it directly; (2) raw_text is valid JSON surrounded by conversational wrapper text before and/or after it (e.g. "Sure, here's the JSON:\n{...}\nLet me know!") -- extract just the JSON object and parse that; (3) raw_text contains no valid JSON at all -- return None rather than raising. Do not use any external libraries beyond the standard library's json module.
Quick recap
  • A production-reasonable extraction prompt combines an explicit typed schema, a "no other text" instruction, and null-for-missing guidance.
  • Deciding the exact failure modes a parsing function must survive is the real design work — the code itself is straightforward once that's clear.
Sub-topic 4 of 4

4. When Structured Output Still Goes Wrong

Even with every technique applied, a few realistic failure modes remain worth knowing about — because "I told the model what to do" is not the same as "the model always does it."

Type mismatches You asked for years_experience as a number; the model returns the string "5 years" instead of the integer 5. Defensive parsing should validate types, not just successfully parse JSON syntax — successfully parsed JSON can still have the wrong shape.
Hallucinated fields, filled in anyway Despite explicit "use null" instructions, a model can still guess at a missing field — this is a real, documented failure mode, not a hypothetical. It's exactly why a human review step matters for any genuinely high-stakes extraction task, and why you shouldn't treat "I told it not to guess" as a guarantee.
Schema drift across many calls A prompt that reliably returns a consistent shape in your testing might occasionally drift on a particularly unusual input it wasn't tested against. This is part of why Week 5's evaluation practices exist: testing against a representative range of real inputs, not just a few convenient examples.
In the Real World
  • A resume parser that silently guesses "3 years experience" for a candidate with no dates listed doesn't just produce a wrong number — it can bias downstream ranking or filtering logic that trusts the field blindly.
  • Teams that ship structured-extraction features without type validation routinely discover the bug only when a downstream calculation (like sorting candidates by experience) throws or silently misbehaves on a string where it expected a number.
  • "It worked on my 10 test resumes" is one of the most common false-confidence traps in real GenAI feature launches — production input is always messier than development input.
Quick recap
  • Type mismatches survive syntax-valid JSON — validate types, not just that json.loads() succeeded.
  • Models can still hallucinate a value into a field you told them to leave null — instructions reduce but don't eliminate the risk.
  • A prompt that's consistent on your test set can still drift on unusual real-world inputs — broad testing is part of the fix, not a nice-to-have.

Points to Remember

  • Models can wrap JSON in conversational text, use inconsistent field names, or produce malformed syntax — none of this is a hypothetical edge case; it's common enough to plan for by default.
  • Four techniques that help: explicit schema definition with types, explicit "no preamble" instructions, a provider's structured-output mode when available, and defensive parsing in your own code.
  • Defensive parsing is the most important technique, because it's the one that doesn't depend on the model behaving — it's your code's responsibility to handle failure gracefully rather than crash.
  • For missing data, instruct null/empty rather than guessing — an absent field is far safer than a confidently hallucinated one, directly connecting to Session 1.5.
  • Successfully parsed JSON can still have the wrong shape or types — validate structure and types, not just JSON syntax validity.
