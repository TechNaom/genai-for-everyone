Session 2.5 Interview Prep 8 min read

Interview Questions: Prompt Systems & Application Design

Prompt engineering is consistently described by hiring managers as the single most "immediately testable" GenAI skill — interviewers often ask candidates to write or critique an actual prompt live, not just describe techniques abstractly. These questions probe the step past that: can you talk about prompts as something a team maintains, not just something one person writes once. Each question below includes what a strong answer sounds like, common red flags, and a natural follow-up. Click any question to expand it.

1 What's the difference between "a good prompt" and "a good prompt system," and why does that distinction matter for a real product?
Strong answer

A single good prompt solves one specific case; a prompt system involves reusable templates with variables, version control, consistent testing across many real-world inputs, and often chaining multiple prompts together — the difference between a one-off script and something you'd actually ship and maintain. A strong candidate frames it as a difference "in kind, not just scale," and can point to a concrete consequence (e.g. a hardcoded prompt buried in application code becomes hard to find, review, or roll back six months later, even if it was well-written on day one).

Red flags

Treating "prompt system" as just "a longer or more complicated prompt," or being unable to name a single concrete maintainability consequence of skipping structure.

Follow-up

"At what point does a project actually need this structure — is it worth it for a single prototype script?" (A good answer notes it's a judgment call tied to team size, lifespan, and number of prompts — not something every five-line script needs on day one.)

2 How would you organize a library of prompt templates for a team building several different AI features?
Strong answer

Separate prompts from application code (not hardcoding strings everywhere), a naming convention that describes each template's purpose, a docstring or comment documenting exactly what variables each template expects and what they mean, and ideally some lightweight testing so a prompt edit doesn't silently break a feature. Bonus points for connecting this forward to versioning ("so we can tell what changed and roll back") — this previews Week 6's prompt CI/versioning topic.

Red flags

Insisting a heavyweight framework or specific vendor tool is required — the discipline (separating, naming, documenting, testing) is what creates the value, not any particular tool.

Follow-up

"Two templates look almost identical except for tone. Do you keep them separate or merge them into one with a tone variable?" (A strong answer reasons about it as a template-design trade-off: a shared template with a tone variable if the structure is truly identical; separate templates if they'll likely diverge in structure over time.)

3 When would you chain multiple prompts together instead of using one larger prompt?
Strong answer

When a task has genuinely distinct sub-problems that benefit from being handled and tested separately — e.g. classify, then extract structured data, then draft a reply, following the worked example from this session. A strong candidate explicitly names the trade-off: chaining adds latency (multiple API calls) and complexity (managing handoffs between steps), in exchange for each step being simpler, more testable in isolation, and easier to debug independently.

Red flags

Treating chaining as strictly "more advanced, therefore always better," or being unable to name the latency/complexity cost at all.

Follow-up

"The final output of a 3-step chain is wrong. How do you find out which step caused it?" (Strong answer: log or inspect each intermediate step's output independently to isolate exactly where the failure happened, rather than re-prompting the whole chain and guessing.)

4 What's a lightweight way to test a prompt template without requiring an exact-match output check?
Strong answer

Since LLM output naturally varies, exact-match testing is unrealistic. Instead, check for specific, verifiable characteristics the output should have — does it contain the customer's name, does it stay under a specified length, does it avoid mentioning a competitor. A strong answer connects this to catching a meaningful fraction of regressions before production, and notes it's a lightweight preview of the fuller evaluation discipline Week 5 formalizes.

Red flags

Claiming LLM output "can't really be tested," or proposing an exact-string-match test as the primary check.

Follow-up

"Give me a check that would catch a real regression, not just a trivial one." (e.g. a check that a required disclosure sentence is present, or that the output doesn't exceed a hard length limit a downstream system depends on.)

5 A team has 15 different prompts scattered across files with no naming convention and no documentation of what variables each expects. What problems will this cause as the team grows?
Strong answer

Duplicate or near-duplicate prompts get written because nobody can find the existing one; nobody knows a given prompt's expected inputs without reading through the calling code; there's no way to tell what changed if a prompt's behavior shifts; and onboarding a new team member becomes much slower since there's no organized place to learn what prompts the system actually uses. A strong candidate frames this as the same problem undocumented, unorganized code causes generally — prompts just haven't been treated with the same discipline yet on most teams.

Red flags

Only naming one problem (e.g. just "it's messy") without the concrete, specific consequences — duplication, undocumented inputs, no change history, slow onboarding.

Follow-up

"If you joined this team today, what's the first thing you'd do about it?" (A pragmatic answer: don't rewrite everything at once — start by cataloging what exists, then apply naming/documentation conventions going forward and migrate the highest-traffic prompts first.)

Strategy Tips

  • Cover the "Strong answer" line, answer out loud, then check yourself against it — that's how these are meant to be used for self-testing.
  • Interviewers are listening for concrete consequences and trade-off reasoning, not textbook recall — always be ready to name what specifically breaks without structure, not just that "it's messy."
