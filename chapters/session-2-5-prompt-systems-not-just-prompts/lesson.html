Prompt Systems, Not Just Prompts

Every technique so far lived in one prompt at a time. This chapter is about what changes the moment you have several prompts, more than one person touching them, and months instead of minutes for them to survive.

On this page 1. A Prompt vs. A Prompt System 2. Prompt Templates and Variables 3. Organizing a Prompt Library 4. Chaining Prompts Together
Every prompt you've built so far in this program has lived in one place at a time — a script, an exercise, a single use case. That's exactly right for learning the techniques. But the moment you're building something real — a product with several AI-powered features, a team with more than one person touching prompts, a feature that needs to evolve over months — a collection of one-off prompts scattered across files stops being a minor inconvenience and starts being a genuine liability. This chapter is about making that transition deliberately: from individual prompts to a prompt system — reusable templates, named variables, and some structure around how prompts are stored, versioned, and tested. It's also a direct preview of Week 6's CI/CD-for-prompts content; the habits you build today are the foundation later, more formal tooling builds on.
Sub-topic 1 of 4

1. A Prompt vs. A Prompt System

A single good prompt solves one specific case, written for one specific moment. A prompt system is something different in kind, not just in scale.

What is... a prompt system? A prompt system involves reusable templates with variables (the same structure, filled in differently each time), some notion of versioning (so you can tell what changed and roll back if a change makes things worse), consistent testing across a representative range of inputs (not just the one example you happened to try first), and often chaining multiple prompts together into a multi-step pipeline.

Here's why the distinction has real consequences. Imagine two engineers building the same feature — a customer support reply generator. Engineer A writes a great prompt, hardcodes it directly into the function that calls the API, and ships it. Engineer B writes the same quality prompt, but stores it as a template with named variables ({customer_name}, {issue_description}, {tone}), in a separate file from the application logic, with a version number and a few test cases attached.

six-months-later.txt 
Engineer A's approach (hardcoded prompt in app logic):
  - New tone option requested   -> dig through application code to find the string
  - PM wants to see the live prompt -> has to be walked through the codebase
  - Bug report comes in          -> no history of what the prompt used to say

Engineer B's approach (template + version + tests):
  - New tone option requested   -> open one well-organized file, add a variable
  - PM wants to see the live prompt -> hand them the file directly
  - Bug report comes in          -> check the version history for what changed
Same starting quality, wildly different outcome
  • Both engineers started with an equally good prompt — the six-month gap comes entirely from structure, not from writing skill.
  • This is the same lesson as software engineering generally: the code that's easy to change six months later usually looked slightly more "boring" and organized on day one.
Quick recap
  • A prompt system differs from a single prompt in kind, not just scale: templates with variables, versioning, consistent testing, and often chaining.
  • Two engineers can write equally good prompts and end up with wildly different maintainability, purely based on whether the prompt was treated as a hardcoded string or a managed artifact.

2. Prompt Templates and Variables

What is... a prompt template? A prompt template is a prompt with placeholders for the parts that change between uses, written once and reused with different values substituted in. You've actually already been doing a simplified version of this in earlier exercises — using Python's .format() or f-strings to substitute values into a prompt string. A prompt system formalizes this practice deliberately, rather than leaving it as an incidental implementation detail.
not_a_template.py 
# Hardcoded, one-off -- has to be re-written by hand for every customer:
prompt = ("Write a polite follow-up email to Sarah Chen about her unpaid "
          "invoice from March 15th, mentioning a 5% late fee.")
a_template.py 
FOLLOW_UP_TEMPLATE = """Write a polite follow-up email to {customer_name} about
their unpaid invoice from {invoice_date}, mentioning a {late_fee_pct}% late fee."""

prompt = FOLLOW_UP_TEMPLATE.format(
    customer_name="Sarah Chen",
    invoice_date="March 15th",
    late_fee_pct=5,
)

The template version separates the reusable structure from the specific data, meaning the exact same well-tested prompt structure gets used for every customer, every invoice — rather than someone re-writing a slightly different version of this prompt by hand each time, with all the inconsistency and untested-edge-case risk that implies.

Try it yourself: change the variables below and re-run to see the same template produce a different, consistently-shaped prompt every time.

template_demo.py
Click "Run Code" — then edit a customer's values and re-run.
Why this matters for quality, not just convenience A template that's been tested against a representative range of inputs (different customer name formats, different fee percentages, different date formats) is far more reliable than re-deriving a similar prompt from scratch each time you need it. This connects directly to Session 2.4's lesson about testing structured-output prompts against a range of inputs, not just convenient examples — a template gives you one well-tested artifact to maintain, instead of many slightly-different, individually-untested variants scattered throughout a codebase.
Quick recap
  • A template separates reusable structure from specific data using named placeholders.
  • You've already been doing a lightweight version of this with .format()/f-strings — a prompt system just makes it deliberate and reused.
  • One well-tested template beats many untested, slightly-different one-off variants.

3. Organizing a Prompt Library

A meaningful practice, even for a solo developer: don't bury prompt strings directly inside the application logic that calls the API. Keep them in a dedicated location — a separate module, a folder of template files — so anyone (including future you) can find and review every prompt the application uses without having to read through unrelated business logic.

Naming and documentation conventions Each template benefits from a clear name describing its purpose, and a short comment or docstring describing exactly what variables it expects and what each one means. This sounds like a small thing, but it's the difference between a six-month-old prompt library being genuinely usable versus being an archaeology project every time someone needs to touch it.
prompts/customer_communications.py 
FOLLOW_UP_TEMPLATE = """..."""  # expects: customer_name, invoice_date, late_fee_pct

REFUND_APOLOGY_TEMPLATE = """..."""  # expects: customer_name, product_name, refund_amount

# prompts/data_extraction.py

RESUME_PARSER_TEMPLATE = """..."""  # expects: resume_text

This is genuinely simple — there's no special framework required to get real value from this practice. The discipline of separating, naming, and documenting templates is what creates the value, not any particular tool.

A note on testing Even a lightweight test — a small set of representative example inputs with expected characteristics in the output (not necessarily an exact string match, since LLM output naturally varies, but checks like "does it include the customer's name," "is it under the specified length," "does it avoid mentioning competitors") — catches a meaningful fraction of regressions before they reach production. This is a preview of what Week 5 formalizes into a complete evaluation discipline; for now, the habit of having any repeatable check beyond "I tried it once and it looked fine" is the valuable starting point.

The exercise for this session has you build exactly this: a small library of templates, each documented, each with at least one lightweight, non-exact-match test. Before you open the starter file, it's worth writing the prompt you'd hand an AI assistant to help you scaffold that structure — the design decisions (what counts as a good check, what "documented" means) are the part that actually matters.

Thought process: the real skill here isn't asking an assistant to "write some prompt templates" — it's specifying the contract each template must satisfy: a docstring naming every variable, and at least one check function that verifies a property of the formatted output rather than an exact string. A vague request gets you templates with no documentation and tests that only work with the one example you gave it.

Paste your prompt into Claude, ChatGPT, Copilot, or whatever assistant you use, and compare what it builds against this session's exercise — does every template get a documented variable list, and does every test check a verifiable property instead of an exact string? That comparison is the real test, not a score.
Show a strong version of this prompt 
Write a Python module for a customer-communications prompt library with 5 template strings as module-level constants, each using {variable_name} placeholders. Above each template, add a one-line comment listing every variable it expects and its type. Then write a TEST_CASES list where each entry pairs one template with sample variable values and a list of small check functions -- each check function takes the FORMATTED prompt string and returns True/False for one verifiable property (e.g. "contains the customer's name", "contains a specific dollar amount"), not an exact-match comparison. Finish with a run_tests() function that formats each template, runs its checks, and prints a pass/fail count. No API calls -- this only needs to test template structure.
Quick recap
  • Keep prompts in a dedicated location, separate from application logic — even as a solo developer.
  • Every template needs a clear name and a documented list of the variables it expects.
  • Lightweight, characteristic-based tests (not exact-match) catch a real fraction of regressions before production.

4. Chaining Prompts Together

What is... prompt chaining? Sometimes a task is genuinely better solved as a sequence of separate prompts, each handling one well-defined sub-task, with the output of one feeding into the input of the next — rather than one enormous prompt trying to do everything at once.

Consider building a tool that processes an incoming customer email: it needs to (1) classify the email's category, (2) extract any specific order numbers or dates mentioned, and (3) draft an appropriate reply. You could attempt all three in one giant prompt, or you could chain three focused prompts:

three_step_chain.txt 
Step 1: Classify the email (few-shot, from 2.2)                 -> category
Step 2: Extract structured data (from 2.4)                       -> order numbers, dates as JSON
Step 3: Draft a reply, with category + extracted data as context -> final reply text

Each step is simpler, more testable in isolation, and easier to debug than one combined mega-prompt — if the final reply is wrong, you can check each step's output independently to find exactly where things went wrong, rather than trying to diagnose a failure buried inside one large, opaque request.

The honest trade-off
  • Chaining adds latency — multiple API calls instead of one.
  • Chaining adds complexity — more code to manage the handoffs between steps.
  • It's the right choice when a task genuinely has distinct sub-problems that benefit from focused, separately-testable prompts — not a default to apply to every task regardless of whether it actually has that structure.
  • A simple task that doesn't need decomposition shouldn't be artificially split into a chain just because chaining is available as a technique.
Go Deeper: how do you decide where to draw the chain's boundaries?

A useful test: could you describe each step's job in one sentence without using the word "and"? "Classify the email" is one job. "Classify the email and pull out the dates and draft a reply" is three jobs wearing one prompt's clothing. If you find yourself writing a prompt with several unrelated instructions stacked on top of each other, that's usually the signal that it wants to be a chain — especially if you'd want to know, when something goes wrong, which of those instructions the model failed to follow.

Quick recap
  • Chaining breaks one task into a sequence of focused prompts, each feeding its output to the next.
  • Benefit: each step is independently testable and debuggable.
  • Cost: more latency and more code to manage — use it when the task has genuinely distinct sub-problems, not as a default.
In the Real World
  • Teams that ship several AI features almost always converge on some version of a prompt library, whether or not they call it that — the alternative (strings scattered through the codebase) becomes unmanageable well before six months pass.
  • "Prompt versioning" is a direct preview of Week 6's CI/CD-for-prompts content: once prompts are treated as artifacts with history, you can diff, review, and roll them back exactly like code.
  • Chaining is the same instinct that shows up in good software design generally — single-responsibility functions are easier to test and debug than one function doing five things, and prompts are no different.

Points to Remember

  • A prompt system differs from a single prompt in kind, not just scale: reusable templates with variables, versioning, consistent testing, and often chaining multiple prompts together.
  • Templates separate reusable structure from specific data, meaning one well-tested prompt structure serves every use case rather than many untested, slightly-different one-off variants.
  • Separate prompts from application code, with clear naming and documentation of expected variables — this is what makes a prompt library maintainable six months later, not any particular framework.
  • Even lightweight testing (checking for specific characteristics in output, not exact string matches) catches a meaningful fraction of regressions before production, previewing Week 5's evaluation discipline.
  • Chaining prompts is for tasks with genuinely distinct sub-problems — it adds latency and complexity, so it's a deliberate choice, not a default.
