Session 2.6 Exercises 45–60 min, hands-on

Exercises: Build the Customer-Support Reply Generator

Integrate everything from Week 2 into one working system: the four pillars of a great prompt (2.1), few-shot tone examples and role framing (2.2), internal chain-of-thought reasoning kept out of the visible output (2.3), schema-constrained JSON with defensive parsing (2.4), and a documented, reusable prompt template (2.5). The scaffold marks every place that integrates this week's concepts with numbered TODO markers.

How to run these You'll need Python 3 installed (check with python3 --version). Download starter.py below (it's a one-line pointer — the real work happens in the file it imports from) or, better, work directly in a copy of the full scaffold. Run python3 support_reply_generator.py to test your implementation against three sample tickets, using a built-in stub that returns deliberately messy responses so your parsing and validation logic has something realistic to defend against — no API key required. To test against a real model, set USE_REAL_LLM=1 and complete the optional TODO for a live API call.
starter.py solution.py (reference)

The tasks

1 Write the few-shot tone examples

Find TONE_EXAMPLES and its TODO(1). Write one short example reply per tone (empathetic, professional, concise) for a sample ticket. These anchor the style the model should match — not content it should copy verbatim into every reply.

2 Write the internal-reasoning instructions

Find REASONING_INSTRUCTIONS and its TODO(2). Ask the model to privately think through what the customer actually needs, whether the ticket gives enough information to resolve it without guessing, and whether it involves money, data loss, or a repeated complaint that should push toward escalation — explicitly instructing it to keep that reasoning out of the final JSON.

3 Build and validate the prompt

Find build_prompt() and its TODO(3). Validate that tone is one of VALID_TONES, raising a clear ValueError immediately if it isn't — a cheap guard that catches a bug before it ever reaches the model — then fill in the template's variables.

4 Implement defensive parsing

Find parse_reply() and its TODO(5). Strip any wrapper text or markdown code fences around the JSON, parse it, and validate every field: all five keys present, tone_applied in VALID_TONES, confidence in VALID_CONFIDENCE, escalate is a real boolean, and reply_body is a non-empty string. Raise a ValueError describing exactly what's wrong on any failure — that specificity is what makes debugging a bad prompt change fast.

5 Wire up the safe fallback

Find generate_reply() and its TODO(6). If parse_reply() raises, return a fallback SupportReply instead of crashing: escalate=True, an escalation_reason that includes the original error for debugging, confidence="low", and a short, generic holding message as reply_body.

🐞 Task 6 — Debug the Code

This escalation-consistency checker is supposed to catch an escalate: true reply that's missing its escalation_reason, but a reply with both fields present still gets rejected. Find the bug.

buggy_check.py 
def check_escalation_consistency(parsed):
    if parsed["escalate"] or not parsed["escalation_reason"]:
        raise ValueError("escalate=True requires a non-empty escalation_reason")

reply = {
    "escalate": False,
    "escalation_reason": None,
}
check_escalation_consistency(reply)   # raises, but this reply is perfectly valid

Hint: the condition uses or, which fires whenever either half is true — including a perfectly fine reply where escalate is False and escalation_reason is correctly None. You only want to raise when escalate is True and the reason is missing.

Checking your work There's no automated grader — that's intentional. Run python3 support_reply_generator.py and confirm all three sample tickets produce valid, schema-matching JSON; that passing an invalid tone raises a clear error immediately in build_prompt(); and that feeding parse_reply() a broken response (try editing the stub to drop a field, or return plain text) raises a ValueError that tells you exactly what's wrong — and that generate_reply() still returns a valid, escalate: True reply rather than crashing when that happens. Compare your implementation against solution.py once you've made a genuine attempt — try to get through the defensive-parsing task on your own first, since it's the part most worth struggling with.
Pro path: extend it Once the core build passes, try logging every generated reply (ticket, tone applied, confidence, escalation decision) to a simple structured log, then write a small script that reports the escalation rate and tone distribution across a batch of tickets — a first, lightweight taste of the monitoring and observability work Week 6 formalizes.
