Sub-topic 1 of 5

1. The build: a support reply generator with tone control

Picture a small software company: twelve hundred support tickets a week, four support agents, and a backlog that never quite gets to zero. Most tickets are routine — a password reset, a billing question, a "how do I export my data" — but each one still needs a reply that's accurate, on-brand, and doesn't read like it was copy-pasted from a template that ignores what the customer actually asked.

The company doesn't want to fully automate support away. They want a tool that drafts a strong first-pass reply for every incoming ticket, in a tone that fits the situation, which a human agent can review, lightly edit, and send — instead of writing every reply from a blank page. That's the artifact you're building today: a customer-support reply generator with tone control.

What is... a synthesis build? A synthesis build is a small project whose whole purpose is to make you use several separate ideas together, in one working system, rather than one idea in isolation. It would be easy to write a single, reasonably good prompt for this task and call it done — and that's exactly the trap. A single ad-hoc prompt might handle one ticket well and quietly fail on the next one, with no way to tell which is which until a customer complains.
Quick recap
  • The tool drafts a first-pass support reply in one of three tones, for a human agent to review and send.
  • The goal isn't full automation — it's a strong, trustworthy first draft.
  • One ad-hoc prompt is a trap: it can look fine in testing and fail unpredictably in production.
Sub-topic 2 of 5

2. Why this build needs every technique from the week

This project was chosen specifically because building it well requires touching almost everything from this week. Look at what the real requirements actually demand, and each earlier session shows up as a concrete design decision:

Session 2.1 — anatomy of a great prompt
None of the rest matters if the prompt itself is vague about what "good" looks like. Clarity, context, constraints, and format specification are the floor everything else is built on.
Session 2.2 — few-shot and role prompting
An angry billing dispute and a casual feature question shouldn't get the same voice. Tone control only becomes concrete once it's backed by example replies, not adjectives like "be empathetic."
Session 2.3 — chain-of-thought
The model needs to reason about severity before it writes: should this ticket be escalated to a human immediately, or is a standard reply fine? That's a judgment worth thinking through step by step.
Session 2.4 — structured outputs
The output needs to be machine-checkable, not just a paragraph of text — a real support tool needs to log the tone used, flag escalations, and route tickets. That means a schema, and defensive parsing that never assumes the model complied.
Session 2.5 — prompt systems
The prompt itself needs to be a maintainable, documented template — not a string improvised fresh for this exercise — because in six months someone will need to add a fourth tone option without reading through application code to find where the prompt lives.
The real lesson of a lab day Production prompting work is rarely "pick the one right technique." It's combining several techniques, each solving a different sub-problem, into one coherent system. Few-shot alone doesn't get you machine-checkable output. A perfect schema alone doesn't get you consistent tone. Today's build only works if all five sessions show up at once.
Quick recap
  • 2.1 sets the floor (clarity/context/constraints/format); 2.2 anchors tone with examples; 2.3 drives the escalation judgment; 2.4 makes the output machine-checkable; 2.5 makes the prompt maintainable.
  • A real prompting problem usually needs several techniques combined, each solving a distinct sub-problem — not one technique picked in isolation.

3. The build, step by step

A natural instinct is to start by writing the prompt and see what comes back. For this build, it's better to start at the other end.

Step 1 — design the output contract first Decide exactly what a finished reply needs to contain, as a schema, before writing a single word of the prompt. This mirrors the discipline from Session 2.4: the schema is the actual deliverable; the prompt is just the mechanism that produces it.
reply-schema.json 
{
  "reply_body": "string",
  "tone_applied": "empathetic | professional | concise",
  "confidence": "high | medium | low",
  "escalate": true | false,
  "escalation_reason": "string or null"
}

Notice what this schema does beyond just holding the reply text. confidence lets a human reviewer triage their workload — a "low confidence" reply gets a closer read before sending. escalate and escalation_reason mean the model isn't just drafting replies blindly; it's making (and explaining) a judgment call about whether this ticket actually needs a human, which is a chain-of-thought decision baked directly into the contract.

Step 2 — define the three tones with examples, not adjectives "Tone control" is a vague phrase until you pin it down with examples. Telling a model "be empathetic" is far weaker than showing it one short example of what empathetic actually sounds like in this context — exactly the lesson from few-shot prompting (2.2).
  • Empathetic — for frustrated, upset, or anxious customers. Leads with acknowledgment before any explanation or solution.
  • Professional — the default for routine, neutral requests. Clear, polite, efficient, no unnecessary warmth or formality.
  • Concise — for customers who clearly want a fast, no-fluff answer. Shortest replies of the three, with no preamble.

Per Session 2.5's convention, this prompt doesn't live as a one-off string improvised inline — it's built as a named, documented template with placeholders, stored separately from the calling code:

support_reply_v1.py 
PROMPT_TEMPLATE = """You are a customer support reply assistant for a software company.
You write clear, accurate replies. You never invent policy details, refund
amounts, or timelines that are not stated in the ticket.

Subject: {ticket_subject}
Body: {ticket_body}

Write a reply in a {tone} tone.

{tone_examples}

{reasoning_instructions}

Return ONLY a JSON object matching exactly this schema:
{schema}
"""

{tone_examples} carries the few-shot anchors (2.2). The {reasoning_instructions} block is where chain-of-thought (2.3) enters — asking the model to privately think through what the customer actually wants, whether the ticket gives it enough information, and whether the issue involves money, data loss, or a repeated complaint that should push toward escalation, while explicitly excluding that reasoning from the final output. A subtlety worth naming: a customer should never see "Let me think about whether this needs escalation..." in their actual reply. Instructing the model to reason "internally" keeps the benefit of chain-of-thought (a more careful decision) without its cost (a confusing, unprofessional-looking reply).

Step 3 — defensive parsing, again Session 2.4 introduced defensive parsing: never trust that the model's JSON is well-formed, never trust that an enum field actually contains one of the allowed values, always validate before your application logic touches the data. It's tempting to think of that as "the 2.4 lesson," already checked off. It isn't. Every session from here forward that touches model output needs this same discipline, because the underlying risk — a model that's usually well-behaved but not guaranteed to be — never goes away. parse_reply() needs to handle, at minimum: JSON that fails to parse at all (the model added a sentence of preamble before the {), a tone_applied value that isn't one of the three defined tones, and an escalate: true response with a missing or empty escalation_reason — a logically inconsistent output the schema doesn't prevent on its own, but your validation code should catch.

Thought process: the entire quality of this build lives in the prompt template's specificity and the validation logic's thoroughness, not in the plumbing around them. So the real "thought process" is deciding, up front: what exactly must be true of a reply before it's safe to hand to an agent? Every answer to that question becomes one more check in parse_reply() — and every gap in tone differentiation becomes one more few-shot example.

Quick recap
  • Design the schema first — it's the deliverable; the prompt is the mechanism.
  • Tone is concrete only with examples; chain-of-thought reasoning about escalation should stay hidden from the customer-facing text.
  • Defensive parsing checks content, not just syntax — valid JSON can still be a logically inconsistent or unsafe reply.

4. "Done well" vs. "done technically"

It's possible to build something that runs without errors and still misses the point of the exercise. Here's the difference, concretely.

Done technically (passes, but misses the point) A single prompt with one line — "respond in whatever tone seems appropriate" — instead of explicit tone options and examples. It returns valid JSON. It doesn't crash. But because "appropriate" is left for the model to interpret case by case, tone drifts across similar tickets: sometimes warm, sometimes flat, sometimes overly casual, even though nothing about the actual instruction changed. Or: parse_reply() does nothing but json.loads() wrapped in a try/except — it "handles errors," but a syntactically valid reply with an invalid tone or an unexplained escalation still sails straight through to a customer.
Done well (the actual goal) Each tone is backed by a concrete example the model can match the style of, not just an adjective. The reasoning instructions explicitly steer the escalation decision toward money, data loss, and repeated complaints. And validation checks content, not just syntax: every field is present, tone_applied is one of exactly three values, and an escalate: true reply is required to carry a real escalation_reason — because a system that always generates a confident-sounding reply, even when it doesn't actually have enough information, will eventually generate replies that are wrong or unhelpful, and a confident tone makes people trust them more than they should.

That distinction — recognizing that a successfully-parsed JSON object is not the same thing as a safe one — is the whole reason Session 2.4's lesson doesn't retire once you've passed its quiz. The stakes of defensive parsing scale with how close a tool is to something real: in an isolated exercise, a malformed response is an inconvenience you notice immediately while testing. In a tool meant to run continuously over a live ticket queue, an unhandled malformed response is the difference between "the system flags one ticket for manual review" and "the system silently sends a customer a JSON parsing error instead of a reply."

Go Deeper: why versioned templates matter here, not just as a style rule

Naming this template support_reply_v1 rather than leaving it as an anonymous string isn't a cosmetic choice. If the support team's ticketing integration is built against v1's exact schema and tone behavior, you want to be able to ship an improved v2 deliberately — deciding when the change rolls out and who reviews it — rather than editing the prompt in place and silently changing behavior for anyone already depending on the current version. That's the practical payoff of Session 2.5's discipline, and it's exactly the kind of thing that only bites you once a prompt is actually load-bearing.

Quick recap
  • "Runs without errors" and "demonstrates real understanding" are different bars — especially for validation.
  • Inconsistent tone across similar tickets is usually a missing-examples problem, not a code problem.
  • A schema-valid reply can still be unsafe; content checks (not just syntax checks) are what catch that.

5. Reflection: what clicked, what's fuzzy

Before moving into Week 3, take five honest minutes (genuinely worth doing, not a platitude) to answer these for yourself:

  • Could you explain, without looking back, why "be empathetic" is a weaker instruction than one concrete empathetic example? If shaky, revisit Session 2.2.
  • Could you sketch, from memory, why a model might be told to reason step by step but hide that reasoning from the final output? If not, Session 2.3 is worth a second pass.
  • Did building today's tool surprise you anywhere — a place where you thought "surely json.loads() succeeding is enough" until you had to think through what content-level checks were still missing? That surprise is valuable information.

This isn't busywork. The single best predictor of struggling in Week 3 (and beyond, once retrieval and multi-step agents enter the picture) is carrying forward an unexamined gap from Week 2, because every later week assumes you can reliably get structured, trustworthy output out of a model — not just a fluent one.

Quick recap
  • Honest self-assessment now is cheaper than discovering a gap later.
  • Shaky on tone consistency → Session 2.2. Shaky on hidden reasoning → Session 2.3. Shaky on validation → Session 2.4.
  • The surprises during the build are the most useful signal you have.
In the Real World
  • Nearly every production support-copilot in 2026 combines these same five ingredients: tone-anchored examples, hidden reasoning for triage decisions, a strict output schema, defensive validation, and versioned prompt templates — there is no shortcut version that skips one and still ships reliably.
  • "It parsed as JSON" is a surprisingly common false sense of security in real incident post-mortems — teams that only wrap json.loads() in a try/except, without content-level validation, are the ones who get paged when a model returns a technically-valid-but-nonsensical response.
  • The escalate/escalation_reason pattern — letting a system say "I don't have enough information" instead of always sounding confident — is the same design principle Week 5 formalizes as evaluation and guardrails; it shows up here already as a basic requirement, not an advanced add-on.

Points to Remember

  • A lab day isn't about learning something new — it's about discovering that the week's separate techniques were never actually separate. A real prompting problem usually needs several combined, each solving a distinct sub-problem.
  • Design the output contract (schema) before writing the prompt. The schema is the actual deliverable; the prompt is the mechanism that produces it.
  • Tone control is concrete only when backed by few-shot examples, not adjectives alone — and chain-of-thought reasoning about sensitive decisions like escalation should often stay invisible to the end user.
  • Defensive parsing is not a one-time 2.4 lesson. Every exercise that touches model output needs it, and the stakes increase as a tool moves from a single test run toward something running continuously on real data.
  • Prompts belong in named, versioned templates from the first version of a tool — not retrofitted later once it's "important enough."
