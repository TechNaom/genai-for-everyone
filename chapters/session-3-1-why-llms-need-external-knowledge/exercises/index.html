Session 3.1 Exercises 15 min, hands-on

Exercises: The "RAG or Not?" Decision Worksheet

Build the habit of running any "we need retrieval for this" request through a real framework before writing a single line of retrieval infrastructure — the single most valuable instinct from this session. This is a pure reasoning-and-classification exercise: no API calls, no paid keys, just plain Python that runs anywhere.

How to run these You'll need Python 3 installed (check with python3 --version). Download starter.py below, then run it from a terminal with python3 starter.py. It prints your answers in a readable format and flags any scenario you haven't filled in yet.
starter.py solution.py (reference)

The task

Open starter.py. For each of the six scenarios in the SCENARIOS list, fill in three fields. Run every scenario through the same three questions from the lesson: is the needed information outside the model's training data, does the answer need to be traceable to a real source, and does the underlying information change over time? If the honest answer to all three is "no," look for a reasoning/writing task, a timeless-knowledge task, or a prompting problem in disguise instead.

1 Make the decision

For every scenario, set decision to "RAG", "Not RAG", or "Something else" (be specific about what "something else" actually is — a tool call, a database lookup, a prompting fix).

2 Justify it with the framework

Set reasoning to 2–4 sentences that explicitly reference at least one of the three RAG criteria (training-data gap, source traceability, time-sensitivity) or one of the three non-RAG signals (reasoning task, timeless knowledge, prompting problem). A gut-feel answer without the framework doesn't count.

3 Name the real fix

If your decision is anything other than "RAG", set actual_fix to the real fix — "better prompting," "the model already knows this reliably," "this needs a tool call to a calculator/API, not retrieval," or "this needs a database lookup, not semantic search." Leave it as None when the decision is "RAG".

🐞 Task 4 — Debug the Code (Pro path)

For scenario 4 (the HR chatbot), go one level deeper: even once you've correctly identified that this needs some form of retrieval, is semantic/vector-based RAG — the kind you'll build in 3.2–3.4 — actually the right mechanism, or does "how many sick days do I have left" call for a direct, structured database lookup instead, with the model only used to phrase the final answer? Write 3–4 sentences on the distinction.

scenario_4.py 
{
    "id": 4,
    "scenario": "How many paid sick days do I have left this year?",
    "decision": "RAG",              # correct so far, but which KIND of retrieval?

Checking your work There's no automated grader — that's intentional. A couple of the six scenarios are genuinely debatable at the edges. The goal isn't perfect agreement with solution.py; it's being able to defend your classification with the training-data-gap / traceability / time-sensitivity framing. Compare your reasoning against solution.py (run it with python3 solution.py) once you've made a genuine attempt.
