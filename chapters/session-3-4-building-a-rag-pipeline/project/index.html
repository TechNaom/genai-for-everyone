Session 3.4 Project Pro path 20–30 min build

Verifying an Honest "I Don't Know"

The Pro path extended challenge for this session. The exercises built a complete retrieve → augment → generate → cite pipeline. This project pushes that pipeline on the exact question the lesson raises: not "does retrieval find a weak match," but "when a fact is genuinely absent from the entire document set, does the system say so honestly, or does it produce a fluent, confident-sounding guess anyway?" You'll also practice a habit that matters more than any single test passing — being explicit about which parts of your result you verified by running the code yourself, versus which parts you're only trusting the model got right on one particular run.

   reimbursement or continuing education benefits. The context discusses

That's the target behavior: the retrieved chunks are real and on-topic — they're genuinely about benefits — but the model correctly recognizes that none of them address tuition reimbursement, and says so instead of inventing a dollar figure that sounds plausible for a corporate benefits page.

No key yet? The offline_test() fallback is_grounded_refusal() is pure string logic with no API dependency — a substring check against a list of refusal phrases — and the starter file includes offline_test(), which validates it against fake answer text (an honest refusal, a fabricated-but-confident answer, and a normal grounded answer) with no network access required at all. Get that function right first; it's the part of this project that's actually new, and running python3 starter.py always runs offline_test() first regardless of whether a key is set.

The task

Open starter.py. It reproduces the completed pipeline from the exercises (chunking, embedding, VectorStore, format_context(), build_rag_prompt(), extract_citations(), answer_question()) so this file is self-contained, then adds two new pieces to build today.

1 is_grounded_refusal() — detecting an honest "I don't know"

Given the model's raw answer text, return True if it honestly indicates the context doesn't contain enough information to answer, and False otherwise. Lowercase the text and check whether any phrase in REFUSAL_PHRASES appears as a substring. This function only detects refusal language — it can't tell you whether a non-refusal answer is actually true, which is exactly why the project still asks you to read the printed answers yourself.

2 run_verification_challenge() — tie it together

For each question in UNANSWERABLE_QUESTIONS, run it through answer_question() against sample_handbook.pdf, check whether is_grounded_refusal(result["answer"]) is True, and print a clear PASS/FAIL verdict alongside the model's actual answer text so you can double-check the automatic classification isn't fooling itself.

Why tuition reimbursement and bereavement leave UNANSWERABLE_QUESTIONS asks about tuition reimbursement/continuing education and bereavement leave. Neither is a weak retrieval match — they're facts that simply never appear anywhere in sample_handbook.pdf (the same six-section handbook from the exercises: PTO, sick leave, remote work, expense reimbursement, health/retirement benefits, parental leave — none of it tuition, education, degree programs, or bereavement). No amount of retrieval tuning could surface a chunk that legitimately supports an answer to either question, which is what makes this a clean test of the grounding instruction rather than of retrieval quality.
Checking your work — verified vs. assumed offline_test() passing with no assertion errors is the first checkpoint, and doesn't need a key. With a key: run run_verification_challenge() and read both printed answers yourself, not just the PASS/FAIL line — is_grounded_refusal() is a keyword check, not a fact-checker. Then write, in your own words, a short verified-vs-assumed split of your own result: which parts did you confirm by actually running the code (retrieval results, the fact-absence check against the PDF text, the offline logic tests), and which part are you only trusting because the model happened to behave correctly on this one run (the exact live wording it generated)? That separation is the real skill this project is built to train — see solution.py's VERIFICATION_NOTES for a worked example of exactly this split.

Why this project matters

A grounding instruction that only gets tested on questions the document set can answer never proves anything — a model that ignores the instruction entirely can still look correct on those. The real test is a fact you know for certain isn't there, checked by actually reading the source text yourself first. And in production RAG systems, "the tests passed" often means "the tests happened to match this run's output," not "the system is reliably grounded" — keeping verified claims and assumed claims in separate buckets, out loud, is exactly the discipline that catches the gap between those two before a user does.
