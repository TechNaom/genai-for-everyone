Session 3.5 Exercises 30 min, diagnostic

Exercises: Debug a Broken RAG Pipeline

This exercise is diagnosis, not coding. You're handed a working-but-broken RAG pipeline with three bugs planted on purpose — one per failure mode from today's lesson: a chunking error, a retrieval miss, and context stuffing. Your job is to run it, inspect the chunks it actually retrieves, and correctly name what went wrong — the same discipline the lesson walked through in its worked example.

🐞 Do not fix broken_pipeline.py

It's broken on purpose, and it's meant to stay that way. Fixing the bugs would skip the actual skill this exercise trains: reading a pipeline's real output and correctly identifying which failure mode you're looking at from the evidence alone, before you ever touch the configuration. Your written work goes in starter.py, a completely separate file.

How to run these You'll need Python 3, plus pdfplumber and numpy: pip install pdfplumber numpy --break-system-packages. No API key and no internet access needed — everything runs against the included sample_handbook.pdf, reusing the same offline chunking/embedding/retrieval code from Sessions 3.3–3.4.
broken_pipeline.py (given, read-only) starter.py solution.py (reference)

The task

Run python broken_pipeline.py first. It prints three cases — a pipeline configuration, a real question, and the top-k chunks that configuration actually retrieved, each with its similarity score. Read that output closely before opening starter.py.

1 Diagnose Case 1

Question: "How many sick days do employees get and do they roll over?" — run at chunk_size=15, overlap=0. Look at the top-3 chunks: does the complete fact about sick-day carryover appear intact in any single chunk, or does it look like it got cut across a boundary?

2 Diagnose Case 2

Question: "Can I telecommute instead of going to the office?" — run at a normal chunk configuration. Does the handbook's actual remote-work section show up anywhere in the top-3 at all? If not, that's a different failure mode than Case 1, even though the visible symptom (a wrong-sounding pipeline) looks similar from the outside.

3 Diagnose Case 3

Question: "How many PTO days do employees get per year?" — run at k=10 against an 11-chunk document. Look at how the similarity scores change from rank 1 to rank 10. Is there a point where the scores clearly fall off a cliff into "not actually relevant"?

What to fill in

Open starter.py. For each of the three CASE dictionaries, set:

  • diagnosis — exactly one of "chunking error", "retrieval miss", or "context stuffing".
  • evidence — 2–4 sentences citing something specific and checkable from the actual printed output: an exact similarity score, an exact chunk boundary, a missing word. Not a generic restatement of the failure mode's definition.
  • proposed_fix — 1–3 sentences on what you'd actually change in the pipeline's configuration.
Resist the pattern-match Case 1, Case 2, and Case 3 do not necessarily correspond to failure modes 1, 2, and 3 in that exact order just because the lesson introduced them that way. Read each case's actual evidence independently before committing to a diagnosis — the whole point of this exercise is practicing the inspect-first habit, not memorizing an ordering.

Pro path — extended challenge

  1. Find the exact orphaned word. For Case 1, work out which two consecutive chunks (at chunk_size=15, overlap=0) the sick-leave-carryover sentence got split across, and identify the specific word or phrase missing from both halves.
  2. Propose a re-ranking fix for Case 2. A larger k alone doesn't reliably fix a genuine vocabulary mismatch the way it can help with a narrowly-missed near-match. Explain why in 2–3 sentences, and describe what a re-ranking step would need to actually evaluate to recover from this kind of miss.
  3. Quantify Case 3's dilution. Calculate what fraction of the 10 retrieved chunks score below 0.15 — a reasonable "probably not actually relevant" threshold for this toy embedding — and use that to argue for a more conservative k.

For a sharper follow-up on Case 2 — instead of just confirming the correct chunk is missing from the top-3, digging into exactly which words in the wrongly-retrieved chunks caused them to outrank it — see the project.

Checking your work A fully worked answer key, with reasoning for all three cases plus the Pro path answers, is in solution.py. Do your own diagnosis first — this is a genuinely useful skill to practice under your own steam before comparing notes.
