Session 3.6 Interview Prep 10 min read

Interview Questions: Synthesizing Week 3

These are scenario-based questions that pull together everything from Week 3 — the kind an interviewer uses to check whether you can actually reason about a retrieval system under real conditions, not just define "embedding" and "chunk." RAG interviews increasingly probe for exactly this: can you diagnose a wrong answer, not just describe the architecture that's supposed to prevent one? Each question below includes what a strong answer sounds like, common red flags, and a natural follow-up. Click any question to expand it.

1 Why can real institutional documents that cross-reference each other be harder for retrieval than documents that don't overlap at all?
Strong answer

With a single, self-contained document, every retrieved chunk is at least from "the right place" by definition — the worst case is an imprecise match within that one document. Once you add multiple documents that genuinely discuss overlapping topics (a registration guide that mentions financial aid holds, a housing handbook that mentions enrollment status), a chunk from the wrong document can still score highly, because it touches the right vocabulary in passing without containing the actual answer. That's a new failure mode, not just a harder version of the old one — a single-document system structurally can't retrieve from the wrong source, because there's only one source.

Red flags

Treating "more documents" as simply "more data to search," with no acknowledgment that cross-referencing content actively degrades naive retrieval precision, or being unable to name a concrete mechanism for why a wrong-document chunk would score well.

Follow-up

"How would you design an evaluation set that specifically catches this failure mode, rather than one that just measures average retrieval accuracy?" (e.g. deliberately including question pairs that target topically adjacent documents, and checking the retrieved source, not just whether the answer text looks reasonable.)

2 You fix a chunking bug for one document type by splitting on numbered headers. A new document type uses different formatting entirely. Walk me through how you'd approach it.
Strong answer

Don't assume the old fix transfers — verify it first. Load the new document, print a sample of the actually-extracted text (not the source PDF as viewed by a human, since extraction can lose formatting like blank lines), and look at what pattern reliably marks a new section in that text: numbers, ALL-CAPS headers, a consistent font-size artifact, something else entirely. Only then write a new splitting rule matched to that pattern, and verify it by actually running it against real test questions for that document — not by assuming structural similarity to the last fix. The transferable skill is the diagnostic process (inspect real extracted text, identify a survivable pattern, verify by running), not any specific regex.

Red flags

Assuming the previous fix (or a fix copied from a tutorial) will just work because "it's still a document," or proposing a new regex without first looking at the actual extracted text of the new document type.

Follow-up

"What would you check to confirm the bug is a chunking problem and not something else, like an embedding model that just doesn't handle this document's vocabulary well?"

3 What's the difference between a chunking error and a retrieval miss, and how would you tell which one you're looking at from a wrong answer alone?
Strong answer

A chunking error means the right information never made it into a coherent, well-formed chunk in the first place — it got merged with unrelated content, split mid-sentence, or diluted inside an oversized block, so even perfect retrieval logic can't find a clean answer that doesn't cleanly exist. A retrieval miss means the right chunk exists intact in the vector store, but the similarity search failed to rank it highly enough for this specific query (a vocabulary mismatch, a query phrased very differently from the source text). To tell them apart from a wrong answer alone: manually search the vector store for the expected chunk by its known content. If it doesn't exist as a clean unit at all, that's a chunking error. If it exists but scored low against the query, that's a retrieval miss — two different fixes (re-chunking vs. better embeddings, query rewriting, or hybrid search).

Red flags

Treating "the answer was wrong" as a single undifferentiated failure and reaching for a fix (like "add more chunks" or "use a better model") without first localizing whether the problem is in chunking or in the ranking step.

Follow-up

"You confirm the correct chunk exists intact but the query doesn't retrieve it in the top 5. Name two different things you could try, and how you'd decide between them."

4 How would you design a multi-document RAG system's citations so a wrong-document retrieval is obvious without reading the model's full answer?
Strong answer

Every citation marker should carry a human-readable source label alongside its chunk number — "[1] (Source: Housing Handbook)," not a bare "[1]." That way, a reviewer scanning a batch of answers can catch a mismatch (a housing question citing the Registration Guide) at a glance, purely from the citation line, without needing to read the retrieved chunk's full text to notice something's off. This turns a hard-to-spot silent failure into a fast visual check, and it scales — it's the same amount of reviewer effort whether you're checking one answer or auditing a thousand logged answers for a pattern of wrong-document retrievals.

Red flags

Treating citations as purely a user-trust feature ("so the user can verify it") without recognizing they're equally valuable as an internal debugging and monitoring signal, or proposing a design where the source document isn't visible without opening the underlying chunk.

Follow-up

"How would you use that same labeling to build an automated monitoring check, not just a manual one?" (e.g. flag any answer whose cited source doesn't match an expected document for a known category of question.)

5 You successfully built a RAG system for customer support using product docs. Now you need to extend it to handle medical research papers. What changes would you make, and what could break?
Strong answer

Name the real domain differences first: medical papers are highly technical, structured (abstract/methods/results/conclusion), and jargon-heavy, versus customer-facing product docs with variable structure and accessible language. Then name what's likely to break: the same embedding model may not capture medical terminology well; a chunking strategy tuned for product docs likely ignores the paper's own structural sections; metadata that barely mattered before (citation count, author, publication date) now matters a lot; and the acceptable false-positive rate drops sharply, since a confidently wrong medical citation is far costlier than a confidently wrong product-doc answer. The concrete changes: evaluate the embedding model specifically on medical-domain queries before assuming it transfers, adapt chunking to the paper's own section structure (the exact same principle as this lab's caps-header fix, applied to a new domain), add metadata indexing, tighten citation requirements, and build a domain-specific evaluation set rather than reusing the product-docs one.

Red flags

"Just point the same system at the new documents" with no acknowledgment of domain-specific risk, no mention of re-evaluating on a domain-specific test set, or treating every document domain as interchangeable.

Follow-up

"You evaluate on 100 medical papers and get 30% accuracy. Is that good? What would you do next?" (Strong answers ask what the baseline and the cost of an error are before judging the number, then propose targeted error analysis rather than a blanket re-tune.)

Strategy Tips

  • For diagnostic questions, narrate your investigation out loud in order — "first I'd check whether the chunk exists at all, then whether it scored low" — interviewers are listening for the sequence, not just the eventual right answer.
  • When asked to extend a system to a new domain, always ask (or state you'd ask) what the acceptable error rate is before proposing changes — the right amount of engineering effort depends entirely on how costly a wrong answer is in that domain.
