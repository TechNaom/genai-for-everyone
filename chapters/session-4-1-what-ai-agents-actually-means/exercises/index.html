Session 4.1 Exercises 20 min, hands-on

Exercises: Trace and Break the Agent Loop

Build two small, fully-offline programs that make the chapter's central distinction concrete: a reactive agent loop (plan → act → observe, where the next step depends on what a tool actually returned) versus a rigid workflow (a fixed sequence that assumes a tool result will always look a certain way). No live LLM calls are used here — today's goal is to internalize the loop structure itself before you build a real tool-calling agent in Session 4.2. Both tools (calculator and weather_lookup) are real, fully working Python functions, even though the "planning" decisions in this exercise are ones you write yourself rather than ones a model makes.

How to run these You'll need Python 3 installed (check with python --version). Download starter.py below, then run it from a terminal with python starter.py.
starter.py solution.py (reference)

The task

Open starter.py. The two tools (calculator and weather_lookup) are already complete and working — don't modify them. Two functions have TODOs for you to finish.

1 Complete the plan-act-observe loop

Finish run_agent_loop so it: calls calculator to get the umbrella total cost, calls weather_lookup for the given city, and builds a final_answer string using only values that came from those tool calls — no invented numbers. If weather_lookup returns an "error" key, the answer must say data isn't available; it must not try to read chance_of_rain_pct in that case. That one check — inspecting the observation before deciding what to say — is the actual "agent" part of this function.

2 Complete the rigid workflow

Finish rigid_workflow by writing the one missing line: index weather["chance_of_rain_pct"] directly, with no error handling. This is deliberately fragile — you are not meant to "fix" it. The point is to watch it crash on a city weather_lookup doesn't know about, and compare that to how your run_agent_loop from Task 1 handles the exact same situation.

3 Run both on a known and an unknown city

Run the file. You should see run_agent_loop("Chicago") produce a grounded final answer recommending an umbrella, run_agent_loop("Nowheresville") produce an honest "no data" answer with no crash, rigid_workflow("Chicago") succeed, and rigid_workflow("Nowheresville") raise a KeyError — that crash is expected, not a bug to fix.

🐞 Task 4 — Explain the Crash

rigid_workflow crashes only when given a city outside WEATHER_DB — it works fine for Chicago. Explain in your own words why it crashed on the unknown city, and what that tells you about why broken workflows often look correct in demos (they've only ever been run on the "happy path" cases someone thought to test).

Then answer the harder follow-up: you could "fix" rigid_workflow with a try/except KeyError around that one line. What's the actual difference between that patch and what run_agent_loop does? Think about how many different unanticipated tool failures each approach could handle without a programmer writing a new branch for each one — a rate limit error, a malformed city name, a value in the wrong units. One catches exactly the case you anticipated; the other reasons over whatever it actually observes.

rigid_workflow.py 
def rigid_workflow(city: str):
    cost = calculator("3 * 14.50")
    weather = weather_lookup(city)
    rain_chance = weather["chance_of_rain_pct"]  # crashes if "error" key present
    return f"{rain_chance}% chance of rain. Total cost: ${cost:.2f}"
