Session 4.1 Interview Prep 8 min read

Interview Questions: Agents, Workflows & the Plan-Act-Observe Loop

"Agent" is one of the most abused words in a GenAI interview right now — interviewers use these questions specifically to separate candidates who can precisely define the term from candidates who just reach for it whenever an LLM is involved. Each question below includes what a strong answer sounds like, common red flags, and a natural follow-up. Click any question to expand it.

1 How would you explain the difference between an agent and a workflow to a non-technical stakeholder who keeps calling everything an agent?
Strong answer

A workflow is a fixed sequence of steps a person designed in advance — even if it calls an LLM at several points, the order and the branches were decided ahead of time. An agent is a system where the model itself decides what to do next based on what it just observed, repeatedly, until it judges the goal is met. A strong candidate reaches for the concrete test from the chapter: if you swapped the model's decisions for a flowchart a person designed, would the system behave differently on a case nobody specifically planned for? If no, it's a workflow with an LLM inside it. If yes, it's a real agent. Framing it this way gives a non-technical stakeholder something checkable, not just vocabulary.

Red flags

Answering only with buzzwords ("agents are autonomous, workflows aren't") without a concrete test or example; or being unable to name a system that uses an LLM but is not an agent by this definition.

Follow-up

"Give me an example of a system that uses three separate LLM calls but is still just a workflow." (Strong answer: any fixed pipeline like summarize → classify → conditionally escalate, where the branching condition was written by a programmer in advance, not decided by the model reacting to something novel.)

2 Describe a real or hypothetical system where making it "fully agentic" would actually be a worse engineering decision than keeping it a workflow.
Strong answer

Any high-frequency, low-variance task is a good example — a scheduled weekly reminder email, a fixed data-extraction pipeline with a stable input format, a routine report generator. These tasks don't have "genuinely distinct sub-problems that need in-the-moment decision-making" — the steps are the same every time. Making them fully agentic adds latency, cost (more model calls), and unpredictability (harder to test exhaustively, new failure modes like an infinite loop or a wrong tool call) without buying any real flexibility, because there was never a decision that needed making at run time. A strong candidate connects this to the chapter's point that most production systems should be mostly workflow, with only a small, deliberately-scoped agentic piece where flexibility actually earns its cost.

Red flags

Claiming agents are strictly "more advanced, therefore always better," or being unable to name a concrete cost of making something needlessly agentic (predictability, testability, latency, spend).

Follow-up

"Your team already built the fully agentic version and it works, but it's expensive and occasionally does something weird. Do you rip it out?" (Pragmatic answer: not necessarily — first measure whether the flexibility is actually being used on real traffic; if the task's variance turns out to be low in practice, scale it back to a workflow with an LLM at the one or two steps that genuinely benefit.)

3 What's the practical difference between a system failing because it crashed and a system failing because it confidently gave a wrong answer? Which is worse, and why?
Strong answer

A crash is loud and immediate — you know something broke, and you can often see exactly where (the rigid workflow in this chapter's trace raises a KeyError the moment it hits a city with no data). A confidently wrong answer is quiet: nothing errors out, the system returns something plausible-looking, and unless someone happens to fact-check it, it can propagate downstream and get acted on. A strong candidate argues the quiet failure is usually worse in production, precisely because there's no signal that anything went wrong — it depends on someone noticing the output was incorrect, which is a much weaker safety net than a stack trace. This is exactly the shape of the Pro-path project for this session: the rigid version there doesn't crash on the contradiction case, it just confidently gives the wrong advice.

Red flags

Claiming crashes are always worse "because they're visible to users" without weighing the cost of an undetected wrong answer; or treating the two failure modes as equivalent without reasoning about detectability.

Follow-up

"How would you design a system to convert more of its 'confidently wrong' failures into 'loud and detectable' ones?" (Good answers mention grounding every claim in a traceable tool result, logging intermediate observations, and adding checks that compare an answer's implications against the evidence it was supposedly based on — exactly the re-planning check this session's Pro-path project builds.)

4 Walk through what "stopping condition" means for an agent loop, and describe one way an agent loop could fail to stop even when it should.
Strong answer

A stopping condition is the explicit rule that ends the plan-act-observe loop — without one, nothing inherently tells the model it's done. Common forms: the model itself emits a "done" or final-answer signal once it judges the goal is met, a hard iteration/step limit acts as a safety net, or a specific success condition is checked after each observation. A concrete failure mode: the model keeps calling the same tool with slightly different arguments because it never becomes confident it has "enough" information, or because the goal itself was ambiguously specified and the model can't tell when it's satisfied — so it loops until an external limit (if one exists) finally cuts it off.

Red flags

Assuming the model will "just know" when to stop without any explicit mechanism, or naming only a step-count limit without discussing why the loop got stuck in the first place.

Follow-up

"You add a hard iteration limit of 10 as a safety net, and now the agent sometimes stops too early on legitimately hard tasks. What does that tell you?" (Strong answer: a hard limit alone treats the symptom, not the cause — the real fix is usually a clearer success condition or better prompting about what "done" looks like, with the iteration limit kept only as a last-resort safety net, not the primary stopping mechanism.)

5 You're asked to build three systems: (A) a reminder email sent every Monday morning, (B) a tool that researches a topic and answers follow-up questions about it dynamically, (C) a tool that extracts structured data from PDFs with a fixed, known layout. For each, would you use an agent or a workflow? Why?
Strong answer

(A) is a workflow — there's no decision to make at run time, just a scheduled action; an agent here is pure overhead. (B) is a strong candidate for an agent — the topic changes every time, the model needs to decide what to search for and when it has enough evidence, which is exactly "deciding what to do next based on what just happened." (C), somewhat counterintuitively, is usually still a workflow if the layout is genuinely fixed and known in advance — a single well-tested extraction prompt (or even non-LLM parsing) handles it more cheaply and predictably than a full agent loop, since there isn't a real decision being made about what to do next. A strong candidate frames the decision rule explicitly: agent when the task has genuine, un-enumerable variability and benefits from in-the-moment reasoning; workflow when the steps are predictable and repeatable, even if an LLM is involved at one stage.

Red flags

Defaulting to "agent" for all three because it "sounds more capable," or treating (C) as automatically agentic just because it involves an LLM parsing unstructured-looking text.

Follow-up

"For (C), what would change your answer and push you toward an agent instead?" (Good answer: if the PDF layouts turn out to vary unpredictably across documents — different vendors, different formats — such that no single fixed extraction approach handles all of them, that's exactly the kind of un-enumerable variability that justifies letting the model decide how to handle each document rather than hard-coding every case.)

Strategy Tips

  • Cover the "Strong answer" line, answer out loud, then check yourself against it — that's how these are meant to be used for self-testing.
  • Interviewers in this space are specifically listening for whether you reach for the flowchart test and can name concrete costs of over-using agents — not just correct-sounding vocabulary.
  • Pair this set with Session 4.3's stopping-condition content once you've built it, for a fuller picture of how "does it know when to stop" gets answered in real code.
