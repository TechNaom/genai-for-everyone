Session 4.1 Project 25 min build

The Contradiction Case

The Pro-path build for this session. The Core-path exercise had the agent react to a missing tool result (an unknown city). This project is harder: the tool result is present, but it contradicts an assumption baked into the user's own question — and you'll design the re-planning branch that makes the agent correct the user rather than politely agreeing with a false premise.

Example run

Output 
=== Consistent case: Chicago (question assumes rain, forecast IS rain) ===
Reactive agent final_answer:
"That matches the forecast -- Chicago is expecting rain tomorrow
(80% chance), so bring an umbrella."
Rigid workflow: "Yes, as your question mentioned, tomorrow's rain
means you'll want an umbrella."

=== Contradiction case: Phoenix (question assumes rain, forecast is SUNNY) ===
Reactive agent final_answer:
"Actually, tomorrow's forecast for Phoenix is sunny with only a 2%
chance of rain -- the opposite of what your question assumed. You
likely won't need an umbrella."
Rigid workflow: "Yes, as your question mentioned, tomorrow's rain
means you'll want an umbrella."   <-- confidently wrong

Notice: the rigid workflow gives the SAME advice in both cases --
it calls weather_lookup, but never actually checks the result
against the question's assumption.
How to run No installation and no API key needed. Download starter.py below and run python starter.py. Both tools in this project are real, offline Python functions — the point of this project is the re-planning logic that compares an observation to an assumption, not live model output.

What to build

Fill in the three # TODO sections in starter.py:

  • TODO 1 — contains_assumed_rain: a simple keyword check on the question text (does it mention "rain" or "raining"?). This stands in for the assumption a real agent would have to extract from the user's phrasing.
  • TODO 2 — run_agent_loop_pro: call weather_lookup, then compare the question's assumption to what the tool actually returned. If they conflict, the final answer must explicitly correct the user and cite the real chance_of_rain_pct — not just answer the literal question as if the premise were true. If they agree, confirm it. If the city has no data, say so honestly.
  • TODO 3 — rigid_workflow_pro: deliberately wrong on purpose — it calls weather_lookup so it looks like it's using real data, but the reply is built purely from whether the question mentioned rain. It never checks that assumption against the tool's actual result. This is the comparison point, not something to fix.

1 Run the consistent and contradiction cases

Run the file with Chicago (where the question's assumption matches the real forecast) and Phoenix (where it doesn't). Confirm the reactive agent's answer changes shape between the two — consistent confirmation vs. explicit correction — while the rigid workflow gives the same kind of answer either way, right or wrong.

2 Write the "what would the workflow need to hard-code" note

In a few sentences, explain what branch a programmer would have to add to rigid_workflow_pro to handle the Phoenix case correctly — and then explain why that fix still wouldn't generalize to the next contradiction nobody thought to check for (a question that assumes snow instead of rain, say, or a specific temperature). See README.md for a full worked answer to compare against.

Why this project matters

The Core-path exercise showed an agent surviving a tool that returned nothing useful. This one is subtler and, in a real product, more dangerous: the tool returned a perfectly good result, but a naive system used it to confirm a premise the user got wrong instead of correcting them. That's the difference between "my code crashed" and "my code confidently told someone the wrong thing" — the second failure mode is quieter and easier to ship by accident. The re-planning branch you wrote here — comparing what was assumed to what was actually observed, and speaking up when they don't match — is the same shape of reasoning a real tool-calling agent needs any time a user's framing might not match reality, which is exactly what Session 4.2 starts building for real.
