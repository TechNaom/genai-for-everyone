Session 4.2 Exercises 30–40 min, hands-on

Exercises: An LLM That Calls a Real Weather/Calculator Tool

Take the same calculator and weather_lookup functions from Session 4.1 — already real, already tested — and wire them up to an actual LLM via the Anthropic API's tool-use feature. You define both tools' schemas, send a real question to the model, execute whichever tool(s) it actually decides to call, and feed the results back to get a final, grounded answer.

Free/open vs. paid API — read this first Most of this course's exercises run entirely free and offline. This one is the exception, and deliberately so: the model's actual tool-calling decision is the entire point of the exercise, and there's no free or open substitute for a live model making that decision. The Anthropic API is a paid, metered service — Session 4.1's simulated trace was designed specifically to avoid this cost while you learned the concepts; this session is where that training wheel comes off. If you don't have a key yet, you can still do real, verifiable work offline — build_tool_schemas() and execute_tool() are pure logic with no API dependency, and offline_test() validates both, including two error-handling edge cases, without touching the network. It's also fine to test the shape of your request with a fake placeholder key — anthropic.Anthropic() constructs without ever reaching the network, so you can confirm the request is built correctly before it fails at the network call.
How to run these You'll need Python 3 and the anthropic package (pip install anthropic --break-system-packages). Download starter.py below, set ANTHROPIC_API_KEY in your environment if you have one, then run python starter.py from a terminal. It runs the offline tests first, then attempts four real questions against a live model.
starter.py solution.py (reference)

The task

Open starter.py. The real calculator and weather_lookup functions are already there, unchanged from Session 4.1. Three functions are left for you to fill in.

1 Define the tool schemas

Fill in build_tool_schemas() so it returns two tool definitions formatted exactly as the Anthropic API expects — each a dict with name, description, and input_schema keys. Write real, specific descriptions that say both what each tool does and when to use it — a vague description ("weather tool") produces unreliable tool-calling behavior, exactly as the lesson described.

2 Execute whichever tool the model requests

Fill in execute_tool() to dispatch a tool name and input dict to the correct real function. Handle the calculator's invalid-input case (catch the ValueError and return a string describing the error, don't let it crash) and an unknown-tool-name case defensively — the same honest-failure-reporting principle from Session 4.1's weather_lookup.

3 Build the full tool-calling loop

Fill in run_conversation(): send the message and tool schemas to the model, check stop_reason, and if it's "tool_use", execute every requested tool and send the results back — tagged with the matching tool_use_id, immediately following the assistant's tool-use turn — then repeat until the model returns a final text answer.

Q: What's 3 umbrellas at $14.50 each, and will I need one tomorrow in Chicago?

Watch for these two specific moments Question 3 ("What's 127 times 38?") is a genuine test of whether the model reaches for the calculator or just answers from its own arithmetic ability — either is a legitimate outcome; the point is to actually observe which happens, not assume. Question 4 (Miami, a city not in WEATHER_DB) tests whether the model reports the tool's honest error back to you clearly, or tries to guess a plausible-sounding forecast anyway despite the tool telling it there's no data.
Checking your work offline_test() should pass with no assertion errors regardless of whether you have an API key. If you do have one, all four test questions should return a sensible final answer, with the calculator and weather questions actually triggering their corresponding tool, and the Miami question producing an honest "no data available" answer rather than a guessed forecast.
