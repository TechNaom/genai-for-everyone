Session 4.2 Interview Prep 9 min read

Interview Questions: Function / Tool Calling

Tool calling shows up in almost every "have you actually built an agent" interview question, and interviewers can tell within thirty seconds whether a candidate has the mental model right or is repeating "the AI decides to run code" without understanding what that sentence hides. Each question below includes what a strong answer sounds like, common red flags, and a natural follow-up. Click any question to expand it.

1 A junior engineer says, "I gave the model a tool, so now it can run code." What's wrong with that statement, and how would you correct it?
Strong answer

The model still can't run anything — it has no execution environment, no hands, no permissions. Giving it a tool means giving it a name, a description, and an input schema; when the model "calls" the tool, it just generates a structured request naming the tool and the arguments it wants to use. Your application is entirely responsible for actually executing the real function and reporting the result back. A strong candidate reframes this precisely: tool calling is a communication protocol between a model that can reason but can't act, and code that can act but can't decide when to.

Red flags

Agreeing with the junior engineer's framing, or being unable to name concretely what step your own code is responsible for (executing the function, and reporting real success/failure back).

Follow-up

"What happens if the model requests a tool call for a tool name that doesn't exist in your schema list?" (Strong answer: your code should handle this defensively — return an explicit error result rather than crashing, the same honest-failure-reporting principle that applies to any other tool failure.)

2 Walk me through what happens, step by step, between a model deciding to call a tool and that tool's result reaching the model again.
Strong answer

You send the model a message plus a list of tool definitions (name, description, schema). The model decides a tool call is the best response and returns a structured signal — the tool's name, the arguments, and an identifier for this specific call — instead of ordinary text. Your code executes the real function with those arguments. You send the actual output back as a new message, tagged with that same identifier, and it must come immediately after the tool-use message with nothing in between, since the model reads the conversation sequentially. The model then reads the result and either calls another tool or produces a final answer incorporating it.

Red flags

Skipping the ordering constraint entirely, or describing the tool result as "sent to the model" without mentioning it must be tagged to the specific call it answers.

Follow-up

"What would go wrong if you appended the tool result two messages later instead of immediately after the request?" (The model has no reliable way to connect the result to the original request — especially once more than one tool call is in flight — and its next response becomes unpredictable.)

3 Your tool-calling agent sometimes calls the wrong tool, or doesn't call a tool when it should. Where do you look first to fix this, and why?
Strong answer

Start with the tool's description and input schema, not the model. A model decides to call a tool through the same next-token-prediction process behind all of its other output — there's no separate "decision module" to debug. Unreliable or unexpected tool-calling behavior is almost always a sign that the description is vague about when to use the tool, or that the schema doesn't clearly specify what's expected — the same way a vague prompt produces a vague or inconsistent response. Concluding "the model is unreliable" skips past the much more common and far more fixable explanation: the specification under-determined the behavior.

Red flags

Jumping straight to "switch to a bigger/different model" without first inspecting the tool definitions, or treating the fix as a mysterious prompt-engineering art rather than the same clarity work used on any other prompt.

Follow-up

"You clarified the description and it still misfires on one specific question. What's your next move?" (Add a concrete example to the conversation showing the kind of question that should — or shouldn't — trigger this tool, and re-test that exact question to confirm the fix actually worked.)

4 Why does a failed tool call need to report failure back to the model explicitly, instead of just being skipped or left out of the conversation?
Strong answer

The model has no other way to know a tool call failed — it isn't watching your code execute, so if you skip the result or return nothing, the model is left reasoning as if the call is still pending, or worse, may fabricate a plausible-sounding outcome. Returning an explicit error result (e.g. a dict with an "error" key) lets the model see exactly what happened and respond honestly — telling the user weather data isn't available, for instance, rather than guessing a forecast. This is the same defensive design principle from structured outputs and graceful failure design earlier in the course, applied to tool results specifically.

Red flags

Suggesting the program should just crash on a tool failure, or that silently omitting a result is acceptable because "the model will figure it out."

Follow-up

"Give me a concrete example of a tool call failing silently causing a worse outcome than an honest error." (e.g. a weather tool returning nothing for an unlisted city, and the model then guessing a plausible-sounding but fabricated forecast instead of saying data isn't available.)

5 Design a tool schema for a "search_web" function that an agent will use. What arguments would you include, and how would you prevent the model from using the tool incorrectly?
Strong answer

A schema with a required query string field (with a description guiding query shape, e.g. "1-10 words recommended") and an optional num_results integer with sane bounds and a default. Clarity in the field descriptions actively guides the model's behavior — the same way a tool's top-level description does — and type/required-field constraints reduce the space of malformed calls your code has to defend against. A strong candidate also flags what your code still needs to handle even with a good schema: what happens if the model sends a 500-word query, or an out-of-range num_results — reject, clamp, or truncate, and test that the tool isn't used with invalid arguments or hallucinated tool names.

Red flags

Vague field descriptions ("query: some text"), no constraints on types or ranges, or assuming the schema alone guarantees correct usage with no validation logic in the tool's own execution code.

Follow-up

"The model keeps sending generic queries like 'information' or 'facts.' How do you fix it?" (Tighten the query field's description with concrete guidance and examples of specific vs. generic queries — the same description-clarity fix used for any unreliable tool-calling behavior.)

Strategy Tips

  • Cover the "Strong answer" line, answer out loud, then check yourself against it — that's how these are meant to be used for self-testing.
  • Interviewers are listening for the reframe (a protocol, not a superpower) and concrete debugging instincts (fix the spec, not the model) — not textbook recall of the round-trip steps alone.
