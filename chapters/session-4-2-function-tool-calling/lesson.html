Function / Tool Calling

Session 4.1 left you with a scripted stand-in for a model's decisions. Today the stand-in disappears — you give a real LLM real tools and watch it genuinely decide, on its own, when to reach for one.

On this page 1. Giving the Model Real Hands 2. The Three Things Every Tool Needs 3. What Actually Happens When a Model "Calls" a Tool 4. When Does a Model Actually Decide to Call a Tool? 5. Connecting Back to the Agent Loop
Session 4.1 left you with a precise definition of an agent — a system where the model decides what to do next, based on what just happened, repeatedly, without a human choosing each step — and a trace you ran by hand, with the model's decisions scripted rather than real. That honesty mattered: nothing in that trace was actually decided by a live model. The calculator and weather_lookup functions were real, executable code, but the choice of when to call them was written by a human in advance, standing in for what a model would plausibly decide. Today, that stand-in disappears. You're going to give an actual LLM real tools, and watch it genuinely decide — on its own, from the conversation alone — when to reach for one. This is the moment the "act" step of the agent loop stops being something you simulate and becomes something you build for real.
Sub-topic 1 of 5

1. Giving the Model Real Hands

Here's the mental model worth holding onto from the start: tool calling does not let the model run code. A language model is fundamentally a text generator. It cannot reach out and execute a Python function, query a database, or hit an API on its own — it has no hands, no permissions, no execution environment of any kind.

What is... tool calling, really? What tool calling actually gives the model is something narrower and, once you see it clearly, much less mysterious: a structured way to say "I want you to run this specific function, with these specific arguments" — and then it's entirely on your code to actually run it and report back what happened.

This matters because it reframes the whole topic. You are not teaching a model a new superpower. You are building a very specific, very deliberate communication protocol between a model that can reason but can't act, and your code, which can act but can't reason about when to. Tool calling is the bridge between those two halves.

Why the reframe matters in practice
  • If you think of tool calling as "the model runs code," a failed tool call feels like a mystery — it isn't. It's your code's job that failed, or your code that never told the model what happened.
  • Once you see it as a protocol between two halves that each do one thing well (reasoning vs. acting), debugging becomes concrete: which half's job actually broke?
Quick recap
  • Tool calling does not let a model execute code — it lets the model request that your code execute something specific.
  • The model has no hands, no permissions, no execution environment of its own.
  • Tool calling is a communication protocol between a model that can reason but can't act, and code that can act but can't decide when to.
Sub-topic 2 of 5

2. The Three Things Every Tool Needs

When you hand a model a tool, you're not handing it code — you're handing it a description of code: a name, an explanation of what it does, and a precise specification of what inputs it needs. The model never sees your function's implementation at all. It only ever sees these three things, and it has to decide when and how to call the tool based on nothing else.

1. A name Short, specific, and unambiguous — get_weather, not helper2. The model uses this name both to refer to the tool internally and, often, as a signal about what the tool is for. A vague name produces vague reasoning about when to use it.
2. A description This is the single highest-leverage piece of a tool definition, and it's worth treating with the same care you gave prompt design back in Week 2 — because that's exactly what it is, a prompt, just one the model reads to make a single decision rather than to generate a long response. A good description says what the tool does, and just as importantly, when to use it: "Get the current weather for a city. Use this when the user asks about weather conditions, temperature, or whether they'll need an umbrella." A vague description — "weather tool" — leaves the model guessing both about the tool's behavior and about whether this question even calls for it.
3. An input schema This is a precise, machine-readable specification of exactly what arguments the tool needs, and what shape they should take — typically expressed as JSON Schema, the same kind of structured-format thinking you practiced in Session 2.4. The schema isn't decoration — it's what lets the model produce a call that your code can actually parse and execute without guessing at what it meant.
weather_tool_schema.json 
{
  "name": "weather_lookup",
  "description": "Get the current weather for a city. Use this when the user asks about weather conditions, temperature, or whether they'll need an umbrella.",
  "input_schema": {
    "type": "object",
    "properties": {
      "city": {
        "type": "string",
        "description": "The city name, e.g. 'Chicago'"
      },
      "units": {
        "type": "string",
        "enum": ["celsius", "fahrenheit"],
        "description": "Optional temperature units"
      }
    },
    "required": ["city"]
  }
}

Put plainly: name tells the model what to call it, description tells the model when and why to call it, and the schema tells the model exactly how to call it. Get any one of the three vague, and the model's tool-calling behavior gets correspondingly unreliable — not because the model is bad at the task, but because you've under-specified the contract, in exactly the way Session 2.1 warned you an under-specified prompt produces an under-specified answer.

Quick recap
  • Every tool has three load-bearing parts: name, description, and input schema.
  • The description is the highest-leverage part — it's a prompt the model reads to decide both what the tool does and when to use it.
  • The schema is what lets the model produce a call your code can actually execute without guessing.
Sub-topic 3 of 5

3. What Actually Happens When a Model "Calls" a Tool

Here's the full round trip, made concrete, because the mechanics matter more than they might seem to at first glance.

the_round_trip.txt 
1. You send the model a message + a list of tool definitions it may use.
2. The model reads the conversation and decides: does this need a tool?
   If yes, which one, and with what arguments?
3. If it decides to use a tool, you get back a structured signal --
   the tool's name, the arguments, and an identifier tying this call
   to whatever response you send back. Not ordinary text.
4. YOUR CODE -- not the model -- actually runs the real function.
5. You send the tool's actual output back to the model, tagged with
   that same identifier, as a new message in the conversation.
6. The model reads the result and continues -- another tool call, or
   a final natural-language answer incorporating what came back.

Step 4 is the one people skim past and shouldn't. The model never executes anything. If your weather tool would, in a real implementation, hit a live weather API, the model has no idea whether that API call succeeded, failed, or returned garbage until you tell it, explicitly, in step 5. This is exactly why the defensive instincts from Session 2.4 (validate before trusting) and Session 2.6 (plan for the failure case, not just the happy path) show up again here: a tool call that fails needs to report failure back to the model honestly, the same way weather_lookup in Session 4.1's exercise returned an {"error": ...} dict rather than silently returning nothing or crashing.

A structural detail that trips people up the first time
  • Steps 3 through 5 have to happen in a specific order in the conversation history. The tool result message has to come immediately after the tool call message — you cannot insert anything else between an assistant's tool-use request and your reply with the result.
  • The model is reading the conversation sequentially, the same way it reads everything else; if the result doesn't directly follow the request, the model has no reliable way to connect the two.

Quick recap
  • The round trip is: you send tools + message → model requests a tool call → your code executes it → you send the result back, tagged → model continues.
  • The model never executes anything itself — step 4 is entirely your code's job.
  • The tool result must come immediately after its matching tool-use request in the conversation — the model reads sequentially and has no other way to connect the two.
Sub-topic 4 of 5

4. When Does a Model Actually Decide to Call a Tool?

This is the question today's chapter title promises and the one most worth sitting with, because the honest answer is less mystical than "the AI decides" makes it sound.

What is... actually happening at decision time? The model calls a tool when, based on the conversation and the tool descriptions you provided, generating a tool-call response is the most plausible continuation — the same next-token-prediction process from every other session this course has covered, just now with "call this tool" as one of the available kinds of output, alongside ordinary text. There's no separate decision-making module bolted on. It's the same model, reading the same kind of context, just with a wider menu of valid response shapes.

This has a genuinely useful practical consequence: if a model isn't calling your tool when you expect it to, or is calling it when it shouldn't, the fix almost always lives in the same place a bad-prompt fix lives — clarify the description, tighten the schema, or add an example to the conversation showing the kind of question that should trigger this tool. You're not debugging a black box. You're doing the same prompt-engineering work from Week 2, applied to a tool definition instead of a task instruction.

Being honest about a real limitation
  • Giving a model a tool doesn't guarantee it will use the tool correctly, or at all, every single time — in the same spirit Session 3.1 insisted on for retrieval.
  • A model might decide a question doesn't need a tool when it actually does, might pass a slightly malformed argument, or might call a tool when a direct answer would've been better.
  • This is precisely why today's exercise asks you to actually run the loop and inspect what happens — not just read about the theory — because seeing a real tool-call decision (and occasionally a real misfire) is the only way to build accurate intuition for when this mechanism is reliable and when it needs guardrails.
Go Deeper: is "just answer directly" ever the right call, even with a calculator available?

Yes — and this is a genuinely observable, legitimate outcome, not a bug. A model might correctly compute 127 × 38 from its own arithmetic ability without reaching for the calculator tool at all, or it might call the tool anyway out of caution. Either is defensible behavior; the exercise asks you to watch which one actually happens rather than assume. The interesting failure mode isn't "didn't use a tool it had access to" — it's producing a wrong answer while skipping a tool that would have caught the error, or reaching for a tool for something so simple that the extra round trip added latency for no benefit.

Quick recap
  • A model decides to call a tool through the same next-token-prediction process behind everything else it generates — there's no separate "decision module."
  • Unreliable tool-calling behavior is fixed the same way a bad prompt is: clarify the description, tighten the schema, or add an example.
  • Tools don't guarantee correct or consistent use — that's why you run the loop for real and inspect what actually happens.
Sub-topic 5 of 5

5. Connecting Back to the Agent Loop

Look at where this sits inside Session 4.1's plan-act-observe framing, because today's session is best understood as filling in exactly one piece of that loop, not introducing a new one.

What is... plan, act, observe, made real? Plan is the model deciding what to do next — which, today, includes deciding whether that "next thing" is calling a tool. Act is the tool call itself: the structured request, your code executing it for real. Observe is the tool result flowing back into the conversation, ready to inform the model's next decision. Session 4.1 simulated all three steps by hand. Today, you're building "act" for real, for the first time — and as a direct consequence, "plan" and "observe" become real too, since they're now driven by an actual model's actual decisions rather than a scripted policy standing in for them.

This is also where Session 4.1's chatbot-vs-workflow-vs-agent distinction gets sharper rather than more abstract. A chatbot with no tools can only ever produce text. A rigid workflow might call a weather API and a calculator in a fixed order regardless of what's actually being asked. What you're building today — a model that looks at a real question, decides for itself whether the question needs a calculator, a weather lookup, both, or neither, and only then acts — is the first genuinely agent-shaped system this course has built where every part of that description is true at once, with a live model making the call.

Quick recap
  • Plan-act-observe was simulated by hand in 4.1; today, "act" becomes real, which makes "plan" and "observe" real by consequence too.
  • A chatbot only produces text; a rigid workflow calls tools in a fixed order; today's build genuinely decides, per question, whether and which tool to use.
In the Real World
  • Production tool-calling systems spend a disproportionate amount of engineering time on descriptions and schemas, not on the loop code itself — the loop is a handful of lines; getting the model to reliably pick the right tool is the actual work.
  • A common production pattern for ambiguous tool boundaries (e.g. a calculator vs. a unit_converter) is to run a fixed set of representative test questions every time a description changes, and check the tool choice didn't regress — the same testing discipline Session 2.5 introduced for prompt templates, applied here to tool definitions.
  • Interviewers frequently ask candidates to design a tool schema live (e.g. for a search_web function) specifically to see whether they reach for tight types, required fields, and descriptive constraints, or leave the schema vague and hope for the best.

Points to Remember

  • Tool calling does not let a model execute code. It lets the model request that your code execute something specific, with specific arguments — your application remains entirely responsible for actually running the operation.
  • Every tool definition has three load-bearing parts: a name, a description (which doubles as a prompt the model uses to decide when to call the tool, not just what it does), and an input schema specifying exactly what arguments it needs.
  • The full round trip is sequential and strict: the model requests a tool call, your code executes it, and the result must be sent back immediately following that request, tagged so the model can match it to the original call.
  • A model decides to call a tool through the same next-token-prediction process behind everything else it generates — there's no separate "decision module." Unreliable tool-calling behavior is usually a sign the tool's description or schema needs the same clarity work as a prompt.
  • A tool that fails should report the failure honestly back to the model (an error result), not crash silently or fail invisibly — the same defensive design principle from structured outputs and graceful failure design earlier in this course.
  • Today's build is the first time this course has implemented the "act" step of the agent loop for real, with a live model making genuine decisions, rather than a scripted stand-in.
