Session 4.2 Project Pro path 30–40 min build

A Third, Deliberately Ambiguous Tool

The Pro-path build for this session — add a third tool with a deliberately ambiguous boundary against one of the two from the core exercise, watch the model's real tool-choice behavior on questions that straddle that boundary, and practice the fix-then-verify loop for unreliable tool-calling behavior.

Needs a real API key Same as the core exercise: this project's entire point is watching a live model make a real, sometimes-ambiguous tool-choice decision, so there's no free or open substitute for running it end to end. If you don't have a key, read through solution.py to see the finished descriptions and the reasoning behind them — the schema design itself is real, verifiable work you can review without spending anything.

The setup

You'll add a unit_converter tool alongside the core exercise's calculator and weather_lookup. A question like "What's 68 degrees Fahrenheit in Celsius?" is genuinely ambiguous against calculator — it's pure arithmetic under the hood, and a human might just as easily call it "a conversion" or "some math." convert_units(), a real working function supporting Fahrenheit/Celsius and miles/kilometers conversions, is already provided in starter.py; your job is the tool schema, the dispatch wiring, and the actual investigation.

starter.py solution.py (reference)

What to build

1 Write unit_converter's schema

Fill in unit_converter_schema inside build_tool_schemas(). Start with something plausible but not yet fully disambiguated from calculator's existing description — you want to actually observe the ambiguity before you fix it.

2 Wire up the dispatch

Add the "unit_converter" branch to execute_tool(), calling convert_units(tool_input["value"], tool_input["from_unit"], tool_input["to_unit"]) and returning the JSON-serialized result.

3 Observe, then fix, then verify

Run run_ambiguity_test() against the three ambiguous questions in AMBIGUOUS_QUESTIONS, printing which tool actually got called each time. For any case where the model picks the "wrong" tool or hesitates, rewrite the relevant description(s) with an explicit "use this for X, not for Y" clause — then re-run the exact same question and confirm the tool choice actually changed. A description that reads more clearly to you is not the same thing as a description that changes the model's decision — check.

Example run (with a real API key)

Output 
======================================================================
Q: What's 68 degrees Fahrenheit in Celsius?
  [tool call] unit_converter({'value': 68, 'from_unit': 'fahrenheit', 'to_unit': 'celsius'})

A: 68 degrees Fahrenheit is 20 degrees Celsius.

======================================================================
Q: If it's 30 degrees Celsius, what's that times 2?
  [tool call] unit_converter({'value': 30, 'from_unit': 'celsius', 'to_unit': 'fahrenheit'})
  [tool call] calculator({'expression': '86 * 2'})

A: 30C is 86F, and 86 times 2 is 172.

======================================================================
Q: How many kilometers is 10 miles?
  [tool call] unit_converter({'value': 10, 'from_unit': 'miles', 'to_unit': 'kilometers'})

A: 10 miles is about 16.09 kilometers.
Why this matters Adding a third tool with a deliberately overlapping boundary is the most direct way to practice the debugging instinct from the lesson: unreliable tool-calling behavior is a specification gap, not a model failure. The interesting outcome here isn't "did the model get it right the first time" — it's whether you can reliably diagnose a wrong or hesitant choice, fix the description, and prove the fix worked by re-running the exact same question rather than assuming clearer-sounding wording did the job.

Why this project matters

Two well-specified tools rarely collide in practice — the interesting failure mode shows up once a third, genuinely overlapping capability enters the picture, which is exactly what happens as real tool-calling systems grow past a toy two-tool demo. Practicing the observe → fix → verify loop on a small, safe example here is the same discipline you'd apply at much higher stakes once a production agent has a dozen tools with real boundary cases between them.
