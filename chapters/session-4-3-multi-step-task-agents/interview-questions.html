Session 4.3 Interview Prep 10 min read

Interview Questions: Multi-Step Agent Design & Debugging

Once a candidate can explain what an agent is and how tool calling works, interviewers move to the question that actually separates "read about agents" from "built one": can you design a multi-step agent loop, name its concrete failure modes, and debug one when it's stuck in a loop or stopping too early. Each question below includes what a strong answer sounds like, common red flags, and a natural follow-up. Click any question to expand it.

1 Design a multi-step agent that researches a topic and writes a report. How would you structure it, what could go wrong, and how would you debug it?
Strong answer

A strong answer names a three-phase structure: Plan (the agent writes out what it will search for, before executing), Execute (a loop where the agent calls search tools and observes results), and Synthesize (the agent stops calling tools and writes the final report). Implementation details worth naming: a working memory that tracks findings so the agent doesn't forget mid-task, a max-iteration safety limit, and a stopping condition based on the absence of tool calls in the response. A strong candidate can also name the concrete failure modes unprompted: infinite loops (same tool, near-duplicate queries), early stopping (partial report, agent quits), forgotten context (early results lost to token limits), and wrong ordering (searching for conclusions before gathering data).

Red flags

"Just call search tools until you have enough data" with no structure at all; no mention of working memory or an iteration limit; no debugging plan; confusing the planning phase with the execution phase.

Follow-up

"Your agent researches 5 topics but only cites the last 2 in the report. Why?" (Strong answer: almost certainly a context-window / forgetting problem — early findings got pushed out or under-weighted by the time the final synthesis prompt ran; fix by summarizing key findings as you go, not just at the end.)

2 Your agent is running for 20 iterations and not stopping. It keeps calling the same search tool with slightly different queries. How would you debug this, and how would you fix it?
Strong answer

Debug systematically: log every iteration (which tool, what query, what result came back), verify the stopping-condition logic is actually correct (does "no tool calls" really trigger a return?), and inspect the prompt for whether it's clear about success criteria. The root cause is usually one of: no real stopping condition at all, a prompt that doesn't define what "enough evidence" means, or the agent genuinely not realizing near-duplicate queries aren't yielding new information. Fixes: add an explicit stopping rule ("if you've called the same tool with a similar query twice, stop"), tighten the prompt to name a concrete success criterion ("stop once you have three independent sources"), add memory of prior queries so the agent can see it's repeating itself, and keep a max-iteration limit as the backstop. Always test with mocked tools before spending real API calls on the fix.

Red flags

"Just set a timeout" without investigating the root cause; no mention of prompt clarity or memory; proposing a fix without first logging/observing what the agent is actually doing.

Follow-up

"You added a 10-iteration cap, but now the agent stops too early on legitimately hard tasks. Why?" (Strong answer: an iteration limit is a safety net, not a quality control — if 10 genuinely isn't enough for the task's real complexity, the fix is a smarter stopping condition or a task-specific limit, not just raising the cap blindly.)

3 A user asks your system: "Analyze our Q3 sales performance, compare to competitors, and recommend next quarter strategy." Design this as an orchestrator-worker system. What tasks do you decompose into?
Strong answer

Decompose into independent worker tasks with a clear input/output contract for each: Worker 1 analyzes internal Q3 sales data, Worker 2 researches competitor Q3 results, Worker 3 gathers market trends and forecasts, and the Orchestrator collects all three results and synthesizes a final recommendation. A strong candidate notes that Workers 1–3 are largely independent and can run in parallel, while the Orchestrator step genuinely depends on all three finishing first — and calls out error handling explicitly (what happens if the competitor-research worker fails to find data, or a worker times out and needs a fallback).

Red flags

"One big agent does everything" (misses the entire point of decomposition); treating genuinely interdependent tasks as if they were parallel; not defining what each worker actually returns; no error handling for a failed or slow worker.

Follow-up

"Worker 1 takes 10 seconds and Worker 2 takes 30 seconds. How do you speed the whole thing up?" (Strong answer: since the three research workers are independent, run them concurrently rather than sequentially — total latency becomes roughly the slowest worker's time, not the sum of all three.)

4 Design an agent that processes incoming emails, categorizes them by urgency, and drafts responses. What could go wrong, and how would you test it?
Strong answer

A multi-step structure: read and categorize the email, extract action items, draft a response for anything urgent, then gate sending behind human review rather than sending automatically. Tool definitions worth naming: read_email, categorize, draft_response, flag_for_review, and send_email kept behind an approval step. A strong candidate treats human-in-the-loop as non-negotiable here (the cost of a wrong auto-send to a real client is high), names a confidence threshold for escalating uncertain cases, and insists on testing against a batch of historical emails before any real send capability is enabled.

Red flags

No human review loop at all (dangerous for anything that actually sends messages); no consideration of what happens when the agent miscategorizes or hallucinates content; no testing strategy beyond "try it and see."

Follow-up

"The agent flags almost every email as urgent. How do you debug and retune it?" (Strong answer: inspect a sample of the flagged emails against the categorization prompt's criteria, check whether the urgency definition in the prompt is too broad, and adjust the threshold or add clearer negative examples of "not urgent" rather than just tweaking a number blindly.)

5 You're building an agent to "Find the three most cost-effective cloud providers and explain why." It makes three searches (AWS, GCP, Azure pricing) and stops. Is that sufficient?
Strong answer

No — three pricing searches alone don't satisfy the task. The agent gathered raw pricing per provider, but never actually compared the pricing models (per-GB vs. per-request vs. egress costs differ meaningfully), never considered other factors like reliability, support, or compliance, and never defined "cost-effective" relative to a specific use case (a small startup's usage pattern looks nothing like an enterprise's). A strong candidate suggests concrete next steps: a comparison-focused search, a use-case-specific search, and a final synthesis step before the agent is allowed to stop. The general point: multi-step agents need to verify sufficiency against the actual task, not just execute a fixed number of steps and declare victory.

Red flags

Saying three searches are sufficient because "it did three things"; not connecting this back to the stopping-condition problem (the agent stopped calling tools, but that doesn't mean the task was actually complete).

Follow-up

"How would you change the prompt so the agent catches this gap itself?" (Strong answer: have the planning phase explicitly require a comparison/synthesis step as part of the plan, not just a list of provider searches — and reinforce during execution that raw data collection alone doesn't satisfy "explain why.")

Strategy Tips

  • Cover the "Strong answer" line, answer out loud, then check yourself against it — that's how these are meant to be used for self-testing.
  • Interviewers are listening for named, concrete failure modes (loops, early stopping, forgotten context, wrong ordering) and specific fixes — not a vague "the agent might mess up."
