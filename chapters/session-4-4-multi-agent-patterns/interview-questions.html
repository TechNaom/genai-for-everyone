Session 4.4 Interview Prep 10 min read

Interview Questions: Multi-Agent Patterns in Production

Multi-agent design is one of the questions interviewers use to separate candidates who've read about agents from candidates who've actually had to make one work reliably. These questions probe pattern selection, decomposition, and the cost/ latency trade-offs that only show up once a system is running for real. Each question below includes what a strong answer sounds like, common red flags, and a natural follow-up. Click any question to expand it.

1 You're building a system for legal document review. Describe how you'd structure it as a multi-agent system. What pattern would you use — orchestrator-worker, debate, or reviewer — and why?
Strong answer

The reviewer pattern is the strongest fit: a writer agent drafts a summary of the document, while a fact-checker verifies claims against the document text, a risk-assessor identifies legal risks, and a compliance-checker checks against relevant regulations. The reasoning: legal work is high-stakes and errors are costly, multiple independent reviewers catch different categories of error, and each agent can specialize like an expert system. A strong candidate also names the implementation details — structured feedback (JSON with error types), a convergence-based stopping condition, and a conflict-resolution rule (if agents disagree, route to a human reviewer) — and is explicit about the trade-off: this is expensive (multiple agents, multiple calls) and slower (sequential reviews), but quality matters far more than cost or speed in this domain.

Red flags

"Just use one agent" (misses the entire value of independent review), picking a pattern without reasoning through why it fits this specific domain, or not considering legal-specific needs (compliance, risk) at all.

Follow-up

"You ran three review rounds and still missed an error. What went wrong?" (Strong answer: reviewers may share the same blind spot, or the error type wasn't covered by any of the three reviewer roles — the fix is adding a reviewer for that specific gap, not just adding more rounds.)

2 A user asks your system: "Analyze our Q3 sales performance, compare to competitors, and recommend next-quarter strategy." Design this as an orchestrator-worker system. What tasks would you decompose it into?
Strong answer

Decompose into independent, specialized workers: Worker 1 analyzes internal Q3 sales data; Worker 2 researches competitor Q3 results; Worker 3 gathers market trends and forecasts; the orchestrator synthesizes all three into a final recommendation. A strong candidate notes the orchestrator's full job — assigning tasks, collecting results, integrating them — and flags that Workers 1–3 are independent enough to run in parallel, which is a real speed win the pattern enables. They also address communication (each task has a clear input/output format) and error handling (what happens if a worker's data source fails or times out).

Red flags

"One big agent does everything" (misses the point of decomposition entirely), treating genuinely interdependent tasks as if they were parallel, or not defining what each worker actually returns.

Follow-up

"Worker 1 takes 10 seconds, Worker 2 takes 30 seconds. How do you speed the whole system up?" (Strong answer: since the workers are independent, run them concurrently rather than sequentially — total latency becomes close to the slowest worker, not the sum of all three.)

3 Your agent-based system costs $0.50 per query and takes 30 seconds across 5 API calls. A user complains it's too slow. Would you use a faster model, fewer iterations, parallelization, or caching — and how do you decide?
Strong answer

Each lever has a different trade-off: a faster model reduces latency but may hurt quality, so test it first rather than assuming; fewer iterations is faster but risks less-thorough output; parallelizing independent agent calls gives a large speed win at the same cost, if the calls are actually independent; caching helps only if queries genuinely repeat. A strong candidate reasons about which lever fits this specific bottleneck — is it slow every time (favors caching or a faster model) or only sometimes (favors parallelization) — and insists on measuring the change (A/B testing latency and quality together) rather than guessing.

Red flags

"Just use a faster model" without acknowledging the quality risk, not considering whether the calls can be parallelized at all, or proposing a fix with no plan to measure whether it actually worked.

Follow-up

"You parallelize and latency drops to 8 seconds, but quality also drops. Why?" (Strong answer: parallel agents likely lost access to each other's intermediate outputs that a sequential pipeline would have passed along — some steps are truly interdependent and can't be parallelized for free.)

4 Your agent keeps calling the same search tool with slightly different queries and won't stop after 20 iterations. How do you debug it, and how do you fix it?
Strong answer

Debug systematically: log every iteration (what tool was called, what came back), check the stopping-condition logic directly, and look for the pattern — is the agent re-searching the same thing because the prompt never told it what "done" looks like? Root causes are usually one of: no stopping condition at all, a prompt that's unclear about success criteria, or the agent not recognizing it already has the answer because each search result looks "slightly new." Fixes: an explicit stopping rule ("stop if you've searched for something similar twice"), a clearer prompt about what counts as sufficient evidence, and a hard iteration limit as a safety net regardless of the smarter fix.

Red flags

"Just set a timeout" as the only fix (treats the symptom, not the cause), not investigating what the agent is actually doing before proposing a change, or no mention of testing the fix with mocked tools first.

Follow-up

"You added a 10-iteration limit, but now the agent stops too early. Why?" (Strong answer: the limit is masking the same underlying problem — the agent still doesn't have a real "I'm done" signal, it's just getting cut off before or after it happens to notice; the durable fix is still a clearer stopping condition, not a smaller or larger number.)

5 You're building a system to generate marketing copy that needs to be accurate, engaging, and on-brand. Budget allows multiple API calls. Which multi-agent pattern would you choose, and why?
Strong answer

Reviewer pattern: a writer produces the copy, and three specialized reviewers — an accuracy/fact-checker, an engagement/style-checker, and a brand-voice checker — each review it independently for their one concern, then the writer revises based on the aggregated feedback. Each reviewer catches a different category of error that the others would miss, which is exactly the value multiple specialized reviewers add over one generalist reviewer. A strong candidate explicitly names the trade-off: this is more expensive than a single pass, but worth it here because accuracy, engagement, and brand consistency all genuinely matter and none can be sacrificed for the others.

Red flags

Picking orchestrator-worker or debate without reasoning about why reviewer fits this specific need better, or naming "reviewer pattern" without being able to say what each reviewer actually specializes in.

Follow-up

"The fact-checker and the style-checker give conflicting feedback on the same paragraph. What does the writer do?" (Strong answer: this is a conflict-resolution decision that should be made up front — e.g. accuracy wins over style when they truly conflict, or the writer is prompted to satisfy both if genuinely possible before picking a winner.)

Strategy Tips

  • Cover the "Strong answer" line, answer out loud, then check yourself against it — that's how these are meant to be used for self-testing.
  • Interviewers listen for pattern-selection reasoning tied to the specific domain, not textbook recall — always be ready to say why a pattern fits, not just name it.
