Multi-Agent Patterns

In Session 4.3 you built one agent that planned, searched, and summarized, all by itself. This chapter is about what happens once you stop asking one agent to do everything, and start running several agents that specialize, collaborate, and check each other's work.

On this page 1. Why Go From One Agent to Many? 2. Three Multi-Agent Patterns 3. The Code: Writer + Critic Pattern 4. Real-World Patterns in Production 5. Trade-offs and When NOT to Use Multi-Agent 6. Building Resilient Multi-Agent Systems
In Session 4.3, you built a single agent that planned, executed tools, and summarized — all its own thinking, all in one place. Powerful, but limited in the same way one person doing every job on a project is limited. Real intelligence tends to emerge from collaboration: when you have a hard problem, you don't solve it alone — you get a colleague to challenge your reasoning, you assign specialized tasks to different people, you have one person drive while another navigates and watches for hazards. Multi-agent systems apply this same principle to AI. Instead of one big agent doing everything, you run multiple agents that specialize, collaborate, and critique each other. One agent drafts a blog post, another reviews it for accuracy. One agent proposes a plan, another argues against it to surface flaws. One agent gathers data, another synthesizes it. This chapter teaches you three patterns for this — orchestrator-worker, debate, and reviewer — and, just as important, when not to reach for any of them.
Sub-topic 1 of 6

1. Why Go From One Agent to Many?

A single multi-step agent, of the kind you built in Session 4.3, runs into real limits once tasks get large or quality bars get high.

Three problems a single agent runs into Context window limits — when an agent runs for many iterations, the token count grows. By iteration 10, earlier observations are buried in context; the agent effectively forgets what it learned in step 2. Specialization — some tasks need different reasoning styles. Writing needs creativity and flow. Fact-checking needs rigor and skepticism. One agent trying to do both trades off quality in each. No verification — a single agent can confidently output nonsense, and nothing catches it. If a second agent reviews the output independently, errors surface that the original agent would never have noticed in its own work.

The fix is straightforward to state: multiple agents, each with a role, instead of one agent doing everything.

one_agent_vs_many.txt 
Instead of:
[Single Agent: Plan -> Search -> Search -> Search -> Summarize]

You run:
[Agent A: Researcher] -> [Agent B: Writer] -> [Agent C: Critic] -> [Agent D: Fact-Checker]

Each agent in the second version has fewer iterations, a cleaner context window, and specialized reasoning to work with. Each can do one thing exceptionally well, rather than one agent doing four things adequately.

Quick recap
  • A single multi-step agent hits three walls as tasks grow: context window limits, the trade-off of needing different reasoning styles at once, and having no independent check on its own output.
  • Multi-agent systems address this by giving each agent fewer iterations, cleaner context, and one specialized job.
Sub-topic 2 of 6

2. Three Multi-Agent Patterns

Most multi-agent systems you'll encounter in production reduce down to one of three shapes. They're not mutually exclusive — real systems sometimes combine them — but each has a distinct idea behind it, a distinct "when to use it," and a distinct set of trade-offs.

Pattern 1: Orchestrator-Worker

What is... the orchestrator-worker pattern? One "boss" agent (the orchestrator) coordinates. Other agents (the workers) execute specialized tasks. Use it when a task is naturally decomposable (e.g. "research the market, research competitors, analyze risks"), when the sub-tasks are independent or only loosely coupled, and when you want one clear entity managing the overall flow.
orchestrator_worker_example.txt 
User: "Prepare a competitive analysis for Q3"

Orchestrator Agent:
  "I'll break this into 3 tasks:
   1. Task A (Research): Analyze Market Trends -> Worker 1
   2. Task B (Execution): Research Competitors -> Worker 2
   3. Task C (Integration): Synthesize findings -> Worker 3"

Worker 1: Calls search tools, returns market data
Worker 2: Calls search tools, returns competitor data
Worker 3: Integrates both, writes summary

Orchestrator: "Great! Here's the final report..."

Pros: clear separation of concerns; easy to parallelize, since workers can often run at the same time; simple to understand and debug. Cons: it requires explicit task decomposition — you (or the orchestrator) have to figure out how to split the work — and it has a single point of failure: if the orchestrator itself fails or mis-plans, the whole system fails with it.

Pattern 2: Debate

What is... the debate pattern? Multiple agents argue opposing positions; truth (or at least a well-explored answer) emerges from the disagreement. Use it when a problem has no obvious right answer, when you want to explore multiple perspectives deliberately, and when truth genuinely emerges from healthy disagreement — e.g. "is this marketing claim true?"
debate_example.txt 
Query: "Is remote work more productive than office work?"

Agent 1 (Pro-Remote):
  "Studies show: fewer distractions, no commute, flexible hours.
   Remote workers are 13% more productive (Stanford 2020)."

Agent 2 (Pro-Office):
  "Counter-evidence: collaboration, mentorship, serendipitous meetings.
   Office workers have 40% higher engagement (Microsoft survey)."

Agent 3 (Synthesizer):
  "Context matters: remote is better for focused, individual work;
   office is better for brainstorming and mentorship."

Pros: it explores trade-offs naturally, it's harder to get stuck in one narrow perspective, and it models how humans actually reason through genuinely uncertain questions. Cons: it can spiral into circular arguments, it requires an explicit stopping condition (when do you declare "done debating?"), and it's computationally more expensive than a single pass.

Pattern 3: Reviewer

What is... the reviewer pattern? One or more agents create; others verify independently. Use it when output quality is critical (writing, code, legal documents), when you want genuinely independent verification, and when errors would be costly.
reviewer_example.txt 
Task: "Write blog post about LLM safety"

Writer Agent:
  "Here's a draft about alignment, RLHF, and robustness..."

Fact-Checker Agent:
  "Fact-check: RLHF acronym is correct, date of GPT-4 release is correct...
   But this claim about alignment is unsupported by the cited paper."

Style Reviewer Agent:
  "The tone is too academic. Simplify technical jargon in paragraphs 2-4."

Synthesizer:
  "Updated draft incorporating feedback..."

Pros: it catches errors the original agent missed; quality scales with the number of reviewers; and each reviewer can specialize (one checks facts, one checks style, and so on). Cons: it's expensive — multiple agents means multiple API calls — it's slower than a single agent, and reviewers can generate conflicting feedback that someone (or something) has to resolve.

Quick recap
  • Orchestrator-worker suits naturally decomposable, loosely-coupled tasks — easy to parallelize, but a single point of failure.
  • Debate suits questions with no obvious right answer — explores perspectives, but needs an explicit stopping condition.
  • Reviewer suits high-stakes output — catches errors independently, but costs more in latency and API calls, and reviewers can disagree.

3. The Code: Writer + Critic Pattern

Let's build a Reviewer pattern in code: one agent writes, another critiques, and the writer revises. This is the smallest possible multi-agent system — just two agents — and it's the shape the Core Path exercise for this session asks you to complete.

writer_critic_loop.py 
from anthropic import Anthropic

client = Anthropic()
MODEL_ID = "claude-3-5-sonnet-20241022"

def writer_agent(topic: str, previous_feedback: str = None) -> str:
    """
    Agent 1: Writer. Writes a short essay on a topic.
    If given feedback, revises based on it.
    """
    if previous_feedback:
        prompt = f"""You are an expert writer.
Topic: {topic}

Here is previous feedback on your draft:
{previous_feedback}

Please revise your essay addressing this feedback. Keep it to 3-4 paragraphs."""
    else:
        prompt = f"""You are an expert writer.
Write a clear, engaging essay on: {topic}
Keep it to 3-4 paragraphs. Use accessible language."""

    messages = [{"role": "user", "content": prompt}]
    response = client.messages.create(
        model=MODEL_ID,
        max_tokens=1024,
        messages=messages
    )

    return "".join([block.text for block in response.content if hasattr(block, "text")])

def critic_agent(essay: str) -> str:
    """
    Agent 2: Critic. Reviews the essay for clarity, accuracy, and impact.
    Returns feedback, not a revised essay.
    """
    prompt = f"""You are a harsh but fair critic. Your job is to improve writing.

Read this essay:
{essay}

Provide 2-3 specific, actionable pieces of feedback. Be constructive but direct.
Focus on: clarity, accuracy, impact, and engagement."""

    messages = [{"role": "user", "content": prompt}]
    response = client.messages.create(
        model=MODEL_ID,
        max_tokens=512,
        messages=messages
    )

    return "".join([block.text for block in response.content if hasattr(block, "text")])

def multi_agent_writing_loop(topic: str, num_iterations: int = 2) -> dict:
    """
    Two-agent loop: Writer -> Critic -> Revision -> Critic -> Done
    """
    result = {"topic": topic, "drafts": [], "feedback_rounds": [], "final_essay": None}

    draft = writer_agent(topic)
    result["drafts"].append(draft)

    for iteration in range(num_iterations):
        feedback = critic_agent(draft)
        result["feedback_rounds"].append(feedback)

        draft = writer_agent(topic, previous_feedback=feedback)
        result["drafts"].append(draft)

    result["final_essay"] = draft
    return result

What's happening, step by step: the writer creates an initial essay; the critic reviews it and gives feedback (not a rewrite — just feedback); the writer revises based on that feedback; and the loop repeats, typically one or two times. The beauty of this split is that each agent is simpler than the single multi-step agent from Session 4.3. The writer doesn't have to critique itself — a genuinely hard thing for any writer, human or AI, to do well. The critic doesn't have to write. They each specialize, and each does its one job better as a result.

Since this is a real API call to a live model, it isn't something we can safely run directly in a browser playground. But the shape of the loop — and in particular, the convergence idea that shows up again in the Pro Path exercise — is worth seeing run.   • Each agent is simpler than a single agent trying to write and critique itself — specialization is the whole point.

4. Real-World Patterns in Production

Each pattern from Part 2 shows up, largely unchanged, in real production systems. Seeing them applied to concrete domains makes the abstractions click.

Orchestrator-Worker in the wild — a hiring pipeline
  • Orchestrator → Recruiter Agent: screen résumés
  • Orchestrator → Interview Agent: conduct a technical interview
  • Orchestrator → Reference Agent: check references
  • Orchestrator → Decision Agent: synthesize everything into a hiring decision
Debate in the wild — risk assessment
  • Bull Agent: "Stock price will rise because..."
  • Bear Agent: "No, it will fall because..."
  • Moderator: "Given both arguments, the risk is..."
Reviewer in the wild — code review
  • CodeWriter Agent: writes Python code
  • SecurityReviewer: "This has a SQL injection vulnerability"
  • StyleReviewer: "This variable name is unclear"
  • PerformanceReviewer: "This loop is O(n²), can be O(n)"
  • → CodeWriter revises based on all three

Notice the same shape recurring across very different domains: hiring, financial risk, and code review all reduce to one of the three patterns from Part 2, once you strip away the domain-specific vocabulary. That's a useful diagnostic when you're designing a new system — ask "which of these three shapes does my problem actually have?" before reaching for a more exotic architecture.

Quick recap
  • A hiring pipeline is orchestrator-worker: one coordinator, several specialized workers.
  • A bull/bear/moderator risk assessment is the debate pattern applied to finance.
  • A code review pipeline with a security, style, and performance reviewer is the reviewer pattern applied to engineering.

5. Trade-offs and When NOT to Use Multi-Agent

Multi-agent systems are not a strict upgrade over a single agent. They trade latency and cost for quality, and that trade isn't always worth making.

The honest trade-off
  • Single-agent is better when the task is simple (one step, one answer), when cost matters (more agents means more API calls), when latency matters (agents typically run sequentially), or when consistency is critical (multiple agents might disagree with each other).
  • Multi-agent is worth it when output quality is critical, when the task naturally decomposes into distinct sub-problems, when different specialized reasoning genuinely helps, and when you have the budget and time for multiple calls.
Go Deeper: how do you decide, for a specific task, which side of that line it falls on?

A useful test, borrowed from the same instinct behind prompt chaining: could you describe the task's quality bar in one sentence without the phrase "it depends"? If a wrong answer is merely inconvenient, a single agent is probably fine. If a wrong answer is expensive — a legal document with a wrong claim, marketing copy with an unsupported number, code with a security hole — that's the signal that paying for a second (or third) independent pass is worth it. The mistake to avoid in either direction: don't add agents "because it's more advanced," and don't skip them "to save money" on a task where a real error would cost far more than the extra API calls.

Quick recap
  • Multi-agent systems trade latency and cost for quality — not a free upgrade.
  • Favor a single agent for simple, cheap, fast, or consistency-critical tasks.
  • Favor multi-agent when quality is critical, the task decomposes naturally, and you have budget for it.

6. Building Resilient Multi-Agent Systems

Once you decide multi-agent is the right call, three design questions determine whether the system is genuinely resilient or just a more expensive way to produce the same fragility.

1. Communication protocol

Agents need to understand each other's output format.

communication_protocol.py 
# Good: Structured output
feedback = {
    "clarity_issues": ["Paragraph 2 is confusing"],
    "factual_errors": ["Date of GPT-4 release is wrong"],
    "impact_improvements": ["Add a concrete example"]
}

# Bad: Unstructured
"This is okay but could be better in some ways"

2. Stopping conditions

When does the multi-agent loop end?

stopping_condition.py 
# Example: Stop after feedback converges (no new issues)
previous_feedback = "..."
current_feedback = "..."

if are_similar(previous_feedback, current_feedback):
    print("Feedback converged, stopping.")
else:
    continue_loop()

"Converged" here means the feedback pattern has stabilized — reviewers are no longer surfacing new issues — not that every agent literally agrees on everything. It's a stopping condition for the loop, not a consensus requirement. The Pro Path exercise for this session implements exactly this idea with a similarity-based convergence score.

3. Conflict resolution

When agents disagree, who wins?

conflict_resolution.py 
# Option A: First agent wins
use_agent_a_output()

# Option B: Majority vote (if 3+ agents)
if vote_majority(agents):
    use_majority_output()

# Option C: Human decides
ask_human_to_choose()

None of these three is universally "correct" — the right choice depends on the stakes. For a low-stakes internal tool, first-agent-wins or majority vote is often fine. For a legal or financial system, routing genuine disagreement to a human reviewer is usually the responsible default.

Quick recap
  • Communication protocol: use structured formats (dicts/JSON with named fields), not free-form prose, so agents can reliably parse each other's output.
  • Stopping conditions: define them before building — convergence (feedback stabilizes) is one common approach.
  • Conflict resolution: decide in advance whether disagreement is resolved by first-agent-wins, majority vote, or a human in the loop — and let the stakes of the task drive that choice.

Points to Remember

  • Multi-agent systems trade latency for quality. More agents means more API calls means slower, but potentially much better output.
  • Orchestrator-worker suits decomposable tasks. Debate suits exploring perspectives. Reviewer suits verification.
  • Agents must communicate clearly — use structured formats, not prose, so feedback is unambiguous and parsable.
  • Define stopping conditions before building — know when the loop ends before you write the loop.
  • Cost and latency matter in production. Don't add agents unless they add real value.
  • Test with mocked agents first, before spending real API calls on a system whose structure you haven't verified yet.
