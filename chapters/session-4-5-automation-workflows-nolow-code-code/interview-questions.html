Session 4.5 Interview Prep 10 min read

Interview Questions: Automation vs. Agents

Interviewers use this exact topic to separate candidates who've only ever built one flashy agent demo from candidates who think like systems engineers — people who know that the right answer to "should this be an agent" is often "no." Each question below includes what a strong answer sounds like, common red flags, and a natural follow-up. Click any question to expand it.

1 You're building three systems: (A) a Monday-morning reminder email, (B) a tool that researches a topic and answers questions dynamically, (C) structured-data extraction from PDFs. For each, would you use an agent or simple automation? Why?
Strong answer

(A) Simple automation — no reasoning needed, just schedule an email; an agent here is pure overkill and pure cost. (B) An agent — the topic changes every time, it requires reasoning and tool use (search), which is exactly where agents excel. (C) It depends: a fixed template calls for automation, but variable document structures benefit from an agent's ability to adapt. A strong candidate names the decision framework explicitly: agent if the task is complex, reasoning-heavy, and has variable inputs; automation if it's simple, predictable, and high-frequency (where cost compounds). Bonus points for naming hybrid thinking — simple automation for the scheduling, an agent for the content.

Red flags

"Always use agents" (misses the cost/complexity trade-off entirely), or "agents can't scale" (false — they're just slower and pricier per run, not fundamentally unscalable). Treating all three tasks identically without distinguishing predictability is also a red flag.

Follow-up

"You used an agent for (A) and it costs $1k/month. How do you fix it?" (Strong answer: replace it with a scheduled rule-based job — the reminder email never needed reasoning, so the fix is a pure automation swap, not a cheaper model.)

2 Your agent-based research system costs $0.50 per query and takes 30 seconds across 5 API calls. A user complains it's too slow. Options: (A) a faster model, (B) fewer search iterations, (C) parallelize agent calls, (D) cache results. What do you recommend?
Strong answer

Weigh each option rather than picking one reflexively: (A) a faster model reduces latency but may hurt quality, so test it first; (B) fewer iterations is faster but risks less-thorough research; (C) parallelizing independent calls gives a large speed gain at the same cost, if the underlying tasks are actually independent; (D) caching gives an instant response, but only for repeated queries. A strong candidate ties the recommendation to the actual bottleneck — "is it always slow, or only sometimes" points toward caching vs. parallelizing — and closes with a measurement plan: A/B test the change and track both latency and quality, not latency alone.

Red flags

"Just use a faster model" with no consideration of quality trade-offs, ignoring whether the 5 calls could run in parallel at all, or proposing any fix with no plan to measure whether it actually worked.

Follow-up

"You parallelize and latency drops to 8 seconds, but quality also drops. Why?" (Strong answer: parallel calls likely lost the sequential context each step was building on — e.g. step 3 was supposed to refine step 2's search based on what step 2 found, and that dependency broke when they ran at the same time.)

3 Design an agent that processes incoming emails, categorizes them (urgent, important, low-priority), and automatically drafts responses. Walk through the architecture, what could go wrong, and how you'd test it.
Strong answer

A four-phase pipeline: the LLM reads an email and categorizes it while extracting action items; for urgent emails, it drafts a response; the system decides whether that draft needs human review; a human reviews, approves, and only then does the agent send. A strong candidate names the tool boundaries (read_email, categorize, draft_response, send_email behind an approval gate, flag_for_review) and the safety mechanisms explicitly: human-in-the-loop before any customer-facing send, a confidence threshold that escalates uncertain cases, an audit trail of what the agent did and why, and testing against historical emails with no real sends during development.

Red flags

No human review loop at all (genuinely dangerous for a system that emails real customers), no acknowledgment of what happens when the agent is wrong, or treating this as "just classification" while ignoring the much harder response-generation half of the problem.

Follow-up

"The agent flags everything as urgent. How do you debug and retune it?" (Strong answer: inspect the categorization prompt and a sample of recent classifications, check whether the urgency threshold or keyword rules are too aggressive, and consider whether the simple rule layer — not the agent — should be catching more of these cases before they ever reach the LLM.)

4 A user asks your system to "analyze our Q3 sales performance, compare to competitors, and recommend next-quarter strategy." How would you decompose this as an orchestrator-worker system, and does that decomposition change if you're deciding between automation and an agent for each piece?
Strong answer

Decompose into distinct workers: analyze Q3 sales from the internal database, research competitor Q3 results, and gather market trends/forecasts — each an independently testable sub-task — with an orchestrator that assigns the work, collects each worker's result, and synthesizes a final recommendation. A strong candidate then applies this session's framework to each piece: pulling internal sales numbers from a database is closer to simple automation (a query, not reasoning), while competitor research and trend synthesis genuinely need an agent's reasoning and tool use. They'll also note that independent workers can run in parallel, while workers with real dependencies (recommendation depends on both analyses finishing) can't.

Red flags

"One big agent does everything" (loses the benefit of decomposition and independent testing), treating genuinely dependent tasks as parallel, or failing to define what each worker returns.

Follow-up

"Worker 1 (internal sales) takes 10 seconds and Worker 2 (competitor research) takes 30 seconds. How do you speed the whole thing up?" (Strong answer: if the workers are independent, run them concurrently so total time is bounded by the slower one, ~30s, rather than the sum, ~40s.)

5 How would you debug a hybrid workflow (scheduler → rule → agent → action) that's producing wrong results intermittently?
Strong answer

Don't debug the whole pipeline at once — identify the failure point first: did the scheduler actually trigger, did the simple rule behave as expected, did the agent produce valid output, did the action execute? Then test each component in isolation with mock data (a fixed fake email, a hardcoded "trigger fired" event) rather than re-running the live workflow and guessing. A strong candidate adds that "intermittent" specifically points toward the agent step — LLM output naturally varies run to run — so logging each step's output and cost, and correlating failures with specific input patterns, is what actually isolates the bug rather than a vague sense that "it's flaky."

Red flags

"Just add retries" without investigating the root cause, or debugging by staring at final output alone instead of inspecting intermediate steps.

Follow-up

"You isolate it to the agent step, and the agent is technically returning valid JSON every time, but the category field is sometimes wrong. What now?" (Strong answer: this is now a prompt/quality problem, not a plumbing problem — tighten the categorization prompt, add few-shot examples of edge cases, and check whether the simple rule layer should be catching more of these cases before they reach the agent at all.)

Rapid-Fire Review

Quick recall check — fill in each blank and hit Check.

🎉 5 for 5 — you're ready to talk about automation vs. agents in an interview.

Strategy Tips

  • Cover the "Strong answer" line, answer out loud, then check yourself against it — that's how these are meant to be used for self-testing.
  • Interviewers are listening for a clear decision framework and named trade-offs (cost, latency, accuracy), not a reflexive "agents are the answer" — always be ready to say when automation wins.
  • Pair this set with the full Week 4 interview-questions pool for the tool-use and multi-agent-pattern questions this set doesn't cover.
