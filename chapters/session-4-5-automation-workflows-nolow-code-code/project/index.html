Multi-Step Email Workflow

The Pro-path build for this session — an EmailWorkflow class that runs the full hybrid pipeline from Part 3 of the lesson (monitor → analyze → draft → track) across a batch of emails, recording cost and timing at every step so the workflow's actual economics are visible, not just its output.

What to build

starter.py already contains a working EmailWorkflow class. Run it as-is first, then study how each piece works before taking on the challenges below:

  • simple_monitor() — the free, instant filter: does the email match an urgent pattern at all? If not, it's skipped before any API cost is spent.
  • agent_analyze() — the agent step: sends the email to the model and parses back a JSON object with category, action_items, sentiment, and priority_score.
  • agent_draft_response() — only runs for "urgent"/"important" categories, drafting a short reply.
  • Cost and timing tracking — self.costs accumulates an estimated dollar cost per agent call, and process_email() records wall-clock time per email, both surfaced in the final summary().

Challenges (extend the code)

1 Add a confidence field

Have agent_analyze()'s prompt also ask for a "confidence" field (0.0–1.0) alongside category. This is the same confidence-threshold idea from Pattern 3 (Human-in-Loop) in the lesson — it's the signal a real system would use to decide whether a human needs to look at this one.

2 Resolve rule/agent conflicts

Right now, if simple_monitor() passes an email through, the agent's category is trusted outright. Implement a conflict-resolution rule: if simple_monitor() matched on an urgent keyword but the agent categorizes the email as "normal", which one should win, and why? Pick a rule and justify it in a comment.

3 Add human-in-loop approval

Add a send_draft_for_approval(email, draft) method that simulates emailing a human the draft (print a formatted message is enough), and call it from process_email() whenever a draft is created and the new confidence field (Challenge 1) is below 0.8 — mirroring Pattern 3 from the lesson exactly.

4 Track rule vs. agent accuracy

Add a mechanism to log, for every email that goes through both simple_monitor() and the agent, whether the two would have agreed on urgency. Over a larger batch of emails, this lets you measure how much of the traffic your simple rule alone could safely handle — directly answering the "can the rule catch more cases without calling the agent" cost-optimization question from Part 6 of the lesson.

Why this project matters

The email-triage example in the lesson describes cost and speed for each step in the abstract; this project makes them measured quantities you can actually watch accumulate across a batch, the same way a real production system would track them. self.costs and processing_time aren't decoration — they're the concrete evidence you'd bring to the "should this be hybrid" conversation from Part 6, instead of a guess. And the confidence/human-review challenges connect this project directly back to Pattern 3: a workflow that knows when to trust itself, and when to ask.
