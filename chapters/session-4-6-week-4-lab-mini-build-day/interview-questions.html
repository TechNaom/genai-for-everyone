Session 4.6 Interview Prep 10 min read

Interview Questions: Synthesizing Week 4

This is the last session of Week 4, so these questions draw across the whole week's pool rather than staying narrowly scoped to today's build — the same way a real interviewer, once you've mentioned "I built an agent," will pull on threads from tool calling, multi-agent design, and the agent-vs-automation judgment call all in the same conversation. Each question below includes what a strong answer sounds like, common red flags, and a natural follow-up. Click any question to expand it.

1 Design a multi-step agent that researches a topic and writes a report. How would you structure it, what could go wrong, and how would you debug it?
Strong answer

Name the phase structure explicitly: a planning phase where the agent decides what to search for, an execution phase that loops on calling search tools and reading results, and a synthesis phase where the agent stops calling tools and writes the final report. Mention concrete implementation details: working memory so the agent doesn't forget early findings by the time it drafts, a hard iteration limit as a safety net, and a clear stopping condition (no more tool_use blocks in the response = done). Name real failure modes — infinite loops calling the same tool repeatedly, an early stop that quits with a half-finished report, forgotten context once token limits are hit, or searching for conclusions before gathering the underlying data. For debugging, describe logging every iteration (what tool was called, what came back), printing the plan to sanity-check it, and verifying the stopping condition logic directly.

Red flags

"Just call search tools until you have enough data" with no structure, no mention of working memory or iteration limits, or no debugging plan at all.

Follow-up

"Your agent researches 5 topics but only cites the last 2 in the report. Why?" (Tests whether they think about context/token limits pushing early findings out of the working memory the drafting phase can see.)

2 You're building three systems: (A) a Monday-morning reminder email, (B) a tool that researches a topic and answers questions about it dynamically, (C) structured data extraction from PDFs. For each, would you use an agent or simple automation, and why?
Strong answer

(A) Simple automation — no reasoning is required, it's a scheduled action; an agent here is pure overkill and needless cost. (B) An agent — the topic changes every time, genuinely requires reasoning and tool use, which is exactly where agents earn their cost. (C) It depends: a fixed, predictable template is a job for plain automation, but variable or messy document structures are where an agent's judgment adds real value. The underlying decision framework: reach for an agent when the task is complex, requires reasoning, or has variable inputs; reach for automation when the task is simple, predictable, and high-frequency enough that cost matters. A strong answer is explicit about cost consciousness, not just capability.

Red flags

"Always use agents" (misses the cost/complexity trade-off entirely), or treating all three systems the same way without distinguishing what's actually driving the decision.

Follow-up

"You used an agent for (A) and it costs $1,000/month. How do you fix it?" (Tests whether they'll actually walk back an over-engineered choice, not just defend it.)

3 You're building a system for legal document review. How would you structure it as a multi-agent system, and which pattern (orchestrator-worker, debate, reviewer) would you pick?
Strong answer

The reviewer pattern is the strongest fit here: a writer agent drafts a summary, then separate fact-checker, risk-assessor, and compliance-checker agents each review that draft from their own specialized angle, and the writer synthesizes the feedback. The reasoning matters more than the pattern name: legal work is high-stakes and errors are expensive, so having multiple specialized reviewers catch different categories of mistakes is worth the extra cost and latency in a way it might not be for a low-stakes task. A strong answer also names the practical mechanics — structured feedback (e.g. JSON with categorized error types), a stopping condition based on convergence (review rounds stop once feedback stabilizes), and a plan for what happens when reviewer agents disagree (escalate to a human, don't let the system silently pick a side).

Red flags

"Just use one agent" (misses the entire point of adding review), picking a pattern without justifying why it fits this specific domain, or no answer at all for what happens when reviewers disagree.

Follow-up

"You ran three review rounds and still missed an error. What went wrong?" (Good answers question whether the reviewers were actually checking different things, or all catching the same category of mistake.)

4 Your agent-based research system costs $0.50 per query and takes 30 seconds across 5 API calls. A user says it's too slow. Options: (A) a faster model, (B) fewer search iterations, (C) parallelize the agent calls, (D) cache results. What do you recommend?
Strong answer

Walk through the real trade-off in each option rather than picking one reflexively: a faster model reduces latency but may hurt output quality, so it needs testing first, not blind adoption; fewer iterations is faster but is a direct quality risk, since it means less thorough research; parallelizing independent calls is close to a free win — same total cost, much lower wall-clock time, if the tasks genuinely don't depend on each other; caching is close to free too, but only helps when queries actually repeat. The real answer depends on diagnosis, not a fixed ranking: is the system slow for every query, or only some (points toward caching vs. parallelizing)? Are the five calls sequential because they have to be, or just because no one parallelized them yet? A strong candidate proposes measuring latency and quality with A/B tests before committing to a fix.

Red flags

"Just use a faster model" without weighing the quality trade-off, not noticing that some of the calls might be independently parallelizable, or recommending a fix with no plan to measure whether it actually worked.

Follow-up

"You parallelize and latency drops to 8 seconds, but quality also drops. Why?" (Points toward: parallel calls may have lost access to context that sequential calls built up turn by turn — the same shared-message-history issue this session's research agent depends on.)

5 Design an agent that processes incoming emails, categorizes them by urgency, and drafts responses automatically. Walk through the architecture, what could go wrong, and how you'd test it.
Strong answer

Lay out a phased architecture: the agent reads and categorizes an email and extracts action items, drafts a response for anything urgent, then decides whether that draft needs human review before a human actually approves and sends it. Name concrete tools: read_email, categorize, draft_response, a send_email that sits behind an explicit approval gate, and a flag_for_review for anything the agent isn't confident about. The non-negotiable safety mechanism is a human-in-the-loop step before anything is actually sent — not an afterthought, a hard requirement, exactly the same principle Session 4.5 raised about not automating a step just because you technically can. Also worth naming: a confidence threshold that escalates uncertain cases, an audit trail logging what the agent did and why, and testing against historical emails with sending disabled before ever running live.

Red flags

No human review loop at all (genuinely dangerous for anything email-adjacent), no consideration of what happens when the agent gets it wrong, or treating this as a simple classification problem while glossing over how much can go wrong in the response-generation step specifically.

Follow-up

"The agent flags everything as urgent. How do you debug and retune it?" (Points toward inspecting the categorization prompt and threshold, and checking whether the training/example emails it saw were skewed toward urgent cases.)

Strategy Tips

  • Interviewers will often hand you a live scenario ("design an agent for X") rather than ask you to define terms — practice narrating a phase structure (plan, execute, synthesize) out loud, the same way you'd sketch it on a whiteboard.
  • Cost and safety come up constantly in agent interviews specifically, because agents are more expensive and less predictable than plain automation — always be ready to say when you'd not use one, not just how you'd build one.
  • Pair these with Weeks 1–3's questions for a realistic mixed-topic mock interview as you move further into the program.
