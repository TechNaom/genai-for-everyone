Week 4 · Session 4.6 Capstone ~30–35 min (mostly building)

Week 4 Lab — Mini Build Day

Five sessions taught you what agents are, how they call tools, how they run multi-step plans, how several of them can work together, and when to skip all of that and just automate. Today you build the thing that needed every one of those lessons at once: a real research agent.

On this page 1. System design: what the agent actually needs to do 2. Tools required: what the agent can call 3. The workflow, phase by phase 4. Implementation outline: the ResearchAgent class 5. What makes this real (not a toy demo) 6. Evaluation criteria: judging your own build
For five sessions you've been learning agent concepts one at a time: what an agent even is (4.1), how it decides to call a tool and reads the result back (4.2), how it strings several of those tool calls into a plan — execute — synthesize workflow (4.3), how multiple specialized agents can work together instead of one agent doing everything (4.4), and when reaching for an agent at all is the wrong call compared to a simple automation (4.5). Today none of that is theory. You're building a research agent that takes a topic, plans what to look into, actually goes and looks, weighs what it found, and drafts a structured report with citations — the kind of tool that shows up, in some form, behind a lot of the "AI research assistant" products currently shipping.
Part 1 of 6

1. System design: what the agent actually needs to do

Start with the job, not the code. Someone types a topic — say, "Research the current state of AI regulation across countries" — and expects back something closer to a junior analyst's first draft than a single paragraph. Sketched out, the job looks like a pipeline with four distinct stages, each one handing its output to the next:

the-agents-job.txt 
User Input: "Research the current state of AI regulation across countries"
    ↓
[Agent: Planner]
  → "I need to research: US, EU, UK, China, India regulations"
    ↓
[Agent: Researcher]
  → Search each country's regulations
  → Gather recent news and policy changes
  → Identify key stakeholders
    ↓
[Agent: Analyst]
  → Evaluate which sources are reliable
  → Identify trends and patterns
  → Note conflicting information
    ↓
[Agent: Writer]
  → Draft a structured report with sections:
    - Executive summary
    - Country-by-country breakdown
    - Emerging trends
    - Implications for AI companies
    - Citations
    ↓
Output: Full research report
What is... a capstone build? A capstone build is deliberately the hardest, most integrated project of a unit — not because it introduces new tricks, but because doing it well is impossible without genuinely understanding everything that came before. There's no clever shortcut through a research agent that skips planning, or tool use, or multi-step execution, or the judgment call of when a step should even be automated. Every earlier session becomes a design decision here, not a fact to recite.

Notice the diagram names four roles — Planner, Researcher, Analyst, Writer — but that's a description of responsibilities, not necessarily four separate agent objects. Which brings up the first real architectural decision you have to make.

Single agent, multiple modes — or true multi-agent? Single agent with multiple "modes": one ResearchAgent object that calls the LLM four times in sequence — once per phase — carrying its own running message history forward each time. Simpler to build, easier to debug, and exactly what Session 4.3's multi-step task pattern already taught you.

Multi-agent (an extension worth trying once the core works): a distinct Researcher agent, Analyst agent, and Writer agent, each with its own focused prompt and context — the orchestrator pattern from Session 4.4. This lab starts with the single-agent, multi-turn version, because that's the version that teaches the workflow itself before adding the coordination overhead of multiple agents talking to each other.
Quick recap
  • The job is a four-stage pipeline: plan → research → analyze → draft, each stage feeding the next.
  • Those four stages can be four "modes" of one agent (simpler, multi-turn) or four cooperating agents (an extension, using the 4.4 orchestrator pattern).
  • This lab builds the single-agent, multi-turn version first — the workflow has to work before the coordination overhead is worth adding.
Part 2 of 6

2. Tools required: what the agent can call

Per Session 4.2, an agent's tools are just functions described to the model in a schema — a name, a description, and (usually) a set of arguments — so the model can request one instead of trying to hallucinate the answer from memory. A research agent needs, at minimum, three:

tools.py 
tools = [
    {
        "name": "search_web",
        "description": "Search the web for current information"
    },
    {
        "name": "get_page_content",
        "description": "Get full content from a specific URL"
    },
    {
        "name": "evaluate_source",
        "description": "Evaluate credibility of a source (news org, gov site, academic)"
    }
]

search_web is the obvious one — it's how the agent goes from "I should look into the EU's approach" to actually having text to reason about. get_page_content matters because search results alone are usually just titles and snippets; a serious agent needs to go one level deeper into an actual page when a snippet isn't enough. evaluate_source is the one that's easy to skip and shouldn't be: it's what keeps a government policy page and an anonymous blog post from being treated as equally trustworthy just because both showed up in the results.

Mocked tools, real lessons For this lab, all three tools are mocked — a fixed lookup of realistic canned results instead of a live API call. That's a deliberate choice, not a shortcut taken because real search integration is "too advanced." Mocking lets you build and debug the entire workflow — planning, looping, analyzing, drafting — without waiting on network latency, API keys, or rate limits, and without a flaky live search result silently changing your test output between runs. In production you'd swap in something like SerpAPI or Firecrawl behind the exact same function signature; the agent's reasoning about when and why to search doesn't change at all.
Quick recap
  • Three tools: search_web (find information), get_page_content (go deeper than a snippet), evaluate_source (weigh credibility).
  • Tools are mocked with realistic fixed data for the lab — swap in a real search API later behind the same function signature.
  • Mocking isn't a shortcut around the hard part; it isolates the workflow logic from network flakiness while you build it.
Part 3 of 6

3. The workflow, phase by phase

Here's where the four pipeline stages become four concrete LLM calls, each with its own job and its own prompt.

Phase 1 — Planning (the agent talks to itself first) Before any searching happens, the agent is asked to think through the research itself: what to search for, what would make a source credible for this particular topic, and how the eventual report should be structured. This is the same instinct from Session 4.3 — a plan made before execution starts is what keeps the later searches purposeful instead of scattershot.
phase_1_plan.txt 
LLM Prompt: "You're a research expert. Topic: {user_topic}
Write a detailed plan for researching this. What searches will you do?
What sources matter? How will you structure the report?"

Agent Output: "I'll research:
1. Government policy documents from each country
2. Recent news (last 6 months)
3. Expert analysis from policy organizations
4. Company perspectives
..."
Phase 2 — Execution (the agent actually searches) For each search the plan called for, the same request — call — result — read loop from Session 4.2 repeats: the agent states what it wants to search for, the system calls the (mocked) search tool, the result comes back, and the agent notes what it found before moving to the next search. In a fuller implementation the agent decides for itself when it has "enough" and stops looping — for this lab, the loop runs a fixed, small number of planned searches, which keeps the workflow predictable while you get the rest of the pipeline working.
phase_2_research.txt 
For each planned search:
  1. Agent outputs: "I'll search for: {query}"
  2. System calls: search_tool(query)
  3. System returns: Results
  4. Agent reads and notes: "Found X results. Key info: ..."
  5. Loop until agent says "I have enough information"
Phase 3 — Analysis (the agent evaluates what it found) Raw search results dumped straight into a report would just be a list of unfiltered facts. Before drafting anything, the agent is asked to step back: what are the actual themes across everything it found, where do sources disagree, and which sources deserve more weight? This is the "Analyst" role from the system diagram, and it's the step that turns raw findings into something worth writing about.
phase_3_analyze.txt 
LLM Prompt: "Review what you found. What's reliable? What contradicts?
What are the key trends?"

Agent Output: "Based on searches:
- Most countries moving toward regulation
- Difference between EU (strict) and US (light)
- China/India still developing frameworks
..."
Phase 4 — Drafting (the agent writes the report) Only now — after there's a plan, real findings, and an analysis of those findings — does the agent write the actual deliverable. The report needs a specified structure (executive summary, a section per finding, implications, citations), not just "write something about the topic," for exactly the reason Session 2.4's structured-output lesson keeps resurfacing: a vague ask gets a vague, unpredictable answer.
phase_4_draft.txt 
LLM Prompt: "Write a comprehensive report on {topic} based on your research.
Structure:
- Executive summary
- [Section for each country]
- Key trends
- Implications
- Citations (reference sources you found)"

Agent Output: [Full report with structure]

The detail easy to gloss over: all four phases share one running conversation. The drafting prompt in Phase 4 never repeats the search results verbatim — it relies on the model remembering them from earlier turns in the same message history. Skip that, and Phase 4 is effectively starting from nothing, which is exactly how a report ends up citing sources it never actually looked at.

Quick recap
  • Plan → research → analyze → draft, in that order — each phase is a separate LLM call building on the last.
  • Analysis exists as its own phase so the report is built on themes and credibility judgments, not a raw dump of search results.
  • All four phases share one running message history — that's what lets the final report ground itself in the actual earlier findings instead of hallucinating.
Part 4 of 6

4. Implementation outline: the ResearchAgent class

Putting all four phases into one object makes the shared conversation history concrete: a single self.messages list that every phase appends to and reads from.

research_agent.py 
from anthropic import Anthropic

class ResearchAgent:
    def __init__(self, topic):
        self.topic = topic
        self.client = Anthropic()
        self.model = "claude-3-5-sonnet-20241022"
        self.messages = []
        self.findings = []

    def plan(self):
        """Phase 1: Create research plan"""
        prompt = f"""You're a research expert. Topic: {self.topic}

Write a detailed research plan. What searches will you do?
What sources matter? How will you structure the report?"""

        response = self.call_llm(prompt)
        self.findings.append(("plan", response))
        return response

    def research(self):
        """Phase 2: Execute searches (mocked)"""
        # In real version: agent makes search decisions
        # Here: mock some searches
        searches = self.extract_search_queries_from_plan()

        for query in searches:
            # Mock search (replace with real API)
            results = mock_search(query)
            self.findings.append(("search", query, results))

        return self.findings

    def analyze(self):
        """Phase 3: Analyze findings"""
        findings_text = format_findings_for_analysis(self.findings)

        prompt = f"""Based on your research on {self.topic}:

{findings_text}

What are the key insights? What contradicts? What are the trends?"""

        analysis = self.call_llm(prompt)
        self.findings.append(("analysis", analysis))
        return analysis

    def draft_report(self):
        """Phase 4: Write report"""
        findings_text = format_findings_for_report(self.findings)

        prompt = f"""Write a comprehensive report on {self.topic}.

Base it on this research:
{findings_text}

Structure:
- Executive Summary (2 paragraphs)
- Main Body (section per key finding)
- Key Trends
- Implications
- Citations (reference sources)

Write professional report:"""

        report = self.call_llm(prompt)
        return report

    def call_llm(self, prompt):
        """Call LLM and track messages"""
        self.messages.append({"role": "user", "content": prompt})

        response = self.client.messages.create(
            model=self.model,
            max_tokens=2048,
            messages=self.messages
        )

        result = response.content[0].text
        self.messages.append({"role": "assistant", "content": result})

        return result

    def run(self):
        """Execute full workflow"""
        print("Phase 1: Planning...")
        self.plan()

        print("Phase 2: Researching...")
        self.research()

        print("Phase 3: Analyzing...")
        self.analyze()

        print("Phase 4: Drafting report...")
        report = self.draft_report()

        return report

# Usage
if __name__ == "__main__":
    agent = ResearchAgent("AI regulation trends 2024-2025")
    report = agent.run()

    print("\n" + "="*60)
    print("FINAL REPORT")
    print("="*60)
    print(report)

Two things about this skeleton are worth calling out explicitly, because they're exactly what the exercise scaffold leaves as TODOs for you to fill in yourself. First, call_llm() is the one place message history gets built — every phase routes through it, which is what keeps the four phases talking to the same running conversation rather than four isolated one-off calls. Second, this outline is intentionally light on the actual prompt wording and on how search queries get extracted from the plan — those specifics are the real work, and they're what separates a report that's actually grounded in what was found from one that's just plausible-sounding text.

Thought process: the whole quality of this agent lives in what each phase's prompt actually asks for, not in the plumbing connecting the phases. Before writing the prompts yourself, it's worth asking: what would make Phase 3's analysis genuinely useful to Phase 4, instead of just restating Phase 2's raw search results in different words?

Quick recap
  • call_llm() is the single chokepoint where every phase reads from and writes to one shared conversation history.
  • The skeleton's plumbing (methods, loop, print statements) is the easy part; the specific prompt wording per phase is the actual design work.
  • A useful analysis phase summarizes and evaluates findings — it shouldn't just restate the raw search results in different words.

5. What makes this real (not a toy demo)

It would be easy to build something that technically runs and still feels like a toy — a single prompt that asks the model to "research and write about X" in one shot, with no distinct phases at all. Here's what actually separates this build from that:

Realistic scope
Research takes multiple searches across different angles, not one or two queries that happen to sound related to the topic.
Structured output
The report has real sections — executive summary, body, implications, citations — not one long, rambling paragraph.
Citation tracking
The agent has to reference the sources it actually found during research, rather than inventing plausible-sounding attributions.
Human review
The draft goes to a human before it's treated as final — the same principle Session 4.5 pushed on when deciding whether something should run unattended at all.
Error handling
What happens if a search returns nothing useful? A real system handles that gracefully instead of silently fabricating a result to fill the gap.

Once the core four-phase build works, there's a natural set of extensions that push it closer to something you'd actually trust in production: a second agent that fact-checks the draft before it's shown to anyone, semantic re-ranking layered on top of simple keyword search, caching so the same topic isn't re-researched from scratch every time, persisting the plan/findings/report to a database instead of losing them when the process exits, and versioning so you can track how a report changed as research continued.

Go Deeper: why "mocking is okay" isn't a compromise

It's tempting to feel like mocked search data means you haven't really built the thing yet. That's backwards. The hard, valuable part of this agent isn't the HTTP call to a search API — that's a function swap. The hard part is everything this session actually asks you to design: what makes a good plan, how findings get carried forward faithfully into analysis, how analysis gets carried forward faithfully into a draft, and what the report should do when a search comes back empty. All of that logic is exactly as real with mocked data as with a live API, and testing it against mocked data you fully control is how you catch bugs before they're expensive to debug against a flaky, rate-limited live search response.

Quick recap
  • Realistic scope, real structure, real citations, human review, and graceful error handling are what separate this from a one-shot toy prompt.
  • Fact-checking, re-ranking, caching, persistence, and versioning are the natural next steps toward a production-grade version.
  • Mocked data doesn't make the workflow logic any less real — it's what lets you debug that logic without live-API flakiness getting in the way.

6. Evaluation criteria: judging your own build

When your agent finishes, "it ran without crashing" is a low bar. Ask these instead, the same way you'd critique someone else's system:

  • Does the plan make sense? Does the agent actually understand the topic and what research it needs, or does the plan read as generic filler?
  • Are the searches relevant? Do they actually answer what the plan said it needed, or do they drift off-topic?
  • Is the analysis grounded? Does the agent cite its actual findings, or does it start inventing conclusions that sound plausible but weren't in the research?
  • Is the report structured? Clear sections and a logical flow, or one long undifferentiated block of text?
  • Are the citations accurate? Do they reference sources the agent actually found during research, not sources it's guessing might exist?
  • Is the length reasonable? Roughly 1500–3000 words for a genuinely useful report — long enough to be substantive, not padded to hit a word count.
Structure beats length A focused 1000-word report that actually answers the question beats a rambling 5000-word one that technically covers more ground but forces the reader to dig for the point. If you find yourself padding a draft to hit a target word count, that's usually a sign the analysis phase didn't surface enough real substance to write about — the fix is a better Phase 3, not a longer Phase 4 prompt.
Quick recap
  • Evaluate plan quality, search relevance, analysis grounding, report structure, citation accuracy, and length — not just "did it run."
  • A short, focused, well-grounded report beats a long, padded, ungrounded one every time.
  • If a draft needs padding to hit a word count, the real problem usually lives upstream, in a thin analysis phase.
In the Real World
  • Plan → execute → synthesize is the same backbone behind most shipping "AI research assistant" products in 2026 — the specifics (which search API, how many agents) vary, but the phase structure doesn't.
  • Teams that skip the analysis phase and go straight from raw search results to a drafted report consistently ship reports with weaker citations and more contradictions slipping through unnoticed — the analysis step is cheap insurance against exactly that.
  • "The agent said it, so it must be true" is a common and expensive mistake with research agents specifically, because a confident, well-structured report reads as more trustworthy than it necessarily is — which is exactly why the fact-checking extension (Pro path) matters more here than it might for a lower-stakes tool.

Points to Remember

  • Plans matter. A good plan leads to good research; a vague plan wastes every search that follows it.
  • Search is iterative in a fuller implementation — the agent might search, learn something, and search again based on what it learned, rather than running a fixed list decided up front.
  • Citations ground claims. "According to X" is a meaningfully stronger and more checkable statement than an unsourced assertion.
  • Humans still matter. Even a genuinely good agent benefits from human review before its output is treated as final.
  • Mocking is okay. Don't wait on real APIs to test structure and logic — mock the data first, swap in real integrations once the workflow itself is solid.
  • Structure beats length. A 1000-word focused report outperforms a 5000-word rambling one.
