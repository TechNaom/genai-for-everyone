Session 5.1 Project 25 min build

Regression Testing for Prompts

The Pro-path build for this session. The Core-path exercise scored a single prompt version against a golden dataset. This project is harder: it builds a full regression testing framework that runs two prompt versions against the same dataset and compares them metric by metric — the same discipline from Part 3 of the lesson, now as real, runnable code. And it hides a genuinely fragile metric for you to find and explain.

A note before you start As with the exercise, starter.py and solution.py here are identical — this is a complete, working regression testing framework, not a fill-in-the-blank stub. The work in this project isn't typing in missing code; it's tracing how the framework scores each criterion, then catching the one criterion that's scored in a way that doesn't actually measure what its name claims.
How to run No installation and no API key needed. Download starter.py below and run python starter.py. Both prompt versions are mock functions with canned responses — the point of this project is the comparison and decision logic, not live model output.
starter.py solution.py (reference)

How the framework is built

Trace these four pieces in starter.py:

  • Two mock prompt versions — prompt_v1 (basic, terse responses) and prompt_v2 (longer, more helpful responses) simulate testing two real prompt variants without calling a live model.
  • RegressionTestSuite.score_response — scores a response on whichever criteria a given example asks for: Relevance (does the expected text appear in the actual response?), Accuracy, and Helpfulness (does the response contain action words like "go to" or "email"?).
  • test_prompt — runs every example in the dataset through a given prompt function, scores each one, and averages scores per criterion into a metrics dict.
  • compare_versions and decision — diff the v1 and v2 metrics dicts, label each metric Improved/Regressed/Stable, and recommend PROMOTE, EQUIVALENT, or REJECT based on the overall average.

1 Run it and read the comparison table

Run the file. Confirm you get the same comparison table shown above, and that the decision at the bottom follows from the Overall row — not from the count of improvements vs. regressions alone (notice v2 wins even though it regressed on one metric out of three).

2 Add a new example and re-run

Add at least one new example via suite.add_example(...) using a category and criteria list of your choice, then re-run the file. Confirm your new example shows up in both v1 and v2's runs and shifts the Overall percentages.

Task 3 — Find and explain the fragile Accuracy proxy

Look closely at the Accuracy branch inside score_response:

score_response (excerpt) 
elif criterion == "Accuracy":
    # For this mock, assume accuracy is based on response length (poor proxy!)
    scores[criterion] = min(len(actual) / 100, 1.0)

This literally scores "Accuracy" by counting characters in the response, capped at 100. In the sample run above, Accuracy goes from 90.0 (v1) to 88.0 (v2) — a "regression." But v2's responses are also the more helpful, more correct ones (they include specific settings paths and timeframes v1 doesn't). Explain, in your own words: how can a metric literally named "Accuracy" go down when the responses got more informative and no less correct? What is this proxy actually measuring instead of correctness, and what's one concrete case (a long response that's confidently wrong, or a short one that's perfectly right) where this metric would give you the opposite of the right answer?

Then propose a fix: rewrite the Accuracy branch so it checks something closer to actual correctness rather than length. You don't need to build a full LLM-as-judge (that's Session 5.2) — even a stricter keyword/fact-overlap check against expected would be a real improvement over len(actual) / 100. See README.md for a full worked explanation to compare against.

Why this project matters

The Core-path exercise scored one system against a rubric where every criterion, at least in principle, should measure the thing its name claims. This project makes the failure mode from Part 5 of the lesson — "metrics that don't match goals" — concrete and runnable: a metric literally named Accuracy that has nothing to do with correctness. That's more dangerous than an obviously broken metric, because the regression table above still runs, still prints clean percentages, and still looks like real evaluation. Catching it requires actually reading what a metric computes, not just trusting its label — the same instinct Session 5.2 formalizes when it covers how to choose (and audit) evaluation methods for real.
