Session 5.2 Exercises 25–30 min, hands-on

Exercises: Eval Harness for a Contract-Clause Summarizer

starter.py below is a fully working evaluation harness — not a fill-in-the-blank file. It scores three prompt variants of a contract-clause summarizer using a mocked LLM-judge (with an explicit partial-failure cap) and a mocked semantic-similarity metric, then routes clauses to human review using the chapter's routing rules. Your job is to trace it carefully until you can predict its output from reading the code alone, then extend it with a new test case and a routing-threshold experiment of your own.

Why this one starts pre-solved Real semantic-similarity embeddings and a real LLM judge call both need paid, networked dependencies this exercise deliberately avoids. So mock_semantic_similarity() approximates real embeddings with a small concept-overlap check, calibrated to reproduce the exact same blind spot real embeddings have for this task — it rewards covering the gist even when the one legally significant detail is the part that's missing. Reading working code that reproduces a real blind spot on purpose is the point here, not filling in boilerplate.
How to run it You'll need Python 3 only — no packages, no API key, no network calls. Download starter.py below and run python starter.py. It prints per-clause scores and a per-variant summary for all three prompt variants.
starter.py solution.py (reference)

Part 1 — Trace it before you run it

Open starter.py. Before running anything, work through these three functions by hand for Variant A (concise)'s arb_1 clause — the one that omits the class-action waiver.

1 Predict the semantic similarity score

mock_semantic_similarity() checks four concepts for arb_1: arbitration, not_court, class_action_waiver, and binding_nature. Variant A's summary is "You agree to settle disputes through arbitration instead of court." — which of the four concepts does it actually hit? Work out the fraction by hand before checking the printed output.

2 Predict the LLM-judge score

llm_judge_score() starts from that similarity score scaled to 0–10, then applies the partial-failure cap. OMITS_DETAIL["Variant A (concise)"]["arb_1"] is True. Given the cap rule (min(base_score, 5)), what should the final score be, regardless of how high the raw similarity looked?

3 Predict whether it gets flagged for review

needs_human_review() flags on high-risk clause type, OR an LLM-judge score of 4–7, OR a similarity in the 0.70–0.85 band. arb_1 is type "arbitration" — on that fact alone, does it matter what the other two numbers are? Run python starter.py and confirm all three of your predictions against the printed per-clause line.

Part 2 — Extend it

4 Add a fourth clause designed to hide in the middle band

Add a new entry to GOLDEN_DATASET (a "non_compete" clause type, not currently in HIGH_RISK_TYPES), a reference summary, and one variant's summary for it that deliberately omits a real detail (e.g. drops a specific geographic scope or duration limit). Add matching entries to VARIANT_OUTPUTS and OMITS_DETAIL. Tune the summary's wording until mock_semantic_similarity() lands in the 0.70–0.85 band on its own — then confirm the LLM-judge cap is the thing that actually catches it, not the routing rule's clause-type override (since non_compete isn't flagged as high-risk).

5 Stress-test the routing bands

Temporarily narrow the middle band in needs_human_review() from 0.70–0.85 to 0.78–0.82 and re-run. Does your new non-compete case still get flagged? If not, that's the lesson made concrete: a routing band that's too narrow silently lets exactly the failure type it was designed to catch slip through. Put the band back to 0.70–0.85 when you're done.

🐞 Debug the Code

A teammate "simplifies" llm_judge_score() to this. What real failure mode does it silently reintroduce, and which specific chapter example (Part 2 or Part 3) does it break on?

buggy_judge.py 
def llm_judge_score(summary, reference, omits_detail):
    # "simplified" -- just use the similarity score, scaled up
    return round(mock_semantic_similarity(summary, reference) * 10)

Hint: this deletes the partial-failure cap entirely. Variant A's arb_1 case — the one you traced in Part 1 — would score however high its raw similarity happens to be, with nothing capping it at 5 despite the omitted class-action waiver. This is exactly the ungrounded, too-generous LLM-judge failure mode from Part 2 of the lesson, reintroduced by a "simplification" that looked harmless.

Checking your work Your traced predictions from Part 1 should match the printed output for arb_1 exactly: similarity 0.75 (3 of 4 concepts), LLM-judge capped at 5/10, and flagged — both because it's high-risk and because 0.75 sits in the middle band. For Part 2, your new non-compete case should show a middle-band similarity score with the LLM-judge cap doing the real work of catching it, since clause type alone won't flag it. solution.py is the same fully-worked harness as starter.py — use it to confirm you haven't accidentally changed the base behavior while adding your own extensions.
