Session 5.3 Exercises 30–45 min, hands-on

Exercises: Red-Team the Vulnerable Wiki Assistant

A permission-blind internal wiki search assistant is provided — intentionally vulnerable across all 4 attack vectors from the lesson. Craft test queries, run them, log what gets retrieved per user, and document which ones leak restricted content and to whom. This is the red-teaming discipline from Part 6 of the lesson, made concrete against a real (if small) mock wiki index. This is a pure-Python exercise — no API key or network access required.

How to run this You'll need Python 3 only — no dependencies, no API key. Download starter.py below, then run it from a terminal with python starter.py.
starter.py solution.py (reference)

The task

Open starter.py. It contains a mock wiki index (5 documents, including one poisoned with a hidden "SYSTEM NOTE" and one confidential-by-title-not-space document), a deliberately vulnerable vulnerable_retrieve/vulnerable_answer pipeline, and two functions to complete: check_for_leakage() and run_red_team_suite().

1 Implement the leakage checker

Complete check_for_leakage(result, user) so it detects three distinct failure types from a single result: a permission leak (any retrieved doc from a space this user's access list doesn't include), a sensitivity leak (any retrieved doc whose title matches a sensitive pattern — "confidential," "do not distribute," "layoffs" — regardless of whether the user's access technically permits it), and an injection fired signal (the response mentions "compensation" when the user's own query never asked about salary or compensation, meaning the embedded "SYSTEM NOTE" successfully hijacked the response).

2 Run the full red-team suite

Complete run_red_team_suite() so it runs the 4 provided red-team cases (one per attack vector: permission-blind retrieval, confidential-by-convention bypass, indirect injection, and a simplified single-turn version of context accumulation), calls check_for_leakage() on each, and prints a clear VULNERABLE/SAFE verdict with the retrieved spaces and leakage detail for every case.

🐞 Task 3 — Debug the Code

A teammate wrote this leakage check for the permission leak specifically, but it reports permission_leak = False for the Marketing employee's salary query even though comp_1 (an hr_only document) was clearly retrieved. Find the bug.

buggy_permission_check.py 
# Bug: this checks whether ALL retrieved spaces are outside the user's
# access (using `all`), so it only flags a leak when EVERY single
# retrieved document is restricted. If even one permitted document
# (like the general-space onboarding doc) is retrieved alongside the
# restricted one, `all(...)` becomes False and the leak goes unreported.
#
# Fix: use `any`, not `all` -- a SINGLE retrieved doc outside the
# user's access is already a leak, regardless of what else came back:
#   permission_leak = any(space not in user_access for space in spaces)
permission_leak = all(
    space not in user_access for space in result["retrieved_spaces"]
)
