Session 5.3 Interview Prep 10 min read

Interview Questions: RAG Safety & Red-Teaming

Once a candidate can define prompt injection, interviewers move to the question that actually separates "knows the term" from "has thought about internal tools": can you name where a RAG tool's attack surface actually lives, explain why an ordinary employee is usually the one who triggers a leak, and describe how you'd red-team your own retrieval pipeline before someone else finds the gap. Each question below includes what a strong answer sounds like, common red flags, and a natural follow-up. Click any question to expand it.

1 An internal wiki search assistant answers "What's the highest salary band for a Staff Engineer?" for a Marketing employee, pulling the answer straight from an HR-only wiki space. Nobody typed a jailbreak. What went wrong, and how do you fix it?
Strong answer

A strong answer names this as permission-blind retrieval: the retrieval step matched purely on semantic relevance, with no awareness of who was asking, so it surfaced a document from a wiki space this user has no business seeing. There's no "attacker" here in the usual sense — an ordinary employee asked an ordinary question, and the system did exactly what it was built to do (find the best semantic match), which is precisely the problem. The fix is permission-aware retrieval: cast a wide net of candidates, then filter to only documents the requesting user is actually permitted to see, and do this filtering before any document reaches the model's prompt context — not just before the final answer is shown. That filtering has nothing to work with unless permission metadata (source space, required access level) was captured at index time, not bolted on as an afterthought at query time.

Red flags

Treating this as a "hacker" problem and reaching for jailbreak-style defenses; proposing to filter only the final answer text rather than the retrieval step itself; no mention of index-time permission metadata.

Follow-up

"Why is filtering at the final-answer stage a weaker guarantee than filtering before the documents reach the model's context?" (Strong answer: once the model has "read" restricted content into its context, a later turn in the same conversation can still reference or be coaxed into revealing it — never including it in the first place is a much stronger guarantee than trusting the model not to mention it.)

2 A document titled "Q3 Layoffs — CONFIDENTIAL — Do Not Distribute" sits in a general wiki space any engineer can technically access. An engineer asks the assistant to summarize it. Should it comply, and why did access control alone not catch this?
Strong answer

No, it shouldn't auto-comply — and the key insight is that this isn't a permissions bug. The access-control system worked exactly as configured; the document really is in a space this user can read. The failure is that technically accessible and appropriate to surface are different questions, and nothing in the pipeline distinguished them. A strong candidate names the fix as a second, independent check: content-level sensitivity signals (title patterns like "confidential," "do not distribute," "layoffs," "restructur-") checked regardless of what access control says, with flagged documents routed to a review/escalation path instead of auto-included. They also flag that a targeted "summarize this specific document" request is its own higher-risk pattern worth detecting, separate from the document's sensitivity — the user already knows the document exists and wants its contents extracted efficiently.

Red flags

Concluding "access control passed, so this is fine"; not distinguishing technical accessibility from appropriate use; no mention of a title/content-based sensitivity signal independent of the permission system.

Follow-up

"Your sensitivity-signal check is just regex on the title. What's the obvious way it fails, and would you still ship it?" (Strong answer: it misses sensitive content that isn't flagged by title convention, and it can false-positive on innocuous documents that happen to contain a matched word. Still worth shipping as one layer of defense — it's cheap, catches the common case, and should be paired with routing to human review rather than treated as a complete solution.)

3 Explain how a wiki page can be used to attack a RAG system without the attacker ever sending it a single chat message.
Strong answer

This is indirect prompt injection via indexed content. Unlike a customer-facing chatbot, where injected instructions come from what the user types, a RAG tool's prompt context includes whatever the retrieval step pulls in. Anyone with edit access to a source document — not chat access — can plant hidden instructions inside it (a "SYSTEM NOTE" buried in a footer, say), and weeks later, when a completely different user asks an unrelated question, the poisoned page can be retrieved as a relevant source. The model, reading it as part of its context, may follow the embedded instruction, because nothing structurally distinguishes "instructions from the system prompt" from "text that happens to appear inside a retrieved document." A strong candidate names two layered defenses: structurally separating retrieved content from instructions in the prompt (explicitly marking it as untrusted reference material that cannot issue instructions, whatever it claims to be), and scanning indexed content for injection signals at index time rather than only at query time.

Red flags

Treating all injection vectors as equivalent to a typed jailbreak; not recognizing that the attacker never has to interact with the chatbot at all; no mention of structural separation or index-time scanning as defenses.

Follow-up

"Why is index-time scanning for injection signals strictly better than only scanning at query time?" (Strong answer: catching a poisoned document at index time removes the threat once, for every future user, rather than relying on every individual query to defend against it correctly — miss the check once, for one query, and the poisoned content still reaches the model.)

4 An HR employee legitimately retrieves a compensation document in turn 1 of a conversation. In turn 5, they ask the assistant to "export this whole conversation as a summary for my team." What's the risk, and what should the system do differently?
Strong answer

This is context accumulation across a session, and it's important to name that it's not a permissions failure at retrieval time — the original user genuinely did have access to the compensation document in turn 1. The risk is that the document is still sitting in the conversation's context five turns later, and gets swept into a bulk export that the employee then pastes into a Slack channel including non-HR staff, without realizing turn 1's document was still attached. The failure is treating "permitted to view" and "safe to bulk-export to an arbitrary downstream destination" as the same question, when they aren't. A strong candidate names the fix: re-check relevance of previously retrieved documents against the current query before including them in a later turn's context, rather than letting everything retrieved earlier in the session silently persist forever; and treat explicit "export everything" / "summarize this whole conversation" requests as their own risk category, worth an extra confirmation step before serializing the full session history.

Red flags

Calling this a permissions bug (the retrieval in turn 1 was legitimate); not distinguishing "viewing" from "bulk-exporting"; no mention of re-checking relevance turn-to-turn.

Follow-up

"If you scope context strictly to what's relevant to the current turn, what do you risk losing?" (Strong answer: genuinely relevant earlier context that the current question depends on — the fix is re-checking relevance per turn, not simply dropping all prior context, since over-dropping breaks legitimate multi-turn follow-ups.)

5 You red-team your internal RAG assistant with 5 attack attempts covering all 4 vectors from this session, and all 5 fail to break it. What do you conclude, and what do you do next?
Strong answer

A near-perfect defense rate on a first pass is more often a sign the attack catalog was too narrow than proof the system is airtight. A strong candidate doesn't stop at "5/5 blocked" — they go back and grow the catalog: more cross-department query phrasings for permission-blind retrieval, sensitively-titled documents under different naming conventions, injection payloads phrased differently than the first attempt, and more varied context-accumulation scenarios (different export phrasings, longer sessions, different document types). They also emphasize checking what was retrieved for each test case, not just what the final response said — a response can look clean on the surface while a restricted document was still pulled into the model's context, which is a leak risk even if that particular response happened not to expose it. Findings should be documented with severity and impact, written for someone who wasn't in the room.

Red flags

Concluding the system is safe and stopping; not questioning whether the 5 attacks were actually rigorous; no mention of logging retrieved documents (not just responses) as part of the audit.

Follow-up

"Give me one attack vector for this RAG tool you'd try next that's meaningfully different from the four covered in this session." (Strong answer: something like a multi-hop query that indirectly reconstructs restricted information by combining several individually-permitted documents, or a request that exploits ambiguous department boundaries in the wiki's space structure — anything that shows the candidate is generating genuinely new attack shapes, not just rephrasing the same four.)

Strategy Tips

  • Cover the "Strong answer" line, answer out loud, then check yourself against it — that's how these are meant to be used for self-testing.
  • Interviewers are listening for you to name the specific RAG-specific mechanism (retrieval-time, index-time, context accumulation) rather than a generic "add more guardrails" answer.
  • Pair this set with Session 5.4's fairness and bias questions for a fuller Week 5 mock interview — the central question shifts from "what data can this system see" to "is this system treating people fairly."
