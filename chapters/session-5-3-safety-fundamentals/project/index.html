What to build

Three defense functions in starter.py:

  • 1. scan_for_injection_at_index_time() — scan a document's text for injection signals ("system note," "ignore previous/your instructions," "when summarizing/answering...also") before it's ever allowed into the clean index (Defense 4.2 from the lesson).
  • 2. flag_sensitive_content() — check a document's title for sensitivity signals, independent of its access-control space (Defense 3.1).
  • 3. secured_retrieve() — find candidates via the same keyword overlap as the vulnerable version, filter to only documents the user has access to, then split the permitted set into documents to include normally and documents to flag for review rather than silently including them (Defense 2.1, combined with 3.1).

🐞 Task 3 — Debug the Code

A teammate wrote this simplified version of secured_retrieve, reasoning that checking sensitivity before checking permission is more "defense in depth." It compiles and looks reasonable, but it actually leaks restricted content in a subtle way. What's wrong?

buggy_order_of_checks.py 
# Bug: this checks sensitivity FIRST, across the full candidate list --
# including documents the user has no permission to see at all -- and
# only filters by permission afterward. The sensitivity check itself is
# harmless, but by the time it runs, an HR-only document has already been
# read and inspected as part of building the "flagged" list for a
# non-HR user, and a bug in how flagged/included get merged downstream
# can easily let a document leak into "included" if it happens to not
# match any sensitive title pattern -- even though the user was never
# permitted to see it in the first place. Permission filtering must
# happen FIRST and gate everything downstream, exactly as the lesson's
# Defense 2.1 says -- sensitivity flagging is a second, independent
# check applied to the ALREADY-PERMITTED set, never a replacement for it.
def secured_retrieve_buggy(query, user, index, top_k=3):
    candidates = get_candidates(query, index, top_k * 2)
    flagged = [d for d in candidates if flag_sensitive_content(d)]
    not_flagged = [d for d in candidates if not flag_sensitive_content(d)]
    user_access = USERS[user]["access"]
    included = [d for d in not_flagged if d["space"] in user_access][:top_k]
    return included, flagged

Ideas to make it your own

  • Wire secured_answer() up to an actual LLM call, using the structural-separation prompt pattern from Defense 4.1 (retrieved content in an explicitly-marked untrusted block), instead of the simulated string-concatenation response.
  • Add a real "review queue": instead of just logging flagged documents, write them to a small file or list that a human reviewer would triage, and track how each flagged case was eventually resolved.
  • Extend context-accumulation handling to a genuinely multi-turn version: track a session history across several calls to secured_answer() and re-check relevance of prior retrieved documents against each new turn's query (Defense 5.1), rather than the simplified single-turn version used here.

Why this project matters

A red-team exercise that only finds vulnerabilities is half the job. The harder, more valuable part is building defenses that hold up when re-tested — permission filtering that runs before content ever reaches the model's context, sensitivity signals checked independently of formal access control, and index-time scanning that protects every future user rather than relying on catching a poisoned document at just the right moment. That's the same discipline Session 5.5's guardrails chapter formalizes further: layered defenses, each doing one job, tested and re-tested rather than trusted blindly.
