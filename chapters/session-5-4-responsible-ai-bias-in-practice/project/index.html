Comprehensive Bias Audit Framework

The Pro-path build for this session — a complete audit framework covering all five steps from Part 3 of the lesson (define scope, collect a sample, annotate, calculate metrics, document in a model card), plus parity checking that decides the model card's recommended-use language automatically.

How to run No installation and no API key needed — just Python 3. Download starter.py below and run python starter.py. AuditConfig, ComprehensiveBiasAudit, and all six audit steps are already implemented; the point of this build is understanding how the pieces fit together end to end, then extending the framework through the challenges below.
starter.py solution.py (reference)

What to build

Run starter.py as-is first, read through each of the six methods, then take on these challenges:

  • Challenge 1 — replace the simulated fairness_score metric, currently 0.85 + (hash(group) % 10) / 100, with a deterministic calculation. That line's biggest problem: Python randomizes string hashing per process by default, so this "metric" produces a different number every time you run the script — not something you'd ever want from a real fairness measurement. solution.py derives it from each group's actual annotated-match rate instead.
  • Challenge 2 — add a 4th group (e.g. "asian") to AuditConfig.groups and to the sample data, and confirm calculate_metrics(), check_parity(), and create_model_card() all handle it correctly without any changes to those methods.
  • Challenge 3 — add an export_model_card() method that writes just the model card dict to its own JSON file, separate from the full text report, so it can be shared on its own with a non-technical stakeholder.

How parity checking drives the model card

check_parity() computes the gap between each metric's highest and lowest group, then compares it against a threshold — 5% for accuracy, 10% for representation and other metrics, both configurable on AuditConfig. create_model_card() then reads those parity results directly: any violated metric becomes a listed limitation, and the presence of any violation flips the recommended-use language from "acceptable for medium-stakes decisions" to "not recommended for high-stakes decisions without human review." This is the audit framework's real payoff — a stakeholder-facing recommendation that's derived directly from measured numbers, not from someone's gut feeling about whether the model "seems fine."

Ideas to make it your own

  • Add an equal_opportunity metric (true positive rate per group among cases with a genuinely positive ground-truth label), matching Metric 2 from Part 2 of the lesson.
  • Have collect_sample_data() warn (rather than silently truncate) when a group doesn't have enough source data to reach its target per_group count.
  • Persist every run's full model card to a dated file (e.g. model_card_2026-07-20.json) so you can track whether parity violations improve or worsen over successive audits.

Why this project matters

A bias audit that only prints numbers to a terminal doesn't change anything — the model card is what turns a measurement into a decision a team can actually act on. This framework's real lesson is the connection between the two: parity violations aren't just displayed, they directly determine whether the model card recommends the system for high-stakes use at all. That's the shape of a real production audit process: config in, numbers out, and a stakeholder-facing recommendation that's honestly derived from the numbers rather than asserted separately from them.
