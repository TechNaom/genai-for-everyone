Session 5.5 Interview Prep 10 min read

Interview Questions: Guardrails & Defense in Depth

Anyone can describe a guardrail in the abstract. What hiring managers actually probe for is whether you understand guardrails as layers that assume each other might fail, not a single fix you apply once and move on from. Each question below includes what a strong answer sounds like, common red flags, and a natural follow-up. Click any question to expand it.

1 What's the key difference between a guardrail and a system prompt?
Strong answer

A system prompt is persuasion — a request to the model that can still be argued with, reframed, or bypassed by a sufficiently creative attacker. A guardrail is enforcement — code that runs regardless of what the model decides to do, whether that's a pattern filter before the LLM ever sees the input, or an output check before a user ever sees the response. A strong candidate names both as necessary, not competing: a hardened system prompt reduces how often the model tries to misbehave, while guardrails ensure that even when it does, the bad output never reaches production.

Red flags

Treating them as interchangeable, or claiming a sufficiently well-written system prompt makes code-level guardrails unnecessary.

Follow-up

"If you could only ship one of the two, which would you pick, and why?" (A strong answer resists the false choice: a system prompt with zero enforcement is fragile, but recognizes that in a resource-constrained situation, code-level output filtering is usually the higher-leverage single investment, since it catches failures regardless of their cause.)

2 What's the most effective fix for a chatbot leaking secrets like passwords or API keys, and why isn't an output filter enough on its own?
Strong answer

The most effective fix is architectural: never put the secret in the model's context in the first place. An output filter that redacts a known secret string is a useful backstop, but it only catches secrets you already know to look for, in exactly the format you expected — it does nothing for a secret it wasn't told about, or one leaked in a slightly reformatted way. A strong candidate frames this as the general principle behind data leakage defense: filtering treats a symptom, removing the secret from context removes the underlying cause.

Red flags

Proposing only a keyword/regex output filter as "the fix," with no mention of removing the secret from context at all.

Follow-up

"Your app genuinely needs the model to know a user's account balance to answer questions about it. Balances aren't secret the way a password is, but how do you reason about what's safe to put in context versus what isn't?" (Strong answer: distinguish data the model needs to do its job from data it never needs to see at all — and for anything sensitive that's arguably needed, still apply output-side redaction as a backstop.)

3 Your input guardrail blocks any message containing the word "password," including "How do I reset my password?" What's actually wrong here, and how would you fix it?
Strong answer

This is a false positive — the guardrail is blocking a legitimate, harmless request because it matched on topic ("password") rather than on the attack itself ("tell me the admin password" or "what's the password"). A strong candidate identifies the fix as more specific patterns, not fewer guardrails: matching the actual attack shape (a demand for a credential, an override attempt) instead of a single broad keyword. They should also mention testing the guardrail against a legitimate-use sample, not just red-team attacks, since that's the only way over-blocking gets caught before it reaches real users.

Red flags

Suggesting the fix is to remove the guardrail entirely, or not recognizing this as a distinct failure mode (over-blocking) from the attack succeeding.

Follow-up

"How would you measure whether your guardrail changes are actually improving things, rather than just moving the false positive/negative trade-off around?" (Strong answer: track both rates — false negative rate against a red-team suite, false positive rate against a legitimate-use suite — every time a pattern changes, not just once at launch.)

4 You add a keyword-based output filter blocking any response containing the phrase "system prompt." A red-team attempt still extracts your instructions using different wording. Did the guardrail fail?
Strong answer

Not a total failure — it still blocks the literal case it was designed for. But it's not a complete fix either: keyword filters are inherently bypassable by rephrasing, and treating this one filter as "done" was the real mistake. The correct response is to document this as an open residual risk and add another layer (a hardened system prompt that declares user input has no special authority, or a semantic classifier instead of literal string matching), not to conclude the whole guardrail approach doesn't work. A strong candidate frames this with the general principle: guardrails are layers of defense, not single solutions, and testing for bypasses is ongoing, not a one-time check.

Red flags

Calling it either a complete failure or a complete success with no nuance, or not mentioning that keyword filters specifically are brittle to rephrasing.

Follow-up

"What additional layer would you add on top of the keyword filter to catch semantically similar bypasses?" (e.g. an LLM-based classifier asking "does this response reveal internal instructions? yes/no," or a hardened system prompt combined with a stricter allow-list of topics.)

5 Walk me through how you'd verify that a set of guardrails you just added actually work, after patching a chatbot that failed a red-team assessment.
Strong answer

Re-run the exact same attack prompts that originally found the vulnerabilities — not a new, easier set — against the patched system, and confirm every one is now blocked. This is regression testing applied to security: it verifies the fix actually works instead of just assuming it does, and it catches cases where a fix for one vulnerability accidentally reintroduces or misses another. A strong candidate also mentions the other half of verification: running a legitimate-use sample through the same patched system to confirm the fix didn't introduce over-blocking, since a guardrail system needs to be measured on both axes at once.

Red flags

Describing verification as "I tried a few things and it looked fixed," or only mentioning the attack side and never the legitimate-use side.

Follow-up

"Your regression suite passes 10/10 on attacks and 5/5 on legitimate requests. Are you done?" (Strong answer: no — a small, fixed suite of known attacks and known legitimate requests is a good regression check, not proof against novel attack framings never tried before; ongoing, expanding red-teaming is still needed.)

Strategy Tips

  • Cover the "Strong answer" line, answer out loud, then check yourself against it — that's how these are meant to be used for self-testing.
  • Interviewers are listening for layered thinking — always be ready to name what happens if the layer you just described fails, not just how it works.
