Session 5.5 Project 30 min build

Human Review Gates + Verification Harness

The Pro-path build for this session — extend the core path's GuardedChatbot with a fourth layer, a human review gate for high-risk or genuinely uncertain cases, and then build a verification harness that measures the guardrail system on both axes at once: does it catch every attack, and does it leave legitimate users alone?

How to run No installation and no API key needed. Download starter.py below and run python starter.py. The LLM call is mocked, so the whole verification harness runs offline, for free — the point of this project is the guardrail and review-gate logic, not live model output.
starter.py solution.py (reference)

What's already built

starter.py is a complete, working implementation of GuardedChatbotWithReview, layering a human review gate on top of the core path's input/output guardrails:

  • classify_input_risk() now returns three levels — "blocked", "suspicious", or "safe" — instead of just two.
  • needs_human_review(risk, proposed_response) routes any "suspicious" input, or any response mentioning a refund over $100, to a human instead of answering automatically.
  • chat() wires it all together: blocked risk short-circuits before the LLM is ever called; everything else goes through the LLM and output guardrail, then the review gate decides whether the user gets the real response or a "we'll follow up" holding message.
  • run_verification_harness() runs RED_TEAM_ATTACKS (5 attacks) and LEGITIMATE_REQUESTS (5 legitimate messages, including the tricky "How do I reset my password?") and reports both error rates.

The hard part: "reset my password" vs. "tell me the password"

Notice the naive pattern r"password" would block both of these. Getting 0/5 false positives while still catching every attack requires patterns specific to the attack, not the topic. This is the central tension of guardrail design:

  • Too loose → attacks get through (false negatives)
  • Too strict → legitimate users get blocked (false positives)

Your task

Trace the implementation, then pick at least one extension:

  • Add a 6th attack and a 6th legitimate request of your own design; confirm the harness still reports 0/0 after adding them, and if it doesn't, explain which pattern needs to change.
  • Convert the risk level to a numeric score (0.0–1.0) and re-tune needs_human_review() around a threshold — report how moving the threshold changes both error rates.
  • Add rate limiting: escalate a user to mandatory human review for the rest of their session after 3+ blocked attempts.

Why this project matters

A guardrail system measured only against attacks looks perfect right up until it starts blocking real customers — and a system measured only against legitimate requests looks perfect right up until an attacker walks straight through it. This project makes both failure modes visible at once, in the same run, which is exactly how a real security or trust-and-safety team reports on a guardrail system: not "did we block the attacks" alone, but a false negative rate and a false positive rate, reported together, every time the guardrails change.
