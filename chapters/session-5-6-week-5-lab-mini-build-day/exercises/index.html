Session 5.6 Exercises 60–90 min, hands-on

Exercises: Write the Eval + Safety Report

The capstone for Week 5: a four-section eval + safety report against a mocked policy Q&A bot (a simplified stand-in for the Session 3.6 project). It's the single build that needs golden-dataset scoring (5.1/5.2), red-teaming (5.3), a bias comparison (5.4), and an honest guardrails write-up (5.5) all at once. There's no core/pro split for this session — instead there's one report to build, with a free/open path and an optional paid-API path:

  • Free/open path — the full four-section report against the provided mocked target system. No API key needed.
  • Optional paid-API path — the same report, pointed at your real Session 3.6 or 4.6 project instead of the mock.
How to run this You'll need Python 3 — that's it for the free/open path. Everything in starter.py runs with the standard library; no API key, no pip install of anything beyond what ships with Python. If you'd rather point it at your real Week 3/4 project (which likely calls the Anthropic or OpenAI API), swap mock_target_system() for your real function — the report structure and every method you're implementing stays exactly the same either way.
starter.py solution.py (reference)

1 Build the golden dataset (Section 1)

Find GoldenDataset and implement add_example(), score(), run(), and report(). Add at least 6 examples spanning happy path, edge case, boundary, and safety categories. The vacation-days question is the one most worth including — mock_target_system() has an intentional grounding bug on it, and that failure is worth more in your report than a dozen passing happy-path examples.

2 Run the red-team log (Section 2)

Find RedTeamLog and implement attempt() and report(). Run at least 5 attack attempts: injection via an "injected document," a direct jailbreak, a scope-escape attempt (asking for something outside the bot's scope), an out-of-scope technical question, and a roleplay-framed jailbreak are a solid starting set. For each, record the exact input, the exact output, whether it succeeded, and a severity.

3 Run the bias check (Section 3)

Find BiasCheck and implement compare() and report(). Run at least 2 comparisons — the same underlying question, phrased two different ways that vary only a demographic or framing detail (e.g. "new mothers" vs. "new fathers," or different tenure phrasing for the same policy fact). A single output can't tell you anything about bias; only a matched comparison can.

4 Log a guardrail + residual risk (Section 4)

Find GuardrailLog and implement log() and report(). Log at least one guardrail you'd add in response to whatever sections 2–3 turned up, and the residual risk that remains even after adding it. "Fully fixed, no remaining risk" is almost never the honest answer — say what's still open.

🐞 Task 5 — Read the mock's bugs before you report around them

mock_target_system() has two intentional flaws baked in, and your job is to catch both in your report rather than quietly work around them:

mock_target_system.py 
if injected_document_text and "override" in injected_document_text.lower():
    return f"[unsafe] Following embedded instruction: {injected_document_text}"

if "vacation" in lowered and "2 year" in lowered:
    return "Employees typically get 15-20 days depending on tenure."  # vague, not grounded — intentional bug

Flaw 1: the vacation-days branch never looks at POLICY_FACTS["vacation_2yr"] at all — it always returns a vague, invented range instead of the actual grounded number ("18 days"). That's exactly the RAG hallucination failure mode from Session 3.5, reproduced on purpose so your golden dataset has something real to catch. Flaw 2: any injected document text containing the word "override" gets echoed straight back into the response, unfiltered — the vulnerability your red-team attempt and guardrail entry should target. Neither flaw is something to "fix" in mock_target_system() itself; they're there so your report has genuine findings to write down, the same way a real audit doesn't get to edit the system under test to make its own job easier.

Checking your work There's no automated grader for this exercise, the same way there's no automated grader for a real production safety report. Confirm instead: the golden dataset's score for the vacation-days question actually comes back as a FAIL, the red-team log records the document-injection attempt as HIGH severity (since it leaks injected text directly into the response), the bias check runs at least two genuinely matched comparisons rather than two unrelated questions, and the guardrail entry names a specific residual risk instead of declaring the problem fully solved. Compare against solution.py once you've made a genuine attempt.
Optional extension Once the free/open path runs end to end, the closest thing this session has to a "pro path" is implementing one guardrail as real working code instead of just a description — for example, an output filter function that blocks any response starting with [unsafe] or containing "system override," run against both the unguarded and guarded versions of mock_target_system() so your red-team log shows a measurable before/after instead of just a written plan.
