Interview Questions: Deploying a GenAI Service

These mirror how deployment-readiness questions actually come up in entry-level and early-career GenAI interviews: interviewers are checking whether you understand the difference between "a project that runs" and "a service someone else can safely depend on." Each question below includes what a strong answer sounds like, common red flags, and a natural follow-up. Click any question to expand it.

1 Walk me through what actually changes when you take a working GenAI script and turn it into a deployable service. Does the AI logic itself change?
Strong answer

No, the underlying GenAI logic (the function that calls the model) stays the same. What changes: an entry point that handles requests as they arrive instead of running once and exiting, configuration read from environment variables instead of hard-coded, and secrets read from the environment and never logged or committed. The practical payoff: the same code runs in local, staging, and production environments with different config and secrets, with zero code changes.

Red flags

Thinking deployment requires rewriting the GenAI logic itself, no mention of environment-based configuration, or not distinguishing "runs once" from "handles ongoing requests."

Follow-up

"What's the risk of hard-coding an API key directly in the script, beyond it being visible in source control?" (e.g. it also can't be rotated without a redeploy, and it tends to get accidentally logged or pasted into a bug report.)

2 Your service works fine locally but crashes on the deployed server with KeyError: 'ANTHROPIC_API_KEY' on the very first request. What's the better failure mode, and why?
Strong answer

Fail fast and clearly at startup: check for required environment variables the moment the process boots, and exit immediately with a message like "Missing required env var: ANTHROPIC_API_KEY" rather than letting the first real user request hit an unhandled KeyError deep in the code. A startup check surfaces the problem to whoever is deploying, immediately and unambiguously, instead of surfacing it as a confusing production error in front of a real user.

Red flags

Suggesting a broad try/except around the whole request handler as the fix (that hides the problem, it doesn't surface it), or not distinguishing between "who sees the error" in each failure mode.

Follow-up

"What would you do if there were five required environment variables instead of one?" (e.g. check all of them at startup and report every missing one in a single message, not just the first.)

3 Why is a dedicated /health endpoint useful for a deployed service, separate from the actual functional endpoint(s)?
Strong answer

A /health endpoint gives infrastructure (load balancers, uptime monitors, container orchestrators) a fast, cheap way to check "is this process alive and able to respond" without exercising the full, often expensive LLM-calling logic. Functional endpoints can be down for reasons unrelated to basic process health (e.g. a downstream API outage), so keeping the two checks separate gives a clearer signal about what's actually broken.

Red flags

Suggesting /health should call the real LLM to "really" verify things work — that makes the health check expensive, slow, and dependent on a third party, defeating its purpose.

Follow-up

"Should /health ever return anything other than a flat 'ok'?" (e.g. it can be useful to include the loaded model name or version for debugging, as long as it stays cheap and fast.)

4 A client sends a POST to your /ask endpoint with no body at all. What should happen, and what's the risk if you get this wrong?
Strong answer

The endpoint should return a proper 4xx response (e.g. 400 Bad Request) with a clear, specific error message like {"error": "question is required"} — not crash with an unhandled exception. The risk of getting it wrong is twofold: a raw stack trace is a poor experience for any real client, and it can leak internal implementation details (file paths, library versions, variable names) to whoever sent the request, which is a real information-disclosure concern for a public-facing service.

Red flags

Assuming clients will always send well-formed requests, or treating validation as optional "nice to have" rather than a baseline requirement for anything reachable over a network.

Follow-up

"What other malformed inputs would you want to guard against besides a missing field?" (e.g. wrong data type for a field, an empty string, or a field that's absurdly long.)

5 What's the risk of printing the value of an API key to the server logs for debugging, and what should you do instead?
Strong answer

Logs are often stored, searched, and shared far more widely than people expect — monitoring dashboards, third-party log aggregators, support tickets that include log snippets. A printed API key can leak to anyone with log access, which is effectively as bad as committing it to source control. Instead, log that a key was loaded and is non-empty (a boolean, or its last few characters at most), never the key's actual value.

Red flags

Treating logs as inherently private or low-risk, or not having a concrete alternative for what to log instead.

Follow-up

"How would you rotate a leaked key without downtime?" (e.g. support reading the key from the environment so a redeploy with a new value is all that's needed, no code change.)

🎉 5 for 5 — you're ready to talk about shipping a GenAI service in an interview.

Strategy Tips

  • Cover the "Strong answer" line, answer out loud, then check yourself against it — that's how these are meant to be used for self-testing.
  • Interviewers in this area are checking for operability instincts, not AI trivia — anchor every answer to what happens when a real client sends something unexpected, or when the environment isn't fully configured.
  • It's fine to think out loud ("a missing field should never crash the process, so that needs a 400...") — the reasoning is what's being evaluated, not just the final word.
