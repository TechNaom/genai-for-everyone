From Notebook to Application

Every project so far has run the same way: a script, executed top to bottom, printing a result. This session closes the gap between "it works on my machine" and "other people can actually call it."

On this page 1. The Gap Between a Script and a Service 2. The Three Changes That Make It Real 3. Why Environment Variables, Specifically 4. A Real-World Scenario, Worked Through
Nobody using your product is ever going to type python my_script.py. They're going to hit a URL from a browser, tap a button in an app, or have another service call yours behind the scenes — and something has to be sitting there, running continuously, ready to handle that request the moment it arrives. Every GenAI idea you've built in this program so far — the policy Q&A bot, the research agent, the multi-agent workflow — is a script that runs once and exits. This session is about the specific, surprisingly small set of changes that turn that script into something a hiring manager, a teammate, or a real user can actually call. None of it is new AI knowledge. It's the plain software engineering that most GenAI courses skip — and exactly why it matters when you're the one who has to ship it.
Sub-topic 1 of 4

1. The Gap Between a Script and a Service

Think about how every exercise in this program has actually run. You open a terminal, type python build_rag_pipeline.py, the script loads, calls an LLM once or a few times, prints a result, and the process ends. That's a completely reasonable way to learn and prototype — it's how most GenAI ideas are first proven out, even inside real companies. But it has one property that makes it unusable as a product: it only runs when a human is sitting there to start it, and it stops the moment it's done.

What is... a service, as opposed to a script? A script runs once, top to bottom, and exits. A service is a process that starts once and then stays running, listening for requests, and handling each one as it arrives — the tenth request gets treated exactly like the first, with no human re-launching anything in between. The GenAI logic inside doesn't have to change at all; what changes is how and when that logic gets invoked.

This is the exact gap between a working prototype and something you can put behind a URL. A hiring manager, a teammate on another team, or a real user doesn't have your terminal, your Python environment, or the patience to run a script for you. They need to send a request and get a response — which means something on a server has to already be running, waiting, the whole time.

Where this shows up
  • A demo that only works as "let me share my screen and run this in my terminal" reads as a prototype, not a product.
  • A teammate on the frontend can't import your Python function into their JavaScript app — but they can call a URL from anywhere.
  • The moment more than one person needs to use something at the same time, "run the script" stops being an option entirely.
Quick recap
  • A script runs once and exits; a service starts once and keeps running, handling requests as they arrive.
  • The GenAI logic itself doesn't need to change — only how it gets invoked, from "run at the bottom of a file" to "run inside a request handler."
  • "It works on my machine" and "other people can call it" are two different engineering problems, and closing that gap is this session's whole job.

2. The Three Changes That Make It Real

The gap between "script" and "service" comes down to exactly three changes. None of them touch the AI logic itself — they wrap around it.

Change 1: an entry point that accepts requests, not just runs once Instead of if __name__ == "__main__": running your logic a single time and exiting, you wrap that logic in a function that a web framework calls every time a request comes in. The process itself stays alive between calls — it's the framework's job to keep listening and route each incoming request to the right function.
Change 2: configuration that isn't hard-coded Your model name, temperature, and any other tunable value should be read from environment variables or a config file — not typed directly into the code — so you can change behavior without redeploying anything.
Change 3: secrets that live outside the code Your API key was probably sitting in a variable, or loaded from a .env file, while you were prototyping locally. In a real service, that same pattern extends to how the deployed service gets its secrets: read from the environment, never committed to source control, never printed in logs.

Here's the shape of a minimal service that applies all three changes to a GenAI function you've already written. Notice what's not here: there's no rewrite of the model-calling logic at all.

minimal_service.py 
from flask import Flask, request, jsonify
import os

app = Flask(__name__)
MODEL_NAME = os.environ.get("MODEL_NAME", "claude-3-5-haiku-20241022")

@app.route("/ask", methods=["POST"])
def ask():
    data = request.get_json()
    question = data.get("question", "")
    if not question:
        return jsonify({"error": "question is required"}), 400
    answer = call_llm(question)  # your existing logic, unchanged
    return jsonify({"answer": answer})

if __name__ == "__main__":
    app.run(port=int(os.environ.get("PORT", 5000)))

call_llm() is exactly the function you already wrote in Weeks 1–5. Wrapping it in a route doesn't touch the GenAI logic at all — it just gives the outside world a way to reach it. Notice too that the if not question: check returns a proper error response instead of letting a missing field crash the process with a raw stack trace — a small habit that matters a lot more once real, imperfect clients start calling your service (more on this in Sub-topic 4).

Quick recap
  • Change 1 — an entry point that handles a request each time it's called, not run-once-and-exit.
  • Change 2 — configuration (model name, tunable values) read from the environment, not hard-coded.
  • Change 3 — secrets read from the environment, never committed, never logged.
  • The GenAI logic (call_llm()) stays exactly the same — only the invocation changes.

3. Why Environment Variables, Specifically

It's worth being precise about why this one habit matters so much, because it's easy to wave it off as a style preference. It isn't — it's the single change that separates "a prototype that works for me" from "an operable service."

The problem with hard-coding A hard-coded API key or model name means every change requires editing code and redeploying. Want to test a cheaper model in staging before rolling it out to production? Edit the file, commit, redeploy. Need to rotate a leaked key at 2am? Edit the file, commit, redeploy. Every one of those should be a config change, not a code change.
The fix: read it from the environment An environment variable means the exact same code can point at a different model, a different rate limit, or a staging vs. production API key just by changing how the process is started — no code change, no redeploy. os.environ.get("MODEL_NAME", "claude-3-5-haiku-20241022") reads the variable if it's set, and falls back to a sensible default if it isn't — so local development, staging, and production can all run the identical codebase with different behavior.

Thought process: before asking an AI assistant to scaffold a service like this, an experienced engineer decides the requirements first — which values must come from the environment (model name, API key, port), what the safe defaults should be for local development, and what should happen if a required value is missing entirely (Sub-topic 4 covers failing fast on that last one). Handing an assistant a vague "wrap this in Flask" invites it to hard-code the first model name it sees.

Do not hard-code the model name or any secret anywhere in the code.
Quick recap
  • Hard-coded config means every change requires editing code and redeploying.
  • An environment variable lets the same code run correctly across local, staging, and production with different values, with zero code changes.
  • os.environ.get(name, default) is the pattern: read if set, fall back to a safe default if not.

4. A Real-World Scenario, Worked Through

The setup: A hiring manager asks you to demo your Week 3 RAG project live, over a video call, from your own laptop. You could just run python build_rag_pipeline.py in a terminal and read them the printed output — that's a fine demo of the AI logic. But it reads as a prototype. If instead you can say "here's the same thing running as a service — let me curl it from my phone," you've just demonstrated a materially different, more hireable skill: the same GenAI knowledge, packaged the way it's actually used at a company.

Getting there cleanly means thinking past the happy path. Two failure modes are worth designing for up front, because they're exactly what separates a demo that survives a live audience from one that doesn't:

failure-modes.txt 
Bad request at runtime
  Client sends {} instead of {"question": "..."}
  Without a check      -> raw Python stack trace, 500 error, leaks internals
  With a check          -> 400 Bad Request, {"error": "question is required"}

Missing config at startup
  ANTHROPIC_API_KEY isn't set on the deploy server
  Without a startup check -> works fine... until request #1, then a confusing
                              KeyError deep inside call_llm()
  With a startup check     -> process refuses to start, prints exactly which
                              env var is missing, exits immediately

That second failure mode is worth sitting with. A service that crashes confusingly on its first real request is strictly worse than one that refuses to start at all with a clear message — because the confusing crash happens in front of a real user (or a hiring manager), while the startup failure happens in front of whoever is deploying, immediately and unambiguously. Fail fast and fail clearly is the operating principle: check for required environment variables the moment the process boots, and exit with a specific error message ("Missing required env var: ANTHROPIC_API_KEY") rather than letting the gap surface as a mysterious error three layers deep, minutes or days later.

There's a third piece that becomes relevant the moment this service is actually deployed somewhere: infrastructure — a load balancer, an uptime monitor, a container orchestrator — needs a fast, cheap way to ask "is this process alive at all?" without triggering an expensive LLM call every few seconds. That's what a dedicated /health endpoint is for, separate from your functional /ask endpoint: it answers "is the process up" without depending on whether a downstream API happens to be having a bad day. This is exactly what the Pro path project builds.

In the Real World
  • The AI logic doesn't change when you deploy it — only how it's invoked changes, from a script running once to a service handling requests.
  • Printing a "debug" API key to server logs is nearly as risky as committing it to source control — logs get stored, searched, and shared far more widely than people expect.
  • A confusing crash on request #1 is a worse failure mode than a clear, immediate error at startup — because of who sees each one and when.
Quick recap
  • Validate incoming requests and return proper 4xx errors — never let a malformed request crash the process with a stack trace.
  • Fail fast at startup on missing required configuration, rather than failing confusingly on the first real request.
  • A separate /health endpoint lets infrastructure check "is this alive" without exercising the full, expensive LLM logic.

Points to Remember

  • A script runs once and exits; a service stays running and handles each incoming request as it arrives — that's the entire gap between a prototype and something other people can call.
  • Three changes close the gap, and none of them touch the AI logic: an entry point that handles requests instead of running once, configuration read from the environment instead of hard-coded, and secrets that live outside the code.
  • Environment variables are what let identical code behave differently across local, staging, and production — different models, different secrets, zero code changes.
  • Fail fast and clearly on missing configuration. A confusing crash on request #1 is worse than a clear startup error that surfaces the problem to whoever is deploying.
  • Validate every request and return proper 4xx errors — never let a malformed request reach the client as a raw stack trace.
