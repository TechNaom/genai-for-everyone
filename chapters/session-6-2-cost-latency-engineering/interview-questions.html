Interview Questions: Cost & Latency Engineering

Cost and latency questions show up constantly in mid-to-senior GenAI interviews — interviewers use them to separate people who've shipped something real from people who've only prototyped against a free tier. They're listening for concrete levers (routing, caching, trimming) and a measurement habit, not vague "just optimize it" answers. Each question below includes what a strong answer sounds like, common red flags, and a natural follow-up. Click any question to expand it.

1 Why are output tokens usually priced higher than input tokens, and how does that change how you'd prompt a model when cost matters?
Strong answer

Generating output requires a full forward pass per token, which is more compute-intensive than processing tokens the model was already given as input. The practical implication: constraining requested output length (e.g., "answer in 2 sentences") is a direct, high-leverage cost lever. Bonus points for mentioning model routing (cheap model for simple requests) and prompt caching (for repeated large prefixes) as the other major levers.

Red flags

Not knowing that input and output are priced differently at all, offering no concrete prompting implication, or suggesting "just use a cheaper model everywhere" with no nuance about quality trade-offs.

Follow-up

"When would prompt caching not actually help reduce cost?" (e.g. when requests don't actually share a stable prefix, or when the prefix is short enough that caching overhead isn't worth it.)

2 Your prompt includes a 2,000-token system prompt on every single request, and you make 10,000 requests/day. What technique specifically targets this kind of repeated cost, and how does it help?
Strong answer

Prompt caching. If the same 2,000-token prefix appears in every request, caching lets you pay full price for it once and a much smaller fraction on every subsequent request that reuses that exact prefix — turning a cost that scales with request volume into something close to a one-time cost, with zero quality trade-off since the model still sees identical content.

Red flags

Proposing to simply shorten or remove the system prompt (loses functionality) instead of recognizing caching solves this without any content change, or not recognizing this as a caching problem at all.

Follow-up

"What has to stay true about your prompt structure for caching to actually kick in?" (e.g. the cached portion needs to be identical and typically needs to come first, before the variable per-request content.)

3 A support chatbot routes every request — from "yes/no" simple questions to complex multi-part troubleshooting — to your most expensive model. What's the first optimization you'd investigate, and why?
Strong answer

Model routing — send simple requests (yes/no, short lookups) to a cheaper/smaller model and reserve the expensive model for genuinely complex requests. This is usually the single biggest lever because most real traffic in a support context skews toward simple questions, so most of the expensive-model spend is unnecessary and quality-neutral to redirect.

Red flags

Jumping straight to "switch everything to a cheaper model" without the routing nuance, or not recognizing that traffic distribution (mostly simple requests) is what makes this lever so effective.

Follow-up

"How would you decide the threshold for what counts as 'simple enough' to route to the cheap model?" (e.g. request length, presence of multiple sub-questions, a lightweight classifier, or a confidence/complexity heuristic.)

4 True or false, and why: batch APIs are a good fit for a live customer-facing chat interface.
Strong answer

False. Batch APIs trade turnaround time (minutes to hours) for a steep discount, which is only acceptable for workloads that don't need an instant response — nightly processing, bulk classification, report generation. A live chat interface needs real-time responses, so the latency trade-off batching makes is unacceptable there regardless of the cost savings.

Red flags

Saying "true" or hedging without committing to an answer, or not being able to name a workload where batching would actually make sense.

Follow-up

"Name a real workload in a typical GenAI product where batching would be the right call." (e.g. nightly summarization of the day's support tickets, or re-scoring a golden dataset for a regression check.)

5 A support chatbot handled 500 conversations in week one with no cost concerns. By month two, at 50,000 conversations, finance is asking about a $12,000 bill. What should have been modeled before launch, and why didn't the problem show up in week one?
Strong answer

Cost modeling at expected production scale (not just pilot scale) should have happened before launch — the per-request inefficiencies (oversized prompts, no model routing, no caching) were always present, just invisible at low volume where the total dollar figure looked trivial. Concrete levers to have modeled: model routing, prompt/context trimming, and prompt caching for repeated prefixes. The "surprise" wasn't really sudden; it was a pre-existing inefficiency multiplied by volume.

Red flags

"There's no way to have predicted this" (misses that cost modeling at scale is a standard practice), or naming only one lever without a broader cost analysis.

Follow-up

"Design a cost dashboard you'd want in place from day one to avoid being surprised like this again." (e.g. per-request cost and token counts logged continuously, alerting on daily spend crossing a threshold, broken down by model tier.)

Strategy Tips

  • Cover the "Strong answer" line, answer out loud, then check yourself against it — that's how these are meant to be used for self-testing.
  • Interviewers are listening for concrete levers and a measurement habit, not textbook recall. Anchor every answer to a specific number or scenario when you can.
  • If you don't know an exact figure (like the 3–5x output multiplier), say the direction confidently and note you'd verify the exact number against current provider pricing — that's what a working engineer actually does.
