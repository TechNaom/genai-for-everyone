Session 6.2 Intermediate 20–25 min read

Cost & Latency Engineering

Estimate and reduce the real dollar cost and response time of a GenAI feature — before a surprise bill or a slow demo forces the issue.

On this page 1. Token Economics, in Practice 2. Caching and Batching: Paying Once Instead of Every Time 3. Model Routing: Not Every Request Needs Your Best Model 4. The Core Discipline: Measure Before You Optimize
Week 1 you handled 500 conversations and everyone was thrilled. Month 2, you're at 50,000 conversations, and finance is asking why the API bill is $12,000. Nobody modeled cost at scale before shipping — the inefficiency was there from day one, just invisible at low volume. Every LLM API call has two costs that matter in production: money (you pay per token, in and out) and time (the user waits for tokens to stream back). Both are controllable. Both are usually ignored until they become a problem. This session gives you the four levers that turn "we'll figure it out later" into a number you can defend in a budget meeting before launch, not after.
Sub-topic 1 of 4

1. Token Economics, in Practice

Providers price per million tokens, and input and output are priced separately. Output is usually 3–5x more expensive than input, because generating a token requires the model to run a full forward pass, while reading a token you've already supplied is comparatively cheap compute. That asymmetry isn't a footnote — it should change how you write prompts the moment cost matters.

What is... a token, cost-wise? A token is roughly a sub-word chunk of text (not a whole word, not a single letter). Every provider charges per token, input and output tracked and priced separately. The practical upshot: two prompts of the same "word count" can cost very different amounts depending on how many tokens they actually tokenize into, and a short input that produces a long, unconstrained answer can cost far more than a long input that produces a tight, constrained one.
three-cost-levers.txt 
1. INPUT SIZE     A RAG pipeline stuffing 10 retrieved chunks into every
                   prompt when 3 would do pays for 7 chunks of pure waste,
                   on every single request.

2. OUTPUT LENGTH   "Summarize this" (unconstrained) vs. "Summarize this in
                   one paragraph" can be a 5-10x difference in OUTPUT
                   tokens -- and output tokens are the expensive ones.

3. MODEL CHOICE    A smaller/cheaper model correctly handles a large share
                   of real traffic (simple classification, short replies).
                   Routing only the genuinely hard cases to an expensive
                   model cuts cost with no quality loss on the easy ones.

Why this surprises people
  • Teams instinctively optimize the prompt they can see (the input) and forget the answer they asked for (the output) is priced 3–5x higher per token.
  • "Just give me a summary" with no length constraint is one of the most common silent cost leaks in production GenAI features — the model isn't being wasteful, it's doing exactly what it was asked (nothing).
  • Model choice is the biggest single lever precisely because most real-world traffic skews toward requests a cheap model handles perfectly well.
Quick recap
  • Input and output tokens are priced separately; output usually costs 3–5x more per token because generating is more compute-intensive than reading.
  • Three levers: trim input size (stop over-stuffing context), constrain output length explicitly, and route by model choice.
  • An unconstrained "summarize this" is a cost bug hiding as a phrasing habit.
Sub-topic 2 of 4

2. Caching and Batching: Paying Once Instead of Every Time

Two more levers don't touch what you're asking the model — they change when and how often you pay full price for the same work. They're easy to miss because neither requires rewriting a single prompt.

What is... prompt caching? If many requests share the same prefix — a long system prompt, a large retrieved document, a big set of tool definitions — prompt caching lets you pay full price for that prefix once, then a fraction of the price on every subsequent call that reuses it. This is a pure latency and cost win with no quality trade-off: the model still sees the exact same content, it's just billed and processed more cheaply the second time onward. Always worth checking whether your provider supports it and whether your prompt structure (stable prefix first, variable content last) actually takes advantage of it.
caching-payoff.txt 
2,000-token system prompt, reused on every one of 10,000 requests/day:

  WITHOUT caching:  10,000 x 2,000 tokens billed at full input price
  WITH caching:      2,000 tokens billed once (full price) + 10,000 x 2,000
                      tokens billed at the much cheaper cached-input rate

The prefix didn't get smaller. What changed is how many times you pay
FULL price for content that never changes between requests.
What is... batching? If a workload doesn't need an instant response — nightly report generation, bulk classification of a backlog, re-scoring a golden dataset — batch APIs process requests asynchronously at a steep discount (often around 50%) in exchange for turnaround measured in minutes-to-hours instead of seconds. It's a direct trade: you give up latency to buy a lower price.
The one rule that matters here
  • Never use batch processing for a live chat interface — a user waiting minutes for "hello" is a broken product, not a cost optimization.
  • Always consider it for anything that already runs on a schedule or doesn't have a human staring at a loading spinner: nightly summaries, bulk tagging, backlog re-processing.
  • Caching and batching solve different problems — caching helps a repeated prefix, batching helps a deferrable workload. Most production systems eventually use both, for different parts of the traffic.
Quick recap
  • Prompt caching: pay full price once for a repeated prefix, a fraction of the price on every reuse — a pure win, no quality trade-off.
  • Batching: trade turnaround time (minutes-to-hours) for a steep discount — only for workloads that don't need an instant response.
  • Rule of thumb: caching for repeated prefixes, batching for deferrable workloads, never batching for live chat.
Sub-topic 3 of 4

3. Model Routing: Not Every Request Needs Your Best Model

Picture a support chatbot that routes every request — from a one-word "yes/no" question to a genuinely complex multi-part troubleshooting thread — to your most expensive, highest-quality model. It works. It's also almost always the single biggest unexamined cost lever in a production GenAI system, because most real traffic in a support context skews toward requests a cheaper model handles just as well.

What is... model routing? Model routing means classifying each request by difficulty (length, apparent complexity, task type) and sending it to the cheapest model tier that can handle it correctly — reserving your most expensive model for the genuinely hard cases. It's not "use a worse model everywhere to save money"; it's "use the right-sized model for each request," which is a quality-neutral way to cut spend on the large share of traffic that never needed the expensive model in the first place.
routing-example.txt 
"What are your support hours?"              -> short, simple lookup -> CHEAP model
"Yes, please cancel my subscription."       -> short, simple intent -> CHEAP model
"My API integration started failing after   -> long, multi-part,    -> EXPENSIVE model
 your last deploy, here are three stack        needs real reasoning
 traces and my config, can you help debug
 which of these is the root cause?"

A simple length/complexity threshold routes the first two away from your
most expensive model entirely -- and in a typical support workload, that's
the majority of traffic.
Why this is usually the biggest lever
  • Model choice affects both the input price-per-token and the output price-per-token simultaneously — unlike trimming input, which only touches one side of the bill.
  • Real traffic distributions are usually skewed: most requests are simple, a minority are genuinely hard. Routing exploits that skew directly.
  • This is exactly the strategy the Pro path project in this session asks you to design and measure — a routing threshold, applied to a realistic mixed workload, compared against an "everything to the expensive model" baseline.
Quick recap
  • Model routing sends simple requests to a cheap model and reserves the expensive model for genuinely hard ones — it's quality-neutral, not quality-cutting.
  • It's usually the single biggest cost lever because real traffic skews toward the simple end.
  • The lever works because it affects both input and output pricing at once, for the requests it redirects.
Sub-topic 4 of 4

4. The Core Discipline: Measure Before You Optimize

Every lever above is genuinely useful — and every one of them can backfire if you apply it without a baseline. The single biggest mistake in cost/latency work isn't picking the wrong lever; it's pulling any lever before you know what your system actually costs and where its time actually goes.

What is... measuring before you optimize? Before changing anything, know three numbers per request: tokens in and out, dollar cost, and latency — ideally broken down by where the time goes (network, model inference, your own processing). Without that baseline, "switch to a cheaper model" or "aggressively truncate the prompt" can quietly break quality or correctness in ways nobody notices until a user complains — and you have no way to tell afterward whether your change actually helped, hurt, or did nothing at all.
measure-first.txt 
WITHOUT a baseline:
  "This feels slow, let's switch models."       -> guessing
  "Let's truncate prompts to save money."        -> guessing
  Six weeks later: is it actually cheaper? Faster? Nobody can say for sure.

WITH a baseline (tokens in/out, $/request, latency by stage):
  "Model inference is 80% of latency, not network -- switching models is
   the right lever, not adding a CDN."
  "Medium-tier daily cost is $X; after trimming input tokens it's $Y --
   here's the exact monthly savings, measured, not estimated."

This is also why "optimize before you measure" is a risky habit for experienced engineers specifically — not just beginners. The "obvious" fix (switch to a cheaper model everywhere, truncate aggressively) often looks correct on its face, and experience makes it tempting to skip the measurement step. But skipping it means you're optimizing a guess about where the problem is, and you lose the ability to prove — to yourself, or to finance — that the change actually worked.

Thought process: before asking an AI assistant to help instrument a service for cost/latency measurement, decide the schema first: what gets logged per request (tokens in, tokens out, model used, dollar cost, latency broken into stages), so the assistant builds a measurement tool rather than a vague "add some logging" pass that misses the numbers you actually need for a budget conversation.

Quick recap
  • Measure three numbers per request before touching anything: tokens in/out, dollar cost, and latency broken down by stage.
  • Without a baseline, you can't tell afterward whether an "optimization" actually helped, hurt, or did nothing.
  • This discipline matters most for experienced engineers — the "obvious" fix is exactly the one worth measuring before applying.
In the Real World
  • A support chatbot handling 500 conversations in week one and 50,000 by month two isn't a success story with a side effect — the per-request inefficiencies were there from day one, just invisible at low volume until they multiplied into a $12,000 bill.
  • Cost engineering isn't a nice-to-have optimization pass done after launch; it's the difference between a project that survives its first real month of traffic and one that gets pulled by finance.
  • Teams that model cost and latency at expected production scale before shipping catch the same problems in a spreadsheet instead of in an incident channel.

Points to Remember

  • Output tokens are the expensive ones — usually 3–5x the price of input tokens — so constrain requested output length deliberately instead of hoping the model is terse.
  • Prompt caching turns a repeated large prefix (system prompt, long context) from a recurring per-request cost into a one-time cost, with zero quality trade-off.
  • Batching trades latency for a steep discount — right for deferrable workloads, never right for a live chat interface.
  • Model routing is usually the single biggest cost lever: most real traffic is simple enough for a cheap model, so reserve the expensive model for genuinely hard requests.
  • Measure tokens, cost, and latency per request before optimizing anything — guessing wastes effort on the wrong fix and leaves you unable to prove a change actually helped.
