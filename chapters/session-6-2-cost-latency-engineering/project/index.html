The Routing Strategy

The Pro path build for this session — a routing exercise built directly on Sub-topic 3 of the lesson: given a realistic mixed workload, design a routing strategy that sends simple requests to a cheap model and complex requests to an expensive model, then measure exactly how much it saves against the "everything goes to the expensive model" baseline.

What to build

REQUEST_TYPES models a support chatbot's traffic as four representative request patterns, each with a share of total daily volume and an average input/output token profile — the way real teams actually model production traffic, not one row per request:

workload.txt 
simple_faq                             55% of traffic   150 in /  60 out
order_status_lookup                    20% of traffic   300 in / 100 out
billing_dispute                        15% of traffic   900 in / 250 out
multistep_technical_troubleshooting    10% of traffic  2200 in / 500 out

Fill in six pieces in starter.py:

  • requests_per_day_for_type — a type's share of the 50,000 total daily requests.
  • daily_cost_for_type — dollar cost of serving all of a type's traffic on a given model tier.
  • baseline_cost — the "everything to the expensive model" total.
  • route_tier — the routing rule itself: below a token threshold, route to the cheap tier; otherwise, the expensive one.
  • routed_cost — total daily cost when every type is routed by that rule.
  • print_comparison — the report: which types routed where, baseline vs. routed cost, and the dollar/percent savings.
The habit this trains A threshold of 500 input tokens is a design decision, not a fact — it's the line you draw between "simple enough for the cheap model" and "needs the expensive model." In the example run, 75% of traffic routes to the cheap tier while the remaining 25% (the two harder types) still accounts for a large share of the leftover cost, because those requests also have the longest outputs. That's the real shape of a production routing decision: most traffic is simple, but the hard slice is disproportionately expensive — so routing the easy majority away is what actually moves the bill, and being able to put a real dollar figure on that decision (not just "routing sounds like a good idea") is the skill this project trains.

Ideas to make it your own

  • Add a fifth request type from a workload you've actually seen (at work, in a side project, or a realistic hypothetical) and see how it shifts the optimal threshold.
  • Try several thresholds (solution.py already compares 500 vs. 350 tokens) and look for the point of diminishing returns — where a lower threshold barely improves savings but risks sending genuinely complex requests to the cheap model.
  • Replace the single-number token threshold with a two-signal rule (token count and a boolean like requires_account_lookup) and think through why a length-only threshold is a reasonable first pass but an imperfect proxy for "actually simple."

Why this project matters

Model routing is usually the single biggest cost lever in a production GenAI system precisely because real traffic is skewed: most requests are simple, and a cheap model handles them exactly as well as an expensive one would. The engineering skill isn't just knowing routing exists — it's being able to put a real number on it: given your actual traffic mix, exactly how much does a specific threshold save, and is the trade-off (a small share of borderline requests possibly under-served by the cheap model) worth the dollars it saves? That's the calculation this project makes you actually run instead of estimate.
