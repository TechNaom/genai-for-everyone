Choosing & Switching Models

By now you've called two or three different models across this program. This session turns "which model?" into a deliberate, revisitable engineering decision — and shows you how to build systems that can switch providers without a rewrite.

On this page 1. Closed API vs. Open, Self-Hosted — the Real Trade-off 2. Designing for Switchability: the Adapter Pattern 3. Fallback Strategies 4. A Real-World Scenario, Worked Through
Somewhere around Week 1, you picked a model — probably whichever one your exercises defaulted to — and you've been calling it ever since. That was the right call for getting started. But "which model" is not a decision you make once at project kickoff and forget: the landscape changes constantly (new models ship, prices shift overnight, a provider has an outage at 2 a.m.), and your requirements change too — the model that was "good enough" for a prototype is rarely the right one once real traffic and real budgets show up. This session is about making that decision deliberately, and building systems that can revisit it — switch providers, add a fallback — without tearing your codebase apart to do it.
Sub-topic 1 of 4

1. Closed API vs. Open, Self-Hosted — the Real Trade-off

There are two fundamentally different ways to get a model into your application: pay a provider per request through a closed API (Claude, GPT, Gemini), or download open-weight model files (Llama, Mistral, and others) and run them on infrastructure you control. Neither is universally "better" — they optimize for different things.

What is... a closed API model? A model you call over the network by sending an API key and a prompt. You never see the weights, never host anything, and the provider handles every operational concern — uptime, scaling, security patches, and rolling out improved versions. You pay per token, and the cost scales directly with usage.
What is... an open-weight, self-hosted model? A model whose weights are published and downloadable, which you then run yourself — on your own GPUs, in your own cloud account, behind your own serving stack. You own every operational concern the closed-API provider would otherwise have handled: hosting, scaling, monitoring, and keeping up with new releases yourself.
Closed API (Claude, GPT, Gemini) Open-weight, self-hosted (Llama, Mistral, etc.)
Setup cost Near zero — get an API key, start calling it Real infrastructure work: hosting, a serving framework, scaling
Per-request cost Pay per token, scales directly with usage Fixed infrastructure cost regardless of usage (can undercut per-token pricing at very high, steady volume)
Quality ceiling Usually the strongest available models Competitive, but typically a step behind the best closed models
Data control Data leaves your infrastructure (subject to the provider's policies) Full control — critical for some regulated or sensitive workloads
Operational burden Provider handles uptime, scaling, updates You own uptime, scaling, and staying current with new releases
The default, and when it flips
  • Most teams start on a closed API because the setup cost is near zero — you can be calling a top-tier model within the hour.
  • Teams move to self-hosting only when a specific driver appears: a hard data-residency or compliance requirement, extremely high steady-state volume where the economics flip in self-hosting's favor, or a need for guarantees a third-party API simply can't offer.
  • "Self-hosting is always cheaper" is a myth — it's only cheaper past a volume threshold, and it always costs real operational effort to reach and maintain that threshold.
Quick recap
  • Closed APIs win on setup speed and (usually) quality ceiling; open self-hosted models win on data control and cost at very high steady volume.
  • Most projects default to a closed API and switch only when a specific driver — compliance, volume, or a guarantee — appears.
  • Self-hosting trades a per-token bill for an ongoing operational bill; it isn't automatically cheaper.

2. Designing for Switchability: the Adapter Pattern

Here's the mistake that makes switching painful later: baking a specific provider's API shape directly into your business logic. If forty different functions across your codebase each call anthropic.Anthropic().messages.create(...) directly, then switching providers — or adding a fallback — means finding and editing all forty of them. The fix is a thin layer that sits between your business logic and any specific provider.

What is... an adapter (layer)? A single function (or small module) that every other part of your codebase calls instead of talking to a provider's SDK directly. It hides each provider's specific request/response shape behind one consistent interface, so the rest of your code never needs to know or care which provider is actually being used underneath.
adapter_pattern.py 
def call_model(prompt: str, provider: str = "anthropic") -> str:
    if provider == "anthropic":
        return _call_anthropic(prompt)
    elif provider == "openai":
        return _call_openai(prompt)
    raise ValueError(f"Unknown provider: {provider}")

# Every call site in your business logic calls call_model(prompt) --
# never a provider's SDK directly. Adding a new provider, or falling
# back to one, means adding a function -- not rewriting every call site.

Notice what this buys you: your application code calls call_model(prompt) and never touches a provider-specific request or response shape. Adding a new provider means writing one new _call_<provider> function and one new branch — it does not mean hunting down every place your app talks to a model. This is the exact pattern the Core-path exercise has you build and use to compare providers side by side.

Thought process: the real design decision here isn't the if/elif — it's deciding the return shape before writing any provider-specific code. Every provider function needs to return something with the same keys (text, cost, latency) so the rest of your code, and any comparison logic, can treat every provider identically. Decide that contract first; the branching is the easy part.

Write the prompt you'd give an AI assistant to scaffold this adapter:

Paste your prompt into Claude, ChatGPT, Copilot, or whatever assistant you use, and compare what it builds against the pattern above — does every provider function return the same shape, and does an unknown provider name raise a clear error instead of failing silently?
Show a strong version of this prompt 
Write a Python module with a dictionary PROVIDERS mapping provider names to functions. Each provider function takes a prompt string and returns a dict with exactly the keys "text", "cost", and "latency_ms" -- so every provider's output has the same shape. Then write a single call_model(prompt, provider="...") function that looks up the provider in PROVIDERS and calls it, raising a clear ValueError (naming the unknown provider) if the name isn't found. Do not let any call site touch a provider's internals directly -- everything goes through call_model.
Quick recap
  • An adapter layer is one consistent function your business logic calls, instead of a specific provider's SDK.
  • Adding or swapping a provider becomes "add one function," not "find and rewrite every call site."
  • The design decision that matters most is a consistent return shape across every provider function.
Sub-topic 3 of 4

3. Fallback Strategies

A production system that depends on a single provider with no fallback has a single point of failure it didn't need to have. Once you have an adapter layer, adding a fallback on top of it is cheap — you're just calling a second provider function when the first one raises. There are a few common shapes this takes, and they optimize for different things.

fallback-strategies.txt 
Hard fallback           primary fails/times out -> retry the SAME request against a
                        secondary provider automatically. Optimizes for: preserving
                        quality via a different provider.

Quality-tiered fallback try the best model first; on failure, fall back to a
                        faster/cheaper model rather than failing the request
                        outright. Optimizes for: guaranteeing SOME response, even
                        at a quality trade-off.

Circuit breaker         after N consecutive failures from a provider, stop trying
                        it for a cooldown period instead of adding latency to
                        every request with a doomed retry. Optimizes for: not
                        wasting time/cost hammering a provider that's clearly down.

A hard fallback and a quality-tiered fallback both retry against a second provider — the difference is intent. A hard fallback assumes the secondary provider is roughly interchangeable and just wants the same job done elsewhere. A quality-tiered fallback deliberately accepts a weaker model as the price of getting any answer back rather than an error. A circuit breaker is a different kind of safeguard entirely: it protects you from retrying a provider that's already known to be down, which just adds latency and cost to every request during an outage instead of helping.

hard_fallback.py 
def call_model_with_fallback(prompt, primary, fallback):
    try:
        result = call_model(prompt, provider=primary)
        result["used_provider"] = primary
        return result
    except ConnectionError:
        result = call_model(prompt, provider=fallback)
        result["used_provider"] = f"{fallback} (fallback from {primary})"
        return result

# Logging used_provider on every call is what lets you measure, later,
# how often the fallback actually fires -- exactly what the Pro path
# project for this session has you build and instrument.
Quick recap
  • No fallback = an avoidable single point of failure in production.
  • Hard fallback preserves quality via a second provider; quality-tiered fallback trades quality for guaranteed response; a circuit breaker avoids retrying a provider that's already known to be down.
  • Logging which provider actually served each request is what turns "we have a fallback" into a measurable fallback rate.

4. A Real-World Scenario, Worked Through

The setup: Your team built a feature entirely around one provider's specific API — calls to that SDK are scattered directly through the business logic, because in the early prototype days that felt like the fastest way to ship. Six months later, that provider raises prices sharply. Switching to a cheaper or better-value provider should be simple. Instead, it means touching forty call sites across the codebase, because provider-specific code was never isolated anywhere.

what-it-would-have-cost.txt 
Without an adapter layer (the actual situation):
  - 40 call sites, each hand-written against the old provider's SDK
  - Every one has to be found, read, and rewritten by hand
  - High risk of missing one, or introducing a subtle bug mid-rewrite
  - Real engineering cost: days to weeks, plus a nervous rollout

With an adapter layer (decided on in Week 6, not month 7):
  - 1 new _call_<new_provider> function
  - 1 changed default in call_model()
  - 40 call sites: untouched, because they only ever called call_model()
  - Real engineering cost: under an hour, and a much calmer rollout

Notice what actually changed between the two columns: not the number of places the model gets called from — that's still forty. What changed is whether provider-specific knowledge was isolated in one place or smeared across forty. That's the entire value of the adapter pattern, made concrete: it converts an expensive, risky, codebase-wide rewrite into a single, contained, low-risk change.

This is also exactly the situation a fallback strategy protects you from in the moment, rather than six months later: if that same provider had a 20-minute outage instead of a price hike, a hard fallback wired through the same adapter would have kept requests succeeding — served by a secondary provider — without a single user-facing error, and without anyone touching code during the incident.

Quick recap
  • The cost of skipping an adapter layer doesn't show up on day one — it shows up the day you need to switch or add a fallback, at the worst possible time.
  • An adapter layer converts "rewrite forty call sites" into "add one function."
  • The same layer that makes switching cheap also makes a fallback cheap — they're the same investment.
In the Real World
  • Model pricing and rankings shift often enough that "which model" is treated as a recurring engineering review, not a one-time kickoff decision, at teams that operate GenAI features at scale.
  • Regulated industries (healthcare, finance, government) frequently choose self-hosted open models specifically for data-residency reasons, even when a closed API scores higher on quality benchmarks.
  • Teams that shipped an adapter layer early describe provider price hikes and outages as "a one-function change" or "we didn't even notice" — teams that didn't describe them as fire drills.

Points to Remember

  • Closed APIs win on setup speed; self-hosted open models win on data control and cost at very high, steady volume — most projects start closed and switch only when a specific driver appears.
  • An adapter layer between your business logic and any specific provider's API is what makes switching — or adding a fallback — cheap later instead of a codebase-wide rewrite.
  • A single-provider system without a fallback has an avoidable single point of failure.
  • Hard fallback, quality-tiered fallback, and circuit breaker are different tools: preserving quality via a second provider, guaranteeing some response at a quality cost, and avoiding wasted retries against a provider that's known to be down, respectively.
  • Model choice isn't a one-time decision — revisit it as the landscape (new models, prices, outages) and your own requirements both change.
