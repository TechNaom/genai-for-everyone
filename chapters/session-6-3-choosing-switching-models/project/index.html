Session 6.3 Project 25 min build

The Fallback Rate Monitor

The Pro path build for this session — on top of the adapter layer from the exercises, implement a fallback wrapper that catches a simulated provider outage, auto-retries against a fallback, and logs which path was used so you can measure how often the fallback actually fires.

How to run Download starter.py below and run python starter.py. No API key and no internet access needed — the primary provider's outage is simulated in-process with random, so this is a fully offline, deterministic-enough-to-grade exercise.
starter.py solution.py (reference)

What to build

Two mocked providers are already defined for you: primary (stronger, but simulates a 25% outage rate by raising ConnectionError) and secondary (always available, a little weaker/cheaper). Fill in three functions:

  • call_model(prompt, provider) — the same adapter pattern from the lesson: look up the provider function and call it, raising a clear ValueError for an unrecognized name.
  • call_model_with_fallback(prompt, primary, fallback) — call primary; if it raises ConnectionError, automatically retry against fallback. Tag the result with used_provider, and append a record to CALL_LOG either way.
  • measure_fallback_rate(n_calls) — fire n_calls requests through call_model_with_fallback, then use CALL_LOG to report the count and percentage that actually needed the fallback.
The habit this trains A fallback that exists in code but is never measured is a fallback nobody actually trusts in production — when someone asks "how often does this actually kick in?", the honest answer should come from a log, not a guess. Tagging every response with used_provider and accumulating that into CALL_LOG is the small habit that turns a reliability claim ("we have automatic failover") into an observable fact you could put on a dashboard.

Ideas to make it your own

  • Change _call_primary's simulated outage rate and re-run measure_fallback_rate — confirm the measured rate tracks the change.
  • Add a third provider and a tiered fallback that tries primary, then secondary, then a last-resort tertiary provider, logging the full chain attempted.
  • Add a basic circuit breaker: after 3 consecutive primary failures, skip calling primary for the next 5 calls and go straight to the fallback — then measure how much that changes total latency across a batch.

Why this project matters

A fallback wrapper is easy to write and easy to leave completely untested in the one situation that matters: a real outage. The value here isn't the try/except — it's the discipline of logging which path served every request, so "our fallback works" is something you can prove with a number instead of assert with confidence. That's the same discipline that lets a team say, during a real incident, "yes, the fallback is handling it, here's the rate" instead of hoping quietly that it is.
