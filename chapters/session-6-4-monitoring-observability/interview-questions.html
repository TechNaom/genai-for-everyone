Session 6.4 Interview Prep 10 min read

Interview Questions: Monitoring & Observability

These mirror how real intermediate-to-advanced GenAI interviews probe production readiness: not "can you build it," but "do you know what happens to it after it ships." Interviewers are listening for whether you treat drift, logging, and feedback as part of "done" — not optional polish added after something breaks. Each question below includes what a strong answer sounds like, common red flags, and a natural follow-up. Click any question to expand it.

1 What's the minimum set of information you'd log for every GenAI request, and why each field earns its place?
Strong answer

Input (redacted if sensitive), output, model/version, token counts, latency, cost, and any downstream signal (feedback, retry, abandonment). A strong answer ties each field to a specific question it later answers — latency answers "was this slow," tokens/cost answer "was this expensive," model/version answers "did something change underneath us."

Red flags

"Log everything" with no reasoning about why, or omitting model/version (which is what lets you catch a silent provider-side change).

Follow-up

"Your logs contain raw user input. What's the risk, and how do you mitigate it?" (data-leak surface; redact/hash sensitive fields, restrict access.)

2 A RAG-based support bot's underlying policy documents get updated, but nobody rebuilds the vector index. Three weeks later, customers are complaining about wrong answers. What went wrong, and what should have caught it sooner?
Strong answer

This is retrieval drift: the source of truth changed while the system (retrieval logic, index) stayed the same. What should have caught it sooner: periodic re-scoring of a golden dataset against the live system, or a feedback mechanism (thumbs up/down) surfacing real failures within hours instead of weeks. Critically, this isn't a code bug — the system worked exactly as built; the world around it changed.

Red flags

Treating this as a bug in the retrieval code, or proposing no ongoing monitoring process — only a one-time fix.

Follow-up

"Design a lightweight process for keeping a RAG index's freshness in check going forward." (e.g. re-score on a schedule or trigger a re-index whenever source documents change.)

3 Your team re-runs the golden dataset weekly and it always scores above your 80% threshold. Is that enough to say the system isn't drifting? Why or why not?
Strong answer

Not by itself. A fixed threshold check only tells you whether today's score clears a bar — it can miss a system that's sliding from 98% to 82%, still "passing" every week while getting steadily worse. The stronger design compares each run against the previous run (a trend line), which surfaces a slide long before it crosses the absolute threshold.

Red flags

Saying "yes, that's enough" without questioning what a fixed threshold can hide, or not distinguishing a snapshot from a trend.

Follow-up

"What would you log alongside each drift check run to make that trend visible later?" (timestamp, pass rate, dataset version, model/version.)

4 Why is a simple thumbs-up/thumbs-down button disproportionately valuable compared to its implementation cost?
Strong answer

It's cheap to build (one button plus logging the input/output pair with the vote) but produces a continuous stream of real, labeled examples of what's actually failing for real users — exactly the kind of high-signal data that's expensive to generate any other way. It also directly feeds back into growing the golden dataset, closing the loop from production reality back to evaluation.

Red flags

Dismissing feedback data as "too noisy to be useful," or not connecting it back to the eval dataset at all.

Follow-up

"A user downvotes a technically correct answer because it was too long. Does that undermine the feedback signal?" (No — it's a lead to investigate, not a ground-truth label; the value is in aggregate patterns and concrete failure examples, not treating every vote as infallible.)

5 What's the practical difference between evaluating a system once before launch and monitoring it continuously after launch?
Strong answer

Evaluating once before launch tells you the system was good at a single point in time, against examples you thought to include. Monitoring continuously after launch catches degradation caused by real-world drift — new user patterns, silent provider changes, stale data — that a one-time pre-launch eval literally cannot see, because those changes hadn't happened yet when the eval ran.

Red flags

Treating a passing pre-launch eval as a permanent guarantee, or not being able to name a concrete way the world can change after launch.

Follow-up

"If you could only add one monitoring mechanism to a system with no observability at all today, which would you pick first, and why?" (Usually structured logging — everything else, including drift checks and feedback analysis, depends on having logs to work from.)

Rapid-Fire Review

Quick recall check — fill in each blank and hit Check.

🎉 5 for 5 — you're ready to talk about monitoring and drift in an interview.

Strategy Tips

  • Cover the "Strong answer" line, answer out loud, then check yourself against it — that's how these are meant to be used for self-testing.
  • Interviewers are listening for whether you treat observability as part of "done," not a bolt-on after an incident. Say so explicitly if it's true of how you'd actually build.
  • When asked about drift, always name a concrete example (a model alias update, a stale document, a shifted user pattern) — abstract definitions alone read as memorized, not understood.
