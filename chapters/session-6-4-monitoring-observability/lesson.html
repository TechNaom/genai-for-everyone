Session 6.4 Intermediate 20–25 min read

Monitoring & Observability

Session 5.1–5.2 taught you to evaluate before shipping. This session is the same discipline, continued after shipping — because a system that scored 95% in testing can quietly get worse in production without a single alert firing, unless you built the visibility in.

On this page 1. The Minimum Bar: What to Log, and Why "Feels Worse" Isn't a Fact 2. Drift: Why a System That Never Changed Can Still Get Worse 3. The Feedback Loop: Your Cheapest Source of Real Labels 4. A Real-World Scenario, Worked Through
Three weeks ago, a support chatbot started giving worse answers. Nobody built it wrong — the code hasn't changed since launch. What changed is the world around it: the company updated its return policy, and nobody rebuilt the retrieval index behind the bot. Customers noticed before anyone on the team did. That gap — between "something broke" and "someone on the team knew" — is exactly what this session closes. Shipping a GenAI feature isn't the finish line; it's the point where a different kind of work starts, the kind where you can no longer see the system directly and have to build instruments that tell you what's actually happening to real users, in real time, without you standing there watching every request.

1. The Minimum Bar: What to Log, and Why "Feels Worse" Isn't a Fact

Imagine someone on your team says, in a stand-up, "I think the bot got worse last week." Without logs, that sentence is a vibe — unfalsifiable, un-investigatable, and impossible to act on with any confidence. With logs, it's a question you can actually answer: pull last week's requests, compare latency and error rate against the week before, look at what users actually asked. The entire value of monitoring comes down to this one shift: turning "I think" into "I checked."

What is... structured logging? Structured logging means every request produces a log entry in a consistent, machine-readable shape — the same fields, every time — rather than free-form text messages that a human has to parse by eye. A consistent shape is what lets you aggregate: compute an average, count errors, filter by date, without writing a fragile text parser first.

For every request to a GenAI feature, logging the following is the minimum bar:

minimum-log-fields.txt 
input          the prompt/user input  (redact anything sensitive -- see 5.3-5.5;
                                        a log file is still a data-leak surface)
output         the model's response
model/version  which model + version actually served this request
tokens         input_tokens, output_tokens (feeds directly into cost tracking)
latency        how long the request took, end to end
cost           token counts x pricing, or your platform's reported cost
signal         any downstream feedback you have: thumbs up/down, retry, abandon

Notice what this list is not: it isn't "log everything you can think of." It's a deliberately minimal set, chosen because each field answers a specific investigation question later — "was this slow?" (latency), "was this expensive?" (tokens/cost), "did the model change underneath us?" (model/version), "did the user actually like this?" (signal). Skip a field and you lose the ability to answer that one question, permanently, for every request logged before you added it back.

The Week 5 concern that follows you here
  • Logs are a data-leak surface, not a neutral debugging tool — the same sensitive-data risks from Session 5.3 apply directly to whatever you write to disk.
  • Redact or hash sensitive fields before logging, restrict who can read log storage, and never log anything you wouldn't want exposed if that storage were compromised.
  • "We need visibility" is not a license to log raw, unredacted user input forever — the two goals (observability and data minimization) have to be designed together, not traded off by accident.
Quick recap
  • Minimum log fields per request: input (redacted), output, model/version, tokens, latency, cost, and any downstream signal.
  • Structured logging means a consistent, machine-readable shape every time — that consistency is what makes aggregation possible.
  • Without logs, "it got worse" is a feeling. With logs, it's a question you can actually answer.

2. Drift: Why a System That Never Changed Can Still Get Worse

Here's the counterintuitive part: your code doesn't have to change for quality to degrade in production. Nobody touched a line of the retrieval logic, nobody redeployed the prompt, and the golden dataset from Session 5.1 still scores exactly the way it did on launch day — and the system can still be quietly getting worse for real users, right now. This is drift, and it's one of the least intuitive ideas in this whole program precisely because "nothing changed" and "it broke" feel like they should be contradictory.

What is... drift? Drift is quality degradation that happens because the world around your system changed, not because your system did. A golden dataset score is a snapshot — accurate the day you measured it, not a permanent guarantee. Three flavors show up constantly in GenAI systems:
three-flavors-of-drift.txt 
Input drift        the questions users actually ask shift over time
                    (new product launch, new policy, new slang) -- your
                    golden dataset from launch day never anticipated them

Silent upstream     your provider updates a model version behind an alias
change              you're already using, and its behavior shifts slightly
                    -- you didn't request the change, it just happened

Retrieval drift     (RAG systems) the underlying documents get updated or
                    removed, and retrieval that used to work now returns
                    stale or missing chunks -- the index is the thing that
                    went stale, not the retrieval code

Notice the common thread across all three: in every case, the code you wrote still runs exactly as designed. There's no exception, no stack trace, no failed test. The retrieval function still returns the top-k most similar chunks — it's just that "most similar" among stale documents isn't "most correct" anymore. This is exactly why drift is dangerous: it produces no error signal at all. A crash gets noticed in minutes. Drift gets noticed in weeks, because everything downstream looks like it's working.

The fix: treat your golden dataset as a recurring check, not a one-time gate Monitoring for drift means periodically re-running your golden dataset in production — or a representative sample of real traffic scored the same way — and watching the trend line, not just checking it once at launch. A single re-score tells you today's number. A trend line tells you whether today's number is the start of a slide.
Go Deeper: why can't you just re-run the golden dataset once a year and call it done?

Because the interval matters as much as the check itself. A RAG index backing a fast-moving policy area (pricing, compliance, product specs) can go stale in days, not months — re-checking annually would let three or four full drift cycles pass unnoticed. The right cadence is a judgment call based on how fast the underlying world actually changes for your system: a slow-moving reference bot might genuinely be fine checked monthly, while a bot fielding questions about an active incident or a just-launched product needs something closer to daily, or event-triggered (re-check whenever the source documents change at all).

Quick recap
  • Drift = quality degradation caused by the world changing, not your code — input patterns shift, models update silently, retrieved documents go stale.
  • Drift produces no error signal by design — the code runs fine, which is exactly why it goes unnoticed for so long.
  • The fix is a recurring re-score of your golden dataset against a trend line, not a single check-once-and-forget at launch.

3. The Feedback Loop: Your Cheapest Source of Real Labels

Your golden dataset is built from examples you thought to include. Real users will always ask things you didn't anticipate — that's not a failure of imagination, it's just what happens once a system meets an open-ended population of people with their own goals. The question is how you find out which of those unanticipated questions are getting bad answers, cheaply and continuously, instead of waiting for a support ticket to escalate.

What is... the feedback loop? A simple thumbs-up/thumbs-down button on every response, logged alongside the input/output pair, is disproportionately valuable relative to how little it costs to build. It's the cheapest mechanism available for generating a continuous stream of real, labeled examples of what's actually failing for actual users — not synthetic test cases, not your best guess at edge cases, but genuine production failures with a human judgment already attached.
Why this closes the loop back to Session 5.1
  • A thumbs-down, logged with its input/output pair, is a candidate for next month's golden dataset — the exact failure mode a real user hit, not a hypothetical one.
  • This is how a golden dataset stays alive instead of going stale itself: it grows from production reality, not just from the team's imagination at launch time.
  • One button, wired to one log entry, turns every user interaction into a potential training signal for your evaluation suite — without asking users to do anything more than a single click.

It's worth being honest about the limits, too: thumbs-down tells you that something failed, not always precisely why — a user might downvote a technically correct answer because it was too long, or upvote a subtly wrong one because it sounded confident. Feedback is a signal to investigate, not a ground-truth label to trust blindly. The Pro path in this session's exercise builds exactly this mechanism: a feedback endpoint that logs a request ID alongside a thumbs up/down, ready to feed a future eval dataset.

Quick recap
  • Thumbs-up/thumbs-down, logged with the input/output pair, is the cheapest continuous source of real, labeled production failures.
  • It closes the loop back to Session 5.1: today's feedback becomes next month's golden dataset additions.
  • Feedback is a signal to investigate, not a ground-truth label — treat a downvote as a lead, not a verdict.

4. A Real-World Scenario, Worked Through

The setup: a support chatbot answers employee questions about company policy, grounded via RAG over a set of internal documents. It launched with a 95% pass rate on its golden dataset and shipped without incident. Two months later, the company updates its return policy. The document that describes the new policy gets uploaded to the internal wiki — but nobody rebuilds the vector index the chatbot retrieves from. The chatbot keeps confidently answering with the old policy, word for word, because that's still what's in its index.

timeline-of-a-silent-failure.txt 
Week 0   Policy updated on the wiki. Vector index NOT rebuilt.
         Code: unchanged. Retrieval logic: unchanged. Golden dataset score: still 95%
         (it was never re-run against the new policy).

Week 1   A handful of employees get the old answer. No alerts fire --
         there's no exception, no failed request, nothing a normal
         health check would catch.

Week 3   Complaints reach a manager. Someone finally manually tests the
         bot against the new policy and finds it confidently wrong.

Week 3   Root cause found: retrieval drift. The index is the thing that
(fix)    went stale, not the code. Rebuilding it fixes the bot immediately.

Two mechanisms from this session would have caught this on day one instead of week three. First, a scheduled re-score of the golden dataset (including a new case built from the updated policy) against the live index — a re-run the same week the policy changed would have shown the pass rate drop immediately, long before any employee got a wrong answer. Second, a feedback button: the very first employee to get the stale answer could have flagged it with one click, surfacing the problem in hours instead of weeks — and it would have arrived as a concrete, labeled example your eval suite could immediately absorb.

Thought process: the instinct to reach for first, before any code, is deciding what the drift-check function actually needs to report: a pass rate against a threshold, compared to the previous run, not just a single absolute number. A drift check that only says "73% pass rate" tells you less than one that says "73%, down from 95% last week" — the trend is the signal, not the snapshot. Before asking an AI assistant to build this, decide that comparison is the point.

Write the prompt you'd give an AI assistant to build this:

Paste your prompt into Claude, ChatGPT, Copilot, or whatever assistant you use, and compare what it builds against this lesson's example — does it compare against the previous run, or just against a fixed threshold? That comparison is the real test.
Show a strong version of this prompt 
Write a Python function check_drift(score_fn, threshold=0.8) that re-scores a fixed GOLDEN_DATASET (a list of {"input", "expected"} dicts) using score_fn(input, expected) -> bool for each item. Compute the pass rate as passed/total. Print the pass rate alongside the threshold, and return True if pass_rate >= threshold else False, printing a clear warning if it's below threshold. Keep it dependency-free and easy to call on a schedule (e.g. from a cron job or a manual command) without needing a real API key to test.

The single highest-leverage decision in this scenario wasn't a code fix — it was deciding, months earlier, that "re-run the golden dataset periodically" and "add a one-click feedback button" were both worth building before launch, not after the first embarrassing complaint. Observability isn't something you bolt on once something breaks; the projects that get it right treat it as part of "done," the same way tests are part of "done" for regular software.

Quick recap
  • Retrieval drift produces zero errors — the code runs perfectly, the index is just stale relative to a world that moved on.
  • A scheduled golden-dataset re-score and a one-click feedback button both would have caught this on day one instead of week three.
  • A drift check should report a trend (vs. the last run), not just a snapshot against a fixed threshold.
In the Real World
  • "The bot got worse last week" is a sentence engineering teams hear constantly — and without logs, it's genuinely un-investigatable, which is why structured logging is treated as table stakes, not a nice-to-have.
  • Real incident postmortems for GenAI systems disproportionately trace back to drift, not bugs: a model alias update, a stale document, a shift in what users actually ask — none of which show up as a failing test.
  • Teams that ship a feedback button on day one consistently build stronger eval datasets six months later than teams that only rely on the golden set they wrote at launch.

Points to Remember

  • Log input, output, model/version, tokens, latency, and cost for every request — this is the minimum bar for turning "I think it got worse" into a fact you can investigate.
  • Logs are a data-leak surface — redact sensitive fields before writing them, the same discipline as Session 5.3.
  • Drift is quality degradation with no code change: input patterns shift, providers silently update models, retrieved documents go stale — and none of it triggers an error.
  • Re-run your golden dataset periodically in production and watch the trend line, not just a single pass/fail snapshot at launch.
  • A cheap thumbs-up/thumbs-down feedback loop is one of the highest-value additions to a shipped GenAI feature — it directly feeds your next eval dataset, closing the loop back to Week 5.
