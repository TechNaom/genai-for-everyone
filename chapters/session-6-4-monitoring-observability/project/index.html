Session 6.4 Project 30 min build

Feedback Loop + Drift Check

The Pro path build for this session — extend a small Flask service (same shape as Session 6.1) with a POST /feedback endpoint and a drift check that re-scores a golden dataset and flags a pass-rate drop against the previous check, not just a fixed absolute threshold. Fully offline: the mock LLM call is grounded in an in-memory knowledge base, so nothing here needs an API key or network access.

Example run

Terminal 
$ curl -X POST http://localhost:5000/ask -H "Content-Type: application/json" \
    -d '{"question": "remote work policy"}'
{"answer": "hybrid, 3 days in office", "request_id": "7c1e2f3a-9b41-4d6e-8c2a-1f0d5e7b6a9c"}

$ curl http://localhost:5000/drift
{"drifted": false, "message": "First run -- baseline recorded, nothing to compare against yet.", "pass_rate": 1.0}

$ curl -X POST http://localhost:5000/simulate-policy-update
{"message": "Simulated a stale knowledge base entry. Call /drift again."}

$ curl http://localhost:5000/drift
{"drifted": true, "message": "DRIFT DETECTED: pass rate dropped 33 points since the last check (100% -> 67%).", "pass_rate": 0.667}
How to run Install Flask (pip install flask), download starter.py below, then run python starter.py. It starts a local server on port 5000. No API key, no internet access needed — call_llm() is a mock grounded in an in-memory knowledge base.
starter.py solution.py (reference)

What to build

/ask, /stats, and call_llm are already implemented — they're the same structured-logging pattern from this session's exercises, given to you as the foundation. Two pieces are left for you to build:

1 POST /feedback

Read request_id (a string that must match a request already logged by /ask) and thumbs_up (a bool) from the JSON body. Validate both — missing, malformed, or unmatched input should return a 400 with a clear JSON error, never a crash. On success, append the record to FEEDBACK_LOG and return it with a 200.

2 check_drift(threshold=0.15)

Re-score every item in GOLDEN_DATASET against the live KNOWLEDGE_BASE using score_fn, and compute the pass rate. Append it to DRIFT_HISTORY. Compare against the entry before the one you just added (if there is one) — flag drifted=True if the pass rate dropped by more than threshold since that previous check. The first-ever run has nothing to compare against, so it just records a baseline.

Why compare to the last run, not just a fixed threshold A fixed threshold alone (say, "flag if pass rate < 80%") can hide a system that's steadily sliding: 98% one week, 84% the next, both still technically "passing," while something is clearly degrading. Comparing each check to the one before it catches the trend — the thing you actually want visibility into. A real production system typically keeps both: an absolute floor you never want to cross, and a relative-drop check that catches a slide long before it reaches that floor.

/simulate-policy-update is a demo-only endpoint that corrupts one entry in the in-memory knowledge base — standing in for a retrieval index nobody rebuilt after a real policy changed. Call /drift before and after to watch your own drift check catch exactly the scenario from this session's lesson.

Ideas to make it your own

  • Add a /feedback/summary endpoint reporting the thumbs-up rate overall and per logged request.
  • Persist REQUEST_LOG, FEEDBACK_LOG, and DRIFT_HISTORY to a file so they survive a restart instead of resetting every run.
  • Read DRIFT_DROP_THRESHOLD from an environment variable instead of hard-coding it — the same environment-based configuration habit from Session 6.1.

Why this project matters

A feedback button and a drift check are two of the cheapest, highest-leverage additions you can make to a shipped GenAI feature — and the reason most teams skip them isn't that they're hard to build (as this project shows, it's under a hundred lines each), it's that "observability" doesn't feel urgent until the first silent failure costs three weeks of unnoticed bad answers. Building both here, offline, with no excuse of "we didn't have time for the API setup," is the point: there's no infrastructure reason not to have this in every shipped feature from day one.
