Interview Questions: CI/CD & Versioning for Prompts

Deployment- and MLOps-track interviews increasingly probe whether a candidate treats prompts as production artifacts, not throwaway text. Interviewers say they're listening for the same rigor you'd apply to a code change — versioning, review, automated gates, a rollback plan — not just familiarity with the words "CI/CD." Each question below includes what a strong answer sounds like, common red flags, and a natural follow-up. Click any question to expand it.

1 Why should a CI regression check for a prompt change compare the new score to a baseline, rather than just checking it against a fixed absolute threshold?
Strong answer

A fixed threshold alone can't detect a regression — a new version could clear the bar while still being meaningfully worse than what it's replacing. Comparing to the last known-good baseline specifically catches relative degradation, which is the actual thing the gate needs to prevent. A strong answer also mentions that both the prompt and the golden dataset should be versioned together so baseline comparisons stay meaningful over time.

Red flags

Not seeing the difference between an absolute threshold and a baseline comparison, or no mention of versioning the golden dataset alongside the prompts.

Follow-up

"A prompt change passes the CI gate but a real production issue shows up two weeks later on a case the golden dataset didn't cover. Whose fault is that, and what should happen next?" (Not really anyone's "fault" — it's an expected gap; the fix is folding the new failure case into the golden dataset, per the Session 6.4 feedback loop.)

2 What's the difference between a regression check that runs in CI and one that runs at service startup? What does the startup check catch that CI alone would miss?
Strong answer

CI-time checks only fire when a change goes through the normal pull-request pipeline. Startup-time checks run every time the service process boots, regardless of how it got into that state. A concrete example strengthens the answer: a manual deploy that skips CI, or an environment variable/prompt version set incorrectly at the infrastructure level — both invisible to CI but caught at boot.

Red flags

Treating the two as redundant or equivalent, or being unable to give a concrete scenario where only the startup check would catch the problem.

Follow-up

"What should the service do if the startup regression check fails — and why is refusing to start better than starting anyway with a warning?" (Refusing to start prevents a known-bad version from ever serving real traffic; a warning that's easy to miss doesn't.)

3 A regression is caught in production, not CI. What's the fastest safe first response, and why isn't investigating the root cause the first step?
Strong answer

Roll back to the last known-good prompt version immediately — exactly like reverting a bad code deploy. Investigating root cause first leaves the broken behavior live in production for however long the investigation takes; rolling back first stops user impact immediately and buys time to investigate safely, without the clock running against real customers.

Red flags

Jumping straight to "let's figure out what went wrong" as the first move, or not recognizing that rollback and root-cause investigation can (and should) happen in that order, not simultaneously as the first action.

Follow-up

"What has to be true about how prompts are versioned for that rollback to take thirty seconds instead of an hour?" (Versions need to be named/tagged explicitly, not silently overwritten in place.)

4 Why should prompts live as their own versioned files instead of inline strings scattered across a codebase?
Strong answer

Standalone files make prompt changes visible as readable diffs, give them their own commit history, and let them go through the same pull-request review as any other behavior-changing code. It also prevents the quiet failure mode where different services — or different teammates — are each running a slightly different, untracked copy of "the same" prompt.

Red flags

Treating prompt text as fundamentally different from code because "it's just words," or missing the duplication/drift risk of inline strings copied across files.

Follow-up

"Your team has the same prompt hardcoded in three microservices. How would you fix that, structurally?" (Centralize it into one versioned source — a shared file, package, or config service — that all three services read from.)

5 Why does non-determinism in LLM outputs not prevent you from building an automated pass/fail check for a prompt change?
Strong answer

Non-determinism means you can't check for exact output equality the way a typical unit test does. But you can still score behavior against a rubric or golden dataset (Session 5.1/5.2) and compare that score to a baseline — which is exactly what a regression gate does. The gate doesn't need identical output every run; it needs the aggregate score to stay within an acceptable range of the baseline.

Red flags

Concluding that automated testing "doesn't really work" for LLM behavior, or not distinguishing between exact-match testing and score-based regression testing.

Follow-up

"How would you set the threshold_drop for a regression gate on a customer-facing bot versus an internal tool? Should they be the same?" (No — customer-facing surfaces usually warrant a tighter threshold given higher blast radius.)

Strategy Tips

  • Cover the "Strong answer" line, answer out loud, then check yourself against it — that's how these are meant to be used for self-testing.
  • Interviewers are listening for trade-off reasoning and concrete examples, not textbook recall. Anchor every answer to a real scenario: a specific threshold, a specific rollback timeline, a specific file layout.
  • If you're not sure, reason out loud from the code-analogy: "this is like a unit test suite, except..." — that's exactly the framing interviewers are checking for.
