Session 6.6 Exercises 45–60 min, hands-on

Exercises: Build the Week 6 Lab Service

Combine everything from Week 6 into one deployable Flask project: a service wrapper, request logging, a /health endpoint, a provider-fallback adapter, and a startup-time regression gate. The scaffold marks every place that integrates this week's concepts with a # TODO — and everything mocks the underlying model calls, so the whole lab runs and is gradeable with no API key or hosting account.

How to run these You'll need Python 3.10+ installed (check with python3 --version), plus pip install flask. Download starter.py below and run it with python3 starter.py. Once the two Pro-path functions are implemented, the service starts on port 5000 (override with PORT=8080) — call it with curl or a browser form.
starter.py solution.py (reference)

What each Week 6 session hands you here

This lab was chosen specifically because building it well touches almost everything from the week. Each earlier session shows up as a concrete piece of the same running process:

Session 6.1 — service wrapper
The Flask app itself — already scaffolded for you — with an /ask endpoint that handles ongoing requests and reads PORT from the environment rather than hard-coding it.
Session 6.2 — cost and latency awareness
The /ask endpoint times every call and returns latency_ms in its response, the same measurement discipline from 6.2 applied per-request.
Session 6.3 — provider adapter with fallback
call_model_with_fallback() — yours to implement in Task 1: call the primary, retry the secondary only on a genuine connection failure.
Session 6.4 — logging, stats, and feedback
REQUEST_LOG and /health — every request's input, output, and latency captured; a cheap liveness check that doesn't exercise the full model-calling path.
Session 6.5 — CI/CD and regression gates
run_regression_check() against GOLDEN_DATASET — yours to implement in Task 2, then wired into the startup sequence itself for the Pro path.

The tasks

1 Core path — the fallback adapter

Find call_model_with_fallback() and its # TODO. Call _call_primary(question); if it raises ConnectionError, call _call_fallback(question) instead and return that result. The caller (and the eventual end user) should never know or care which provider actually answered.

2 Core path — wire up /ask

Find the # TODO inside the ask() view function. Validate that the incoming JSON body has a non-empty "question" field (return a 400 with a clear error if not), call call_model_with_fallback(), time the call, append {"input", "output", "latency_ms"} to REQUEST_LOG, and return the answer and latency as JSON. /health is already implemented for you — it reports the count of requests served, without ever calling the model.

3 Core path — write DEPLOY.md

Write a DEPLOY.md that a stranger could follow in under 5 minutes: required environment variables (there are none for the mocked version — say so explicitly), the exact start command, and how to verify the service is healthy (the /health curl call). This file is itself part of the deliverable, not an afterthought — see README.md in this folder for what a strong one looks like.

4 Pro path — the regression check

Find run_regression_check() and its # TODO. Run every example in GOLDEN_DATASET through call_model_with_fallback(), score each one (a simple substring check — does the expected fragment appear in the output — is fine for this mocked lab), compute the pass rate, print it, and return True only if the pass rate is at or above REGRESSION_THRESHOLD.

5 Pro path — make it a startup gate

The ##__main__## block already calls run_regression_check() before app.run() and exits non-zero if it fails — that part is done for you. Your job is to prove it actually works: temporarily lower REGRESSION_THRESHOLD past what your implementation can hit (or make _call_primary always raise), run the service, and confirm it refuses to start with a clear FATAL message instead of opening a port anyway. Then restore the threshold and confirm it starts normally.

🐞 Task 6 — Debug the Code

A teammate's fallback silently swallows every failure, not just connection problems — which means a real bug inside _call_primary gets hidden behind a fallback answer instead of surfacing. Find the bug and fix it so only ConnectionError triggers the fallback; anything else should still raise.

buggy_fallback.py 
def call_model_with_fallback(question):
    try:
        return _call_primary(question)
    except Exception:               # too broad -- hides real bugs, not just outages
        return _call_fallback(question)

Hint: the fallback should only trigger on the specific, known-recoverable failure — a network-level ConnectionError — not on every possible exception _call_primary could ever raise.

Checking your work There's no automated grader — that's intentional. Run python3 starter.py and confirm the service starts, that curl http://localhost:5000/health reports "status": "ok", and that curl -X POST http://localhost:5000/ask -d '{"question": "vacation days after 2 years"}' -H "Content-Type: application/json" returns an answer with a latency. Compare your implementation against solution.py once you've given every task a genuine attempt — proving the startup gate actually refuses to start on a failing score (Task 5) is the part most worth doing yourself, not reading about.
Pro path: extend it Once everything passes with the mocked providers, swap _call_primary for a real API call (see Session 6.1's example) and set ANTHROPIC_API_KEY. Then, optionally, deploy the service to a free tier of Render, Railway, Fly.io, or PythonAnywhere for a real public URL — and update your DEPLOY.md to reflect the real deployment steps you actually followed, not the ones you assumed would work.
