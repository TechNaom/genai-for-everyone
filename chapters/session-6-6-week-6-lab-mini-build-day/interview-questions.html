Session 6.6 Interview Prep 10 min read

Interview Questions: Synthesizing Week 6

These are scenario-based questions that pull together everything from Week 6 — deployment, cost economics, provider fallback, monitoring, and CI/CD regression gates — the kind an interviewer uses to check whether you can reason about a GenAI service as a system that has to stay up, not just describe each technique in isolation. Each question below includes what a strong answer sounds like, common red flags, and a natural follow-up. Click any question to expand it.

1 A support chatbot handled 500 conversations in week one with no cost concerns. By month two, at 50,000 conversations, finance is asking about a $12,000 bill. What should have been modeled before launch, and why didn't the problem show up in week one?
Strong answer

Cost modeling at expected production scale — not just pilot scale — should have happened before launch. The per-request inefficiencies (an oversized prompt, no model routing, no caching) were always present; they were just invisible when volume was low enough that the total bill looked negligible. Concrete levers to have modeled and to fix now: model routing (route simple requests to a cheaper model), trimming redundant context, and prompt caching for repeated prefixes. The "surprise" wasn't sudden at all — it was a pre-existing per-request inefficiency multiplied by a 100x volume increase.

Red flags

"There's no way to have predicted this" (misses that cost-at-scale modeling is standard practice), or naming only one lever ("just use a cheaper model everywhere") without broader analysis of where the spend is actually going.

Follow-up

"Design a cost dashboard you'd want in place from day one to avoid being surprised like this again." (e.g. cost per conversation, token breakdown by request type, alerting on week-over-week spend growth rather than only a monthly total.)

2 Your codebase calls a specific provider's SDK directly in 40 different files. What's the risk, and how would you fix it — and how does that fix make a fallback strategy cheap later?
Strong answer

The risk: switching providers, adding a fallback, or upgrading the SDK requires finding and changing all 40 call sites — slow, error-prone, and easy to miss one. The fix is an adapter layer: a single function or module wrapping provider calls, so business logic always calls one consistent interface regardless of which provider is actually behind it. Once that abstraction exists, adding a fallback is a small, localized change inside the adapter (try primary, catch its specific failure, retry secondary) instead of a 40-file migration — the adapter is exactly what makes Session 6.3's fallback design cheap to introduce.

Red flags

Proposing "rewrite all 40 files" as the fix instead of introducing an abstraction, or not connecting the adapter layer to how it later enables a fallback strategy.

Follow-up

"Design the function signature for that adapter layer." (Strong answers keep it provider-agnostic: a question/context in, a plain string or structured answer out, with provider-specific details fully hidden inside.)

3 You've built a fallback: if the primary provider times out, retry against a secondary model. In production, the primary is experiencing intermittent slowness (not full outages), and 15% of requests are triggering the fallback unnecessarily. What's wrong, and how would you fix it?
Strong answer

The fallback's trigger condition — a per-request timeout — is too sensitive to transient slowness that isn't a genuine failure. A fix: use a more tolerant timeout, or better, a circuit-breaker pattern that only engages the fallback after a sustained run of failures rather than reacting to every single slow request independently. The trade-off to name explicitly: falling back too eagerly means serving users a weaker model far more often than necessary, which has its own quality cost.

Red flags

"The fallback is working as designed, no issue here" (misses that 15% is clearly excessive for intermittent slowness), or no concrete fix proposed beyond "increase the timeout" with no mention of a circuit breaker as the more robust option.

Follow-up

"How would a circuit breaker specifically prevent this compared to a per-request timeout retry?" (It tracks failure rate over a window and trips once, instead of re-deciding independently on every single request.)

4 What's the difference between a regression check that runs in CI and one that runs at service startup? What does the startup check catch that CI alone would miss?
Strong answer

A CI-time check only fires when a change goes through the normal pull-request pipeline. A startup-time check re-runs the same check every time the service process boots, regardless of how it got into that state. Concrete example a CI check would miss entirely: a manual deploy that skips CI, or an environment variable/prompt version set incorrectly at the infrastructure level — both invisible to CI, both caught the moment the process tries to boot with a startup gate in place.

Red flags

Treating the two as redundant or equivalent, or being unable to give a concrete scenario where only the startup check would actually catch the problem.

Follow-up

"What should the service do if the startup regression check fails — and why is refusing to start better than starting anyway with a warning?" (Refusing to start fails loudly and gets noticed immediately; starting anyway risks silently serving degraded answers for days before anyone notices.)

5 Your service passes its regression gate, but then a red-team-style failure appears in production that the golden dataset never covered. Is this a failure of the Week 6 deployment pipeline? Explain.
Strong answer

Not strictly a Week 6 pipeline failure. A regression gate can only catch what's represented in the golden dataset, and by definition a genuinely new failure mode wasn't in it yet — that's not a bug in the gate, it's an inherent coverage limit of any fixed test set. This is exactly why the Session 6.4 monitoring and feedback loop exists: to catch failures the golden dataset didn't anticipate, and feed them back in as new golden dataset examples, so the regression gate catches this specific failure mode the next time a related prompt change is proposed. The gate and the monitoring loop are two different layers of the same defense, not one system that should have caught everything alone.

Red flags

A flat "yes, the pipeline failed" or "no, nothing's wrong" without explaining the golden-dataset coverage limitation, or not mentioning the feedback loop as the mechanism that should close this gap going forward.

Follow-up

"Who owns the process of turning a real production failure into a new golden dataset entry, and how often should that happen?" (Strong answers propose a recurring cadence, not an ad hoc "whenever someone remembers.")

Strategy Tips

  • Listen for provider-independence in your own answers: describe "production-ready" as a set of properties, not a specific cloud host.
  • For cost questions, reach for concrete levers — routing, trimming, caching — rather than a vague "optimize it."
  • For gate-design questions, narrate the sequence out loud ("first I'd check whether this is a chunking-style coverage gap or a genuine regression") — interviewers are listening for the reasoning path, not just the eventual right answer.
