Sub-topic 1 of 5

1. The build: one deployable project, five pieces

Today's lab doesn't introduce a single new concept. It's an integration exercise, on purpose — and integration is its own skill, distinct from knowing each piece in isolation. Here's exactly what each earlier session hands you, and where it lands in today's build:

Session 6.1 — service wrapper
The Flask app itself: an /ask endpoint that handles requests as they arrive instead of running once and exiting, with configuration (like PORT) read from the environment rather than hard-coded.
Session 6.2 — cost and latency awareness
The instinct to measure, not guess: today's /ask endpoint times every call and returns latency_ms alongside the answer, the same measurement discipline from 6.2 applied at the request level instead of the notebook level.
Session 6.3 — provider adapter with fallback
call_model_with_fallback() — try the primary provider, and if it raises a connection error, transparently retry against a secondary. The caller never has to know which one actually answered.
Session 6.4 — logging, stats, and feedback
REQUEST_LOG and the /health endpoint — every request's input, output, and latency captured, plus a cheap way for infrastructure to check the process is alive without exercising the full model-calling path.
Session 6.5 — CI/CD and regression gates
run_regression_check() and GOLDEN_DATASET — the same pass-rate-against-a-threshold logic from 6.5, moved from a CI script into the service's own startup sequence.
What is... an integration lab? An integration lab doesn't test whether you can implement any one technique — you already proved that five separate times this week. It tests whether you can make several independently-correct pieces cooperate inside one running process without any of them silently breaking another. That's a different skill, and it's the one real production code actually demands every day.
Quick recap
  • Today combines 6.1 (service), 6.2 (measurement), 6.3 (fallback), 6.4 (logging/health), and 6.5 (regression gate) into one process.
  • No new technique — the skill being tested is integration, not any single piece in isolation.
Sub-topic 2 of 5

2. What "deployable" actually means (and doesn't)

Say the word "deployed" out loud and most beginners picture a specific cloud provider's dashboard. That's not what the word actually means in this lab, and it's not what a hiring manager means when they use it either.

What is... "deployable," precisely? A service that starts with one command, reads its configuration from the environment, logs every request, degrades gracefully if its primary model provider fails, and has a passing regression check before you'd call it done. Every clause in that sentence is a property of the code, not a property of where it happens to run. A service demoed live on your own laptop that has all five properties is more "deployable," in every way that matters, than a service running on an expensive cloud host that has none of them.

1. Flask service running on localhost, demoed live over a call,
   called with curl or a simple browser form.

2. Same service, deployed to a free tier of Render, Railway,
   Fly.io, or PythonAnywhere -- for the "it has a real public URL"
   experience. (Check current free-tier terms before relying on
   one long-term -- they change.)

The artifact that matters is identical either way: a project with
a clean README that lets a stranger `pip install -r requirements.txt`,
set a couple of environment variables, and have it working in
under 5 minutes.

That last line — "working in under 5 minutes, for a stranger, without asking you anything" — is the actual bar. It's a harder bar than it sounds. It means your README or DEPLOY.md has to spell out every environment variable, the exact start command, and how to verify the thing is actually healthy — not "should just work," which is the phrase that precedes almost every failed onboarding attempt in real engineering teams.

Why this framing matters beyond the lab
  • Interviewers and hiring managers consistently say the same thing: a project with a working service, a README a stranger can follow, visible logging, and a passing eval gate reads as production judgment — regardless of which specific host it happens to run on.
  • Teams that treat "deployed" as "runs on Cloud Provider X" tend to skip the properties that actually matter (config hygiene, logging, graceful degradation) and only discover the gap during their first real incident.
  • A DEPLOY.md a stranger can follow in 5 minutes is, by itself, a skill worth demonstrating — onboarding friction is one of the most common, least glamorous causes of slow teams.
Quick recap
  • "Deployable" = five concrete properties of the code (one-command startup, env-based config, logging, graceful degradation, passing regression check) — not a specific cloud host.
  • Local-and-demoed-live and free-tier-hosted both satisfy the lab equally.
  • The real bar: a stranger, using only your DEPLOY.md, working in under 5 minutes, without asking you anything.

3. The startup-time regression gate

The Pro path's centerpiece is a small but genuinely important design decision: where does the regression check from Session 6.5 actually run? A CI pipeline is the obvious answer — and it's necessary, but it isn't sufficient on its own.

What is... a startup-time gate? A CI-time regression check only fires when a change goes through the normal pull-request pipeline. It cannot catch a service that gets started with bad configuration outside that pipeline — a manual deploy that skips CI, a stale prompt version left in an environment variable, a golden dataset pointed at the wrong file. A startup-time gate re-runs the same check every single time the process boots, regardless of how it got into that state, and refuses to start at all if the check fails.

Here's the actual shape of it in this lab's starter code. Two functions carry all the weight:

starter.py (excerpt) 
def call_model_with_fallback(question: str) -> str:
    """
    TODO 1: call _call_primary; on ConnectionError, call _call_fallback instead.
    """
    raise NotImplementedError


def run_regression_check() -> bool:
    """
    TODO 2 (Pro path): score GOLDEN_DATASET against call_model_with_fallback
    (a simple substring/keyword check is fine), compute pass rate, print it,
    and return True only if pass rate >= REGRESSION_THRESHOLD.
    """
    raise NotImplementedError


if __name__ == "__main__":
    # Pro path: startup-time regression gate -- refuse to start if it fails.
    if not run_regression_check():
        print("FATAL: regression check failed at startup. Refusing to start.", file=sys.stderr)
        sys.exit(1)

    port = int(os.environ.get("PORT", 5000))
    app.run(port=port)

Notice the order of operations: the gate runs before app.run() ever executes. If run_regression_check() returns False, the process exits with a non-zero status and never opens a port at all — there's no window where a broken service is technically "up" and silently serving bad answers.

Try the core mechanic here — a small, self-contained version of the same try/except fallback and pass-rate gate the real service uses, shrunk down to something you can run and tweak in a few seconds:

fallback_and_gate.py
Click "Run Code" — notice the fallback keeps every question answered even when the primary "fails," and the gate only blocks startup on the pass rate, not on any individual provider hiccup.

Thought process: the interesting design decision here isn't the try/except — it's deciding what counts as "passing" for the regression check, and deciding to fail loudly (exit non-zero, no port opened) instead of failing quietly (start anyway with a logged warning). An experienced engineer treats "refuse to start" as the safer default for anything customer-facing, because a service that's silently degraded and technically "up" is far more dangerous than one that's visibly down — the second gets paged immediately, the first gets discovered by an angry user.

Paste your prompt into Claude, ChatGPT, Copilot, or whatever assistant you use, and compare what it builds against this session's exercise — does it actually exit non-zero and skip app.run() on a failed gate, or does it just log a warning and start anyway? That comparison is the real test, not a score.
Show a strong version of this prompt 
Write a Python Flask service with: (1) a call_model_with_fallback(question) function that calls a primary model function and, on ConnectionError specifically, retries against a secondary fallback function; (2) a POST /ask endpoint that validates a "question" field is present, calls call_model_with_fallback, times the call, logs the input/output/latency to an in-memory list, and returns the answer plus latency as JSON; (3) a GET /health endpoint that returns a status and the count of requests served so far, without calling the model at all; (4) a run_regression_check() function that runs a small golden dataset of question/expected pairs through call_model_with_fallback, computes a pass rate against a threshold, prints the result, and returns a boolean; (5) in the __main__ block, call run_regression_check() BEFORE app.run() and sys.exit(1) with a clear stderr message if it fails, so the service never actually starts serving traffic in a known-bad state. Read the port from the PORT environment variable, defaulting to 5000.
Go Deeper: why "refuse to start" beats "start with a warning"

It's tempting to make the startup gate softer — log a warning and start anyway, so a flaky golden-dataset example doesn't take the whole service down. Resist that temptation for anything customer-facing. A service that's visibly down gets noticed immediately: a monitoring alert fires, an on-call engineer gets paged, the fix happens in minutes. A service that's quietly serving degraded answers behind a green "status: ok" health check can run for days before anyone realizes something's wrong — and by then it's a customer complaint, not a deploy log. The failure mode you can see immediately is almost always cheaper than the one that hides.

Quick recap
  • A CI-only regression check can't catch bad config introduced outside the normal PR pipeline — a manual deploy, a stale env var, a wrong golden dataset file.
  • A startup-time gate re-runs the same check on every boot and refuses to open a port if it fails — no window where a broken service looks "up."
  • Failing loudly (non-zero exit, no port) is the safer default; a service that's visibly down gets fixed faster than one that's silently degraded.

4. "Done well" vs. "done technically"

It's entirely possible to fill in every # TODO, watch the service start, and still have missed the point of the lab. Here's the difference, concretely.

Done technically (passes, but misses the point) You implement call_model_with_fallback() and run_regression_check(), the service starts, curl returns an answer, and you call it finished. But your README just says "run the file" with no mention of required environment variables, your /health endpoint was never actually tested against a genuinely broken state, and you never confirmed the gate really refuses to start when the pass rate is pushed below threshold — you only ever saw it pass.
Done well (the actual goal) You deliberately break something — lower REGRESSION_THRESHOLD past what your mocked providers can hit, or force _call_primary to always raise — and confirm the service actually refuses to start, with a clear message, and exits non-zero. You then hand your DEPLOY.md to someone else (or re-read it cold yourself, after a break) and check whether every step is genuinely followable without any tribal knowledge you happen to be carrying in your head.

That distinction — verifying the failure path actually fails, not just that the happy path happens to succeed — is exactly the instinct Session 6.5's regression-gate thinking was building toward, now applied to your own service instead of someone else's example.

Quick recap
  • "It started and answered one question" and "I verified the failure path actually fails" are different bars.
  • Deliberately forcing a failing regression score is the only way to know your gate genuinely blocks startup, rather than just assuming it would.
  • A DEPLOY.md is only proven correct once someone who isn't you (or you, cold) has actually followed it.

5. Reflection: what clicked, what's fuzzy

Before moving into the Week 6 written exam, take five honest minutes (genuinely worth doing, not a platitude) to answer these for yourself:

  • Could you explain, without looking back, the five properties that make a service "deployable" — and name which Week 6 session each one came from? If shaky, revisit Sub-topic 1.
  • Could you describe a concrete scenario where a startup-time gate catches something a CI-only gate would miss? If not, Sub-topic 3 is worth a second pass.
  • If your service's regression check failed for real production reasons tomorrow, does your current design actually stop it from serving traffic — or does it just log a warning and continue? Answering that honestly is the whole point of Sub-topic 4.

This isn't busywork. The single best predictor of struggling with real production systems later is assuming a safety mechanism works because you wrote it, rather than because you watched it actually catch a failure you deliberately caused.

Quick recap
  • Honest self-assessment now is cheaper than discovering a gap during an actual incident.
  • Shaky on "deployable" → Sub-topic 1 or 2. Shaky on the gate's purpose → Sub-topic 3.
  • A safety mechanism is only proven once you've watched it actually fire.
In the Real World
  • "Show me something you built end to end" is one of the most common real interview prompts for GenAI-adjacent roles — and a single integrated project with visible logging, graceful degradation, and a passing gate answers it far better than five disconnected scripts ever could.
  • Startup-time regression gates are standard practice at companies that have been burned once by a manual deploy or a misconfigured environment variable silently shipping a known-bad prompt version to production.
  • A polished DEPLOY.md is frequently the difference between a project a teammate actually picks up and one that quietly gets abandoned the moment its original author is on vacation.

Points to Remember

  • "Deployable" is five properties of the code, not a specific host: one-command startup, environment-based configuration, request logging, graceful degradation via fallback, and a passing regression check.
  • Local-and-demoed-live and free-tier-hosted satisfy the lab equally — the artifact that matters is a working service plus a DEPLOY.md a stranger can follow in under 5 minutes.
  • A startup-time regression gate catches what a CI-only gate structurally can't: bad configuration introduced outside the normal PR pipeline — a manual deploy, a stale env var, a wrong dataset file.
  • Failing loudly beats failing quietly. Refusing to start (non-zero exit, no open port) is safer for anything customer-facing than starting anyway with a logged warning.
  • Everything from Week 6 is meant to compose. None of Sessions 6.1–6.5 were designed to be used in isolation on a real project — today is proof they actually do fit together.
