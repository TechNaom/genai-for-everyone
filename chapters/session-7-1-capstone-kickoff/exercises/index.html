Session 7.1 Exercises 30–45 min, mostly writing

Exercises: Write & Stress-Test a Capstone One-Pager

This exercise is pure writing plus a small Python checklist script — no API calls, no cost. Write a one-page capstone proposal using the template provided, then run a scope-checker script against it that flags common vagueness red flags before you show it to anyone else.

  • Core path — fill in proposal_template.md for a project you can realistically build using 2-3 techniques from this program, then get it passing the checks in starter.py.
  • Pro path — write two competing proposals for the same underlying problem (one narrow-and-finishable, one ambitious-and-risky) and make an explicit written case for which you'd actually choose to build.
How to run this You'll need Python 3 — that's it. Everything in starter.py runs with the standard library; no API key, no pip install of anything beyond what ships with Python.
proposal_template.md starter.py solution.py (reference) example_proposal.md (reference)

1 Fill in the proposal template

Copy proposal_template.md and fill in all five sections for your own capstone idea: problem + user, solution sketch, techniques used (and why), success criteria, and out of scope. Aim for something realistically buildable using 2-3 techniques from this program in the 2-3 sessions remaining before demo day.

2 Implement the scope checker

Find check_required_sections(), check_vague_phrases(), and check_success_criteria_has_number() in starter.py and implement each. Together they catch missing sections, filler phrases like "everything"/"helps with", and a success criterion with no measurable number in it.

3 Run it against your own proposal

Run python3 starter.py your_proposal.md. Fix anything it flags, then get a peer (or yourself, a day later) to re-read the one-pager and check that a stranger could picture the end-to-end system in two minutes.

🐞 Task 4 — Don't let the checker be the whole bar

The scope checker only catches mechanical red flags — a missing section, a filler phrase, a success-criteria sentence with no digit in it. A proposal can pass all three checks and still describe an unrealistically large project, or a success criterion that's technically numeric but not actually meaningful (e.g. "works 100% of the time" is a number, but not a credible one). Passing the checker is necessary, not sufficient — the real test is still whether a mentor reading it in two minutes could immediately spot an over-scoped idea.

Checking your work There's no automated grader for the writing itself, the same way there's no automated grader for a real project proposal review. Confirm: your proposal passes all three scope-checker checks, your success criterion names an actual number tied to a concrete test (not just any digit), and your "out of scope" section names at least one thing a reader might otherwise assume was included. Compare against example_proposal.md and solution.py once you've made a genuine attempt.
Pro path — extended challenge Write two competing proposals for the same underlying problem — one narrow-and-finishable, one ambitious-and-risky — and make an explicit written case for which you'd actually choose to build given the time remaining, using the same scope-vs-time-vs-risk reasoning a real team would use in a project kickoff meeting. Both proposals should still pass the scope checker cleanly; the challenge is the trade-off reasoning, not looser scoping discipline.
