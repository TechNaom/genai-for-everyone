Session 7.2 Exercises 30–45 min

Exercises: Case Study Analysis Worksheet

Analyze the support-ticket-triage case study from the lesson using a structured worksheet, then run a small script that scores your worksheet for completeness. This is pure analysis and writing — no API calls, no cost, just Python 3 for the checker script.

case_study_worksheet.md starter.py solution.py (reference) filled_worksheet_example.md (reference)

1 Core path — fill in the worksheet

Fill in case_study_worksheet.md for the support-ticket triage case study, identifying where each Week 1–6 concept shows up: predictive vs. generative components, at least 4 concepts from the program (e.g. RAG grounding, confidence-based gating, drift, guardrails) and where each appears, a one-paragraph root-cause analysis of the data-loss incident, and one thing you'd have flagged as a risk before launch.

2 Run the completeness checker

Find split_sections() in starter.py and implement it: split the worksheet text into a dict of {section_header: section_body} for each header in REQUIRED_SECTIONS, where a section's body is the text between its header and the next one (or end of file). Then run:

terminal 
python3 starter.py case_study_worksheet.md

The script checks that every required section is present and has at least 15 words — enough to catch a skipped section or a one-sentence non-answer, not enough to enforce any particular "correct" analysis. This is a completeness check, not a correctness check — a worksheet can pass every check here and still contain a shallow or wrong analysis. The value is in actually writing the analysis, not in passing the script.

3 Pro path — extended challenge

Propose a specific, concrete redesign of the confidence-gating logic that would have caught the drift problem earlier (new/unrecognized ticket types being force-fit with high confidence). Write it as a short design note, as if proposing this change to the team that owns this system — not a separate code file, a piece of writing with the same rigor as the worksheet's root-cause section.

Checking your work There's no automated grader for the analysis itself, the same way a real case-study critique doesn't get graded by a script. Confirm instead: the checker reports all four sections present with 15+ words each, your root-cause paragraph names both compounding gaps (not just the stale doc), and your pro-path design note proposes something concrete enough that a teammate could actually implement it — not just "add better monitoring." Compare against filled_worksheet_example.md once you've made a genuine attempt, and check your split_sections() implementation against solution.py.
