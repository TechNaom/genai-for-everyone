Capstone Build Day I

Build a working v1 of your capstone using an MVP-first, milestone-driven approach — so that by the end of this session you have something that runs end to end, even if incomplete, rather than several unfinished pieces.

On this page 1. MVP-first, not perfect-first 2. Milestone checkpoints 3. When to ask for help vs. push through
The single biggest risk on a build day isn't running out of skill — it's running out of time with nothing that runs. The fix is a discipline borrowed directly from real engineering teams: build the thinnest possible end-to-end version first, then layer in depth, rather than perfecting one piece before touching the next.
Part 1 of 3

1. MVP-first, not perfect-first

For a RAG-based capstone, "thinnest possible end-to-end version" looks like: hard-code 3 documents, get retrieval-then-generation working with the ugliest possible prompt, and print an answer to the console. That is a complete pipeline, even though every piece of it is crude. Only after that works do you improve chunking, add more documents, improve the prompt, or add a UI.

The alternative to avoid Perfecting your chunking strategy before you've ever generated a single answer risks ending the day with a beautiful chunker and nothing that actually answers a question.
Quick recap
  • Build the crudest possible complete pipeline first — hard-coded documents, an ugly prompt, console output.
  • Improve chunking, add documents, refine the prompt, and add a UI only after that pipeline runs end to end.
Part 2 of 3

2. Milestone checkpoints

Break the build into checkpoints with a rough time budget, and treat each checkpoint as a go/no-go decision point, not just a to-do list item:

checkpoints.txt 
Checkpoint 1 (≈25% of build time): Thinnest possible end-to-end pipeline runs, however crude
Checkpoint 2 (≈50%): Core path functionality from your proposal works on your golden dataset examples
Checkpoint 3 (≈75%): At least one Week 5 eval pass done (does it actually work, not just "did it run")
Checkpoint 4 (≈100%): Pro path extension attempted, or scope consciously cut if time ran short

If you're not at Checkpoint 1 by 25% of your time, that's the signal to simplify immediately — cut a feature, hard-code something you meant to make dynamic, use a smaller document set — rather than pushing forward on the original plan and hoping time works out.

Quick recap
  • Four checkpoints, roughly at 25/50/75/100% of your build time: thin pipeline, core path on golden examples, an actual eval pass, pro path or a conscious scope cut.
  • Behind at a checkpoint? Simplify immediately — that's the point of treating it as go/no-go, not a hope-it-works-out to-do list.
Part 3 of 3

3. When to ask for help vs. push through

Two failure modes are equally costly on a build day: asking for help on something you could solve in 2 more minutes of debugging, and silently struggling for 40 minutes on something a mentor could unblock in 2.

A reasonable rule If you've been stuck on the same specific error for more than 10–15 minutes with no new information, that's the signal to ask — not a sign of failure, but time-management discipline.
Quick recap
  • Silently struggling for 40 minutes and asking too early are both costly — the goal is the right threshold, not "never ask" or "always ask."
  • 10–15 minutes stuck on the same error with no new information is the signal to ask — treat it as time management, not failure.
In the Real World
  • A team building a demo for a Monday board meeting spends three days perfecting the retrieval quality for one document type, then discovers on Friday afternoon that the generation step, never tested end to end, produces malformed output for their actual use case.
  • An MVP-first approach — thin pipeline working by day one — would have surfaced that problem three days earlier, when there was still time to fix it.

Points to Remember

  • Build the thinnest possible end-to-end pipeline first; only then improve individual pieces — a complete crude system beats a polished incomplete one, every time you're short on time.
  • Treat checkpoints as go/no-go decision points: if you're behind schedule at a checkpoint, simplify immediately rather than hoping to catch up later.
  • Getting unblocked quickly (asking after 10-15 minutes stuck) is a time-management skill, not a sign you're behind — silently struggling for 40 minutes is the actual failure mode to avoid.
  • A capstone v1 that runs end to end, even simplified, is worth more at the end of a build day than several unfinished, individually-impressive pieces.
