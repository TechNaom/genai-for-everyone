Session 7.4 Interview Prep 10 min read

Interview Questions: Reading Systems, Human-in-the-Loop, and Peer Review

These questions draw on today's case study and build-day themes: reading an unfamiliar system critically, the trade-off behind keeping a human in the loop, diagnosing a problem in someone else's system, and evaluating a project honestly — the exact muscle both today's case study and today's peer review exercise. Each question below includes what a strong answer sounds like, common red flags, and a natural follow-up. Click any question to expand it.

1 I'm going to describe a system to you that you've never seen before: it's a support-ticket triage tool that classifies tickets and drafts suggested responses, gated by a confidence score. What would you want to know before you trusted this system?
Strong answer

Ask where evaluation happens and against what dataset. Ask what the fallback/review path is for low-confidence or uncertain cases. Ask how drift would be detected — is the confidence calibration re-validated over time. Ask whether guardrails or review requirements are applied consistently across all risk levels, or unevenly. This is the same posture the contract-review case study rewards: don't take a system's stated behavior at face value, probe specifically for where the review gate might be inconsistent or where confidence might be miscalibrated for a subset of high-stakes cases.

Red flags

"Looks good to me" with no probing questions; only asking about the model or technology, never about evaluation or failure handling; not asking what happens when the system is wrong.

Follow-up

"Given what you now know about this exact system, what's the single most likely place for a hidden failure to be hiding?"

2 A stakeholder asks: "Why do we need a human to review every flagged output if the model is usually right?" How do you answer?
Strong answer

Reframe "usually right" as not the relevant bar — the value of human review is specifically in catching the rare, confidently wrong cases. Explain that in high-stakes domains, the cost of a rare miss can vastly outweigh the cost of routine review time. Point to a concrete category of failure — like the contract-review case study's near-miss, where a model treated a small wording difference as insignificant when it was actually legally significant — where confidence alone would have been misleading.

Red flags

"If it's usually right, we probably don't need review" (misses the entire point of human-in-the-loop design); no concrete example of what a confident-but-wrong failure looks like; not distinguishing stakes or domain as a factor in the decision.

Follow-up

"Under what conditions would you feel comfortable removing the human review step for a subset of cases?"

3 An eval report shows accuracy dropped from 90% to 60% over the past month, with no code changes. Walk me through how you'd diagnose this.
Strong answer

Don't guess at a fix immediately — investigate the specific failing examples first to find the pattern. Consider drift explicitly: has the input distribution changed, has an underlying model or document set changed. Check whether the golden dataset itself is still representative, or needs updating. Propose a systematic diagnostic process, not a single guess — the same discipline the contract-review case study's severity-scoring fix required: identify exactly what's failing and why, before deciding what to change.

Red flags

Proposing a fix ("just retrain it" or "switch models") before investigating the actual failure pattern; not mentioning drift as a possible cause; treating this as necessarily a code bug.

Follow-up

"You find the drop is concentrated entirely in one specific question category. What does that tell you, and what would you check next?"

4 Two candidates have technically similar projects. One's GitHub README is a single line: "RAG chatbot, run python app.py." The other has a paragraph on the problem, a screenshot, eval numbers, and run instructions. Does this matter, and why?
Strong answer

Yes, it matters — a recruiter or hiring manager skimming for under two minutes needs the value made instantly visible. The fuller README demonstrates the same judgment and communication skill being assessed in "walk me through your project," just in written form. Note the README's real audience: a stranger with zero shared context, not someone who already knows the project — the same reason a peer-review checklist has to be legible to someone who didn't build the thing being reviewed.

Red flags

"The code is what matters, not the README" (misses that unreviewed code has zero signal to a time-constrained reviewer); no mention of the README's actual audience.

Follow-up

"What's the one thing you'd cut from a README if you only had room for 4 of the 5 recommended sections?"

5 Walk me through a GenAI project you built.
Strong answer

Lead with the problem and specific user, not a list of technologies. Explain the approach and why that approach was chosen over alternatives. Name one specific hard trade-off or decision made during building. State actual success criteria and whether they were met, with real numbers — the exact thing a peer-review checklist is designed to catch if it's missing.

Red flags

"I used LangChain, a vector database, and Claude" with no problem statement or reasoning; no mention of how they know it worked; can't name a single hard decision or trade-off.

Follow-up

"What would you do differently if you rebuilt this from scratch today?"

Strategy Tips

  • Interviewers testing this material often hand you an unfamiliar system description rather than ask you to define terms — practice asking targeted probing questions (evaluation, fallback path, drift detection) instead of giving a generic "looks fine."
  • The human-in-the-loop question rewards naming a concrete failure category, not just repeating "safety is important."
  • When asked to evaluate someone else's project or README, remember the real audience is a stranger with zero shared context — the same standard your own capstone's peer review should be judged against.
