Session 7.5 Exercises 30–45 min

Exercises: Practice Your Project Answer

Practice a "walk me through your project" answer for your own capstone, then run it against a self-check script that flags whether each of the four required elements is present. There's no core/pro split into separate builds this session — instead there's one exercise with a harder pro-path extension:

  • Core path — write your project answer, run the checker, fix flagged gaps.
  • Pro path — run a full timed mock interview (system design + live debugging) using the provided question bank, and write structured feedback.
How to run this You'll need Python 3 — that's it. starter.py runs with the standard library only; no API key, no pip install of anything beyond what ships with Python.
starter.py solution.py (reference)

1 Write your project answer

In a plain text file (e.g. my_answer.txt), write a "walk me through your project" answer for your own capstone, following the four-part structure from the lesson: the problem and user, the approach and why that approach over alternatives, one specific hard trade-off you made, and your actual success criteria (how you know it worked).

2 Implement the checker

Open starter.py and find check_answer(). For each element in REQUIRED_ELEMENTS, check case-insensitively whether any of its keyword list appears in the answer text, and return a dict of {element_name: True/False}.

3 Run it against your own answer

Run python3 starter.py my_answer.txt. Fix any element flagged as missing — either by adding it to your answer if it's genuinely absent, or by rephrasing if you covered it with different wording than the checker's keyword list expects.

Checking your work Run python3 starter.py example_answer.txt (the reference example in this folder) once your check_answer() is implemented — it should report all 4/4 elements present. Compare against solution.py once you've made a genuine attempt.

🐞 Watch out for — keyword matching is a blunt instrument

The checker only looks for specific keyword strings, so it can produce false negatives on a genuinely good answer that just uses different wording (e.g. "picked" instead of "chose"), and false positives if a keyword appears without the substance behind it (e.g. the word "success" mentioned in passing with no actual criteria named). That's a fair trade for a simple self-check script — treat a "missing" flag as a prompt to re-read that part of your answer critically, not as an automatic failure.

Pro path — extended challenge Do a full mock interview with a peer (or self-run using question_bank.md): one system design question and one live-debugging question from the provided sets, timed at 15 minutes each. Then write structured feedback for the other person (or yourself) following the "specific, actionable" standard from the lesson — name the exact moment something went well or poorly, not just "that was good" or "that needs work."
