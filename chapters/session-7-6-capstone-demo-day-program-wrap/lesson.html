Session 7.6 Capstone 15–20 min read

Capstone Demo Day & Program Wrap

Present your capstone in a demo format that actually lands with an audience, and write a portfolio README that makes the project legible to a stranger — a recruiter, a hiring manager, or a future you six months from now.

On this page 1. The demo: structure beats improvisation 2. The portfolio README: written for someone who will never talk to you 3. Career next steps
Seven weeks of building comes down to a few minutes of demo, and separately, to whatever's left in your GitHub repo after the program ends. Both need to be optimized deliberately — neither happens well by accident.
Part 1 of 3

1. The demo: structure beats improvisation

A strong 5-minute capstone demo follows a tight shape:

five-minute-demo.txt 
1. The problem, in one sentence (not "let me show you my architecture")
2. A live example, showing real input -> real output
3. One thing that went wrong during building, and how you fixed it
   -- the single highest-signal moment in most demos, because it
   shows judgment, not just a working feature
4. Your actual success criteria and whether you met them (numbers, not vibes)
5. What you'd build next, if you had another week

Notice what's not in this list: a tour of every file in your codebase, or an explanation of every technology used. Demo time is scarce; spend it on the story, not the inventory.

Quick recap
  • A strong demo has five beats: problem, live example, one real thing that went wrong and how you fixed it, actual success numbers, and what's next.
  • The "what went wrong" beat is the highest-signal moment in most demos — it shows judgment, not just a working feature.
  • Demo time is scarce: spend it on the story, not a tour of every file or technology.
Part 2 of 3

2. The portfolio README: written for someone who will never talk to you

Six months from now, a recruiter finds your repo, reads it for 90 seconds, and decides whether to reach out. That README needs, in order:

What a portfolio README needs, in order
  • What the project does and for whom (one paragraph)
  • A way to see it work — a screenshot, a GIF, or a live demo link (text alone undersells a working project)
  • What techniques it uses and why (your Session 7.1 language, refined)
  • How you evaluated it (your actual numbers)
  • How to run it yourself (your Session 6.6 DEPLOY.md pattern)

This is the same discipline as every session doc in this program: concept, then evidence, then how to actually use it.

Quick recap
  • A recruiter reads your README for about 90 seconds — it has to work for a stranger with zero shared context, not a peer from this program.
  • The five required elements, in order: what/for whom, proof it works, techniques + why, eval numbers, and how to run it.
  • Same discipline as every other session doc: concept, then evidence, then usage.
Part 3 of 3

3. Career next steps

The program's real output isn't a certificate — it's a portfolio and a vocabulary. Concretely, before you consider this "done":

Before you call it done
  • Your capstone repo has a real README (above).
  • Your resume or LinkedIn references the specific techniques you used — not "AI," but "built a RAG pipeline with a golden-dataset eval and a red-team safety pass" (the language from Weeks 3 and 5).
  • You've identified one or two follow-up projects that would extend this work, so the learning doesn't stop at demo day.
Quick recap
  • The program's real output is a portfolio and a vocabulary, not the certificate.
  • Use specific technique language on your resume/LinkedIn, not a vague "I used AI."
  • Name one or two follow-up projects so the learning continues past demo day.
In the Real World

Two capstones are equally good technically. One repo has a one-line README saying "RAG chatbot, run python app.py." The other has a paragraph on the problem, a screenshot of it working, the eval numbers, and clear run instructions. A recruiter skimming GitHub profiles for 90 seconds each will remember the second one — and that's the entire game of a portfolio, regardless of how good the code underneath actually is.

Points to Remember

  • A strong demo has five beats: problem in one sentence, live example, one real thing that went wrong and how you fixed it, actual success numbers, and what's next — not a tour of every file.
  • A portfolio README is written for a stranger who will never talk to you — it needs to answer "what is this, does it work, and how do I run it" in under 90 seconds of reading.
  • Describing your project using specific technique vocabulary (RAG + golden dataset + red-team pass) demonstrates real skill in a way that "I used AI" never will.
  • This program's real output is a portfolio and a vocabulary you can use in an interview — the certificate is secondary to both.

Core path: write your capstone's portfolio README following the structure above, and prepare your 5-minute demo script (the 5 beats above, timed) — then run the README checker to confirm all required elements are present. Pro path: deliver the actual 5-minute demo (to a peer, mentor, or recorded for self-review) and get feedback on whether the problem statement was clear in the first 30 seconds, whether the "what went wrong" moment was concrete, and whether the success criteria were real numbers rather than impressions.
